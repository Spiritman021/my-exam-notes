Chapter 22

IPv4 Header

Every IPv4 packet (datagram) starts with this header. It carries the two addresses from chapter 19, plus everything a router needs to forward the packet: how long it is, whether and how it has been fragmented, how many more hops it may take, and which protocol sits inside. Two fields are too small to hold their real values directly, so they use scaling factors: HLEN counts in 4-byte units and Fragment Offset in 8-byte units. Numericals almost always come from those two and from fragmentation.

22.0The Header at a Glance (20–60 bytes)

🎓 From the lecture The bit positions run 0 to 31: each row is 32 bits = 4 bytes, the size of one IP address (the source and destination rows). The header has 6 horizontal slots: the first 5 are mandatory, the 6th is options, which can be 0 to 40 bytes.
So the minimum header = 5 × 4 = 20 bytes (no options) and the maximum = 20 + 40 = 60 bytes. After the header comes the data / payload from the layer above. The whole thing (header + data) is called a datagram; its total size can go up to about 2¹⁶ bytes, which is why the Total Length field is 16 bits.

22.1Version Field

🎓 From the lecture VER = 4 bits, enough to write 4 or 6. IPv4 = 0100 (4); IPv6 = 0110 (2 + 4 = 6).
➕ Why it matters The version is the first field so a receiver can tell at once how to parse the rest. A router receiving a packet whose version does not match the protocol it is running drops it.

22.2Header Length (HLEN) and Scaling Factor

🎓 From the lecture The header is 20 to 60 bytes, but HLEN has only 4 bits: values 0 to 15. It can't even hold 20! So a scaling factor is used: (maximum header length) ÷ (largest 4-bit value) = 60 ÷ 15 = 4.
HLEN therefore counts in units of 4 bytes: header length = HLEN × 4. HLEN = 5 → 5 × 4 = 20 bytes (0101); HLEN = 15 → 60 bytes. Values 0–4 are never used, because the mandatory 20 bytes must always be there. So HLEN ranges 5 to 15 (20 to 60 bytes).
header length (bytes) = HLEN × 4 valid HLEN: 5 … 15 → 20 … 60 bytes options length = (HLEN × 4) − 20

22.3Type of Service (TOS)

🎓 From the lecture TOS is an 8-bit field (4 + 4 + 8 + 16 = the first 32-bit row). Its first 3 bits are P = precedence, i.e. priority: 000 to 111, 0 = lowest, 7 = highest. Some packets are high priority and must get the road first, just as all vehicles make way for an ambulance.

22.4Type of Service (TOS) Bits

TOS byte: P P P | D T R C | 0 precedence TOS bits unused
🎓 From the lecture Next come 4 TOS bits: D = delay, T = throughput, R = reliability, C = cost. We want low cost, high reliability, high throughput, low delay.
• 0000 → default / normal service
• 0001 (C set) → minimise cost
• 0010 (R set) → maximise reliability
• 0100 (T set) → maximise throughput
• 1000 (D set) → minimise delay
➕ Today's meaning: DSCP + ECN RFC 2474/3168 redefined this byte as DSCP (6 bits, Differentiated Services Code Point, used for QoS, e.g. EF = 46 for voice) plus ECN (2 bits, Explicit Congestion Notification). Exams on "IPv4 header" usually expect the classic precedence + DTRC view; if "DiffServ" is mentioned, answer DSCP.

22.5Total Length and Data Length

🎓 From the lecture Total Length = 16 bits, maximum 65 535 bytes = header length + data length. We have both a total-length field and a header-length field, so the data length is easy: data = total length − header length. Careful: first multiply HLEN by the scaling factor 4, then subtract. The answer can never be negative, since the total includes the header.
data length = Total Length − (HLEN × 4) max data = 65 535 − 20 = 65 515 bytes

22.6IPv4 Fragmentation and MTU

🎓 From the lecture Sender and receiver are on different networks with a router in between; each network has an MTU. The receiving side says "I can't take more than 200 bytes per packet." Biscuit analogy: an adult eats a whole biscuit in one go, but a small child has a tiny mouth, so we break the biscuit into pieces and feed them one by one: that is fragmentation.
The sender has 500 bytes of data + 20-byte header = 520 bytes. Too big. Break the data: first try 180 + 180 + 140 (= 500). Why 180? To get as close to the MTU as possible, while each fragment still needs its own 20-byte header: 200 − 20 = 180. Each fragment is then ≤ 200 bytes and is accepted. (We will adjust 180 shortly; see 22.8.)

22.7Identification Field

🎓 From the lecture Identification = 16 bits. When fragments arrive at the receiver, fragments of other packets may be arriving too, so they could get mixed up. School-uniform analogy: at a big city function attended by students from many schools, you recognise each student's school by the uniform. Likewise, every fragment of one original packet gets the same identification number (say 10, 10, 10). The receiver sees the same ID and knows these pieces belong to one datagram.

22.8Fragment Offset and Scaling Factor

🎓 From the lecture Fragment Offset = 13 bits. It says how many bytes of data are ahead of me (before this fragment in the original). First fragment: 0 bytes ahead → offset 0 (so offset 0 always marks the starting fragment). Second: 180 bytes ahead → 180. Third: 180 + 180 = 360.
The big problem: data can be up to 65 535 − 20 = 65 515 bytes. In the worst case the last fragment carries 1 byte with about 65 514 bytes ahead of it, roughly 2¹⁶, which needs 16 bits. We only have 13.
Fix: scaling factor, just like HLEN: 2¹⁶ ÷ 2¹³ = 2³ = 8. The offset is stored in units of 8 bytes, so every fragment's data size (except the last) must be divisible by 8.
180 ÷ 8 = 22.5: not a whole number! So adjust: take 4 bytes off each of the first two fragments (180 → 176) and add those 8 bytes to the last (140 → 148). Nothing is lost; the bytes just move. Now offsets are 0 ÷ 8 = 0, 176 ÷ 8 = 22, 352 ÷ 8 = 44, all fitting in 13 bits.
offset field = (bytes of data before this fragment) ÷ 8 first byte of this fragment = offset × 8 max data per fragment = ⌊(MTU − header) ÷ 8⌋ × 8 (except the last fragment)

22.9Flags: MF and DF

Flags (3 bits) = 0 (reserved) | DF | MF
🎓 From the lecture MF (More Fragments): more pieces are coming. In every fragment except the last, MF = 1; in the last one MF = 0 (no more fragments after it).
DF (Don't Fragment): DF = 1 means "do not fragment this packet"; DF = 0 means it may be fragmented.
MFOffsetThis packet is…
00not fragmented at all (whole datagram)

➕ DF in practice If DF = 1 and the packet is larger than the next link's MTU, the router drops it and returns an ICMP "Destination Unreachable: Fragmentation Needed" message. Path MTU Discovery deliberately sets DF = 1 and uses these replies to find the smallest MTU on the path.

22.10Time to Live (TTL)

🎓 From the lecture A router doesn't know where to send a packet, so it hands it to its default router ("I don't know, go ask him"). R1's default is R2, R2's is R3, and R3's default is R1. The packet keeps going round: an infinite loop that creates congestion.
TTL (Time To Live) fixes it: at every hop the TTL is decremented by 1. If a router finds it has reached 0, the packet is discarded. Example: the sender knows the receiver is 3 hops away and sets TTL = 3; 3 → 2 → 1 → 0 on arrival. In the loop, TTL 3 → 2 → 1 → 0 at a router → dropped.
⚠️ Exam trap The lecture says TTL "should be 0 at the receiver". In reality the sender sets a generous TTL (commonly 64 on Linux/macOS, 128 on Windows, max 255, since the field is 8 bits); it simply has to stay above 0 until delivery. Exam facts: TTL is 8 bits; it is decremented by each router; at 0 the router drops the packet and sends ICMP Time Exceeded; traceroute exploits this by sending TTL = 1, 2, 3 …

22.11Protocol Field

🎓 From the lecture Protocol = 8 bits: which protocol's data is inside, so the receiver knows whom to hand it to. Numbers: ICMP = 1, IGMP = 2, TCP = 6, UDP = 17.
The lecture also describes a priority use: when a router's buffer is full and a TCP packet arrives, the router throws out a lower-priority packet (it looks for ICMP first) to make room. Priority order given: TCP > UDP > IGMP > ICMP.
⚠️ Exam trap The protocol numbers are standard and asked very often: 1 ICMP, 2 IGMP, 6 TCP, 17 UDP (also 89 OSPF, 41 IPv6-in-IPv4, 50 ESP, 51 AH). The "drop ICMP first" priority order is the lecture's teaching example, not part of the IP standard. Real routers decide what to drop by queue policy (tail drop, RED) and QoS marking.

22.12Header Checksum

🎓 From the lecture 16-bit field. Divide the header into 16-bit (2-byte) parts and compute a checksum the same way as in chapter 14 (wraparound sum + one's complement); store it here.
It is recomputed at every router / node on the path, because header fields change in transit: the TTL drops at every hop, options may change, and corruption can hit total length or HLEN.
➕ Precise points It covers the header only, not the data (TCP/UDP have their own checksums for the payload). During computation the checksum field itself is taken as 0. A router that finds a mismatch drops the packet silently. IPv6 removed the header checksum entirely to speed up routers.

22.13Options: Record Route

🎓 From the lecture Options: 0 bytes (header = 20) up to full capacity (header = 60). Record route: as the packet goes from source to destination, every router it passes writes its IP address into the options field: R1, then R2 … At the destination you know the whole route. Like a traveller texting "reached X, now Y, now Z" on the way to Delhi, and relatives at the destination saying "you took the long way, you should have asked me!"
How many routers fit? One IP address = 4 bytes; options = 40 bytes, so in theory 10. But some space must be kept (for the option's own header, padding and so on), so in practice a maximum of 9 router addresses can be recorded.
➕ Why exactly 9 The record-route option itself needs 3 bytes (type, length, pointer). 40 − 3 = 37 bytes → ⌊37/4⌋ = 9 addresses. That is why ping -R shows at most 9 hops; traceroute (TTL-based) has no such limit.

22.14Options: Strict and Loose Source Routing

🎓 From the lecture Source routing: the source specifies the path to the destination, stored in the options field.
Strict source routing = Mummy's advice. Going to mama's house, Mummy knows the safe road, where the danger and the traffic are, and tells you exactly: "go R1, then straight to R2, don't even dare look at R4, then R3, then the destination." You must follow this path exactly, however free or busy the other roads are.
Loose source routing = Papa's advice. Papa is chill: "You'll pass the R1 chowk after leaving home and the R3 chowk before mama's house. Between them, go via R2 or R4, your call." Only some landmarks are fixed; the rest of the path is your choice.

➕ Security note Source routing lets an attacker steer packets around firewalls, so almost all routers today block source-routed packets. It is an exam topic, not a practical tool.

22.15Options: Padding

🎓 From the lecture The header length must fit HLEN's 4-byte units. Suppose the header comes to 30 bytes: 30 ÷ 4 is not a whole number. So pad the options field with extra bytes until it divides: add 2 bytes → 32 bytes → 32 ÷ 4 = 8, which HLEN can hold. That is what the leftover option bytes are used for.
⚠️ Exam trap 30 ÷ 4 = 7.5 (the transcript says 7.2). Rule: the header length must always be a multiple of 4 bytes; padding (zeros) fills the gap. Padding needed = (4 − header mod 4) mod 4.

Solved numericals Q1. HLEN = 8. Header size and options size? 8 × 4 = 32 bytes; options = 32 − 20 = 12 bytes.

Q2. Total Length = 1000, HLEN = 5. Data length? 1000 − 20 = 980 bytes.

Q3. A fragment has offset 100, HLEN 5, Total Length 500, MF = 1. First and last data byte numbers? Is it the last fragment?
First byte = 100 × 8 = 800; data = 500 − 20 = 480 → last byte = 800 + 480 − 1 = 1279. MF = 1 → not the last fragment.

Q4. A 4000-byte datagram (20 header + 3980 data) enters an Ethernet link (MTU 1500). Fragments?
Max data = ⌊(1500 − 20)/8⌋ × 8 = 1480. Fragments: data 1480 / 1480 / 1020; offsets 0 / 185 / 370; MF 1 / 1 / 0; total lengths 1500 / 1500 / 1040. 3 fragments.

Q5. A packet arrives with MF = 0 and offset = 0. → It was never fragmented.

Q6. Header length 26 bytes before padding. Padding and HLEN? 26 → 28 (pad 2), HLEN = 28/4 = 7.

Q7. TTL arrives as 1 at a router that is not the destination. → Router decrements to 0, drops it, sends ICMP Time Exceeded.
🎯 IBPS exam alert Fast facts: min/max header 20/60; HLEN unit 4; offset unit 8; total length max 65 535; fragmentation fields = Identification, Flags, Fragment Offset; TTL and Protocol are 8 bits; reassembly happens only at the destination; checksum covers the header only.

⚡ Rapid Revision — Chapter 22

  • Header = 5 mandatory rows × 4 bytes = 20 + options 0–40 → 20–60 bytes. Datagram ≤ 65 535 bytes.
  • Version 4 bits (0100). HLEN 4 bits × 4 (5–15 → 20–60). Data = Total Length − HLEN×4.
  • TOS 8 bits: PPP precedence (ambulance) + D T R C (min delay, max throughput, max reliability, min cost).
  • Fragmentation (biscuit for a child): 500 B data, MTU 200 → 176 + 176 + 148, offsets 0, 22, 44, MF 1,1,0, same Identification (school uniform).
  • Fragment Offset 13 bits × 8 → data in every fragment but the last must be a multiple of 8.
  • Flags: DF = 1 don't fragment; MF = 1 more fragments follow (0 on the last).
  • TTL 8 bits, −1 per hop, drop at 0 → kills default-router loops; traceroute uses it.
  • Protocol 8 bits: 1 ICMP, 2 IGMP, 6 TCP, 17 UDP.
  • Header checksum 16 bits, header only, recomputed at every router (TTL changes).
  • Options: record route (max 9 IPs), strict (Mummy: exact path) vs loose (Papa: landmarks) source routing, padding to a multiple of 4.
