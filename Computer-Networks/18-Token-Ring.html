Chapter 18

Token Ring (IEEE 802.5)

Ethernet lets everyone talk and then sorts out collisions. Token Ring does the opposite: a small permission packet, the token, travels around the ring, and only the station holding it may transmit. There are no collisions and the access delay has an upper bound, which is why it suits deadline-sensitive traffic. The price is housekeeping: lost tokens, frames nobody removes, and a monitor station to clean up. The lecture walks through every one of these problems, and each one explains a bit in the frame format at the end.

18.0Token Ring at a Glance

🎓 From the lecture As the name says, it is about a token and a ring.
  • Topology: ring.
  • Data flow is unidirectional: frames go one way round the ring only; bidirectional flow is not allowed.
  • Acknowledgement exists (unlike Ethernet), of the piggybacking type (ACK + data together).
  • Encoding: Differential Manchester (DME).
  • Data rates: 4 Mbps or 16 Mbps.
  • Access control: token passing (next section).

➕ Background Developed by IBM (1980s), standardised as IEEE 802.5. Physically the stations are wired in a star to a MAU / MSAU (Multistation Access Unit), which forms the logical ring inside and bypasses a failed or switched-off station using relays. That is the "alternative path" the lecture mentions in 18.6. A faster cousin, FDDI (100 Mbps, dual fibre ring), uses the same token idea.
⚠️ Exam trap "Piggybacking" is the lecture's word. In the standard, the "acknowledgement" is really the A and C bits in the frame status field, which the destination sets as the frame passes by and the sender reads when the frame comes back round (18.8). If asked how Token Ring acknowledges, answer with the A/C bits.

18.1Token Passing

🎓 From the lecture The token is "chhota packet, bada dhamaka": a small message with a big impact, because the whole access control depends on it. The first fundamental rule: whoever holds the token transmits. "Hold the token, then transmit the data." Accessing the ring without the token is like boarding a train without a ticket: illegal.
Because flow is unidirectional and access is so strict (only one station holds the token at a time; the others simply cannot transmit), no collisions can happen. It is like a SIM card: with one number you cannot make two calls at the same time.

18.2Ring Latency

Ring latency (RL): the time for one bit to travel all the way round the ring and return to the point where it was sent.
RL = d / v + N × b d = ring length · v = propagation speed N = number of stations · b = delay (bit holding time) at each station
🎓 From the lecture A station holds the token and transmits. Its first bit goes out, takes a full turn round the ring, and comes back to the same position: the time this takes is the ring latency. A longer ring means more time (d); a faster signal means less time (÷ v). On the way, every station holds the bit and releases it (hold, release, hold, release); that takes a tiny time b at each of the N stations, so add N × b.
➕ In bit units b is often given in bits (e.g. 1-bit delay per station). Convert using the data rate: a 1-bit delay at 4 Mbps = 1/(4×10⁶) s = 0.25 µs. Ring latency in bits = RL × data rate: this is the number of bits "in flight" on the ring.

18.3Token Holding Time

🎓 From the lecture Token Holding Time (THT): how long one station may keep the token. The token is so important that if one station just held on to it forever, nobody else could transmit. So there must be a rule: the default THT is 10 ms. Questions often come from THT in two categories: delayed and early token reinsertion.

18.4Delayed Token Reinsertion

🎓 From the lecture Station 1 holds the token and transmits its frame. The frame goes all the way round the ring and comes back, and all this time S1 still holds the token.
A golden rule: whoever put a frame on the ring is responsible for removing it. When the frame returns, only S1 may discard it; S2, S3 and the others never remove it.
Only after its frame has come back does S1 release the token; then S2 can grab it and transmit. It reinserts the token "in a relaxed, delayed manner": transmit → frame takes a round trip → returns to the station → token released.
Total time ≈ Tt + RL (transmission time + ring latency).

18.5Early Token Reinsertion

🎓 From the lecture Here S1 transmits frame 1 and immediately releases the token, so the token follows right behind its frame. S2 receives F1, holds and forwards it, then grabs the token behind it, sends F2, and releases the token behind F2. S3 does the same. The order is always F1, F2, F3 … with the token always last: an important, frequently asked pattern.
When the train of frames reaches S1, S1 may remove only F1. F2 and F3 are removed by their own senders.
There is no round trip wait, so the ring-latency part disappears: total time = Tt only.
Efficiency: in delayed reinsertion there is only one frame on the ring at a time. In early reinsertion there can be as many frames as stations. So early is more efficient, delayed less.

a = RL / Tt. The efficiency formulas are added for the exam and derived in 18.20.

18.6Source-Related Problems: Orphan Packet and Monitor Station

🎓 From the lecture Orphan packet: S1 holds the token and transmits frame 1, but then S1 goes down (hardware, software, OS: any reason). The ring takes the alternative path around the dead station. Since only the sender may remove its frame, and the sender is dead, F1 keeps circling for ever: it has no "parent" left, so it is an orphan.
Solution: the monitor station. Like a class monitor who watches everyone, reports to the teacher who did mischief or skipped homework, and comes running when anything goes wrong, the monitor station watches the whole ring.
Each frame has a monitor bit (M). The sender transmits it with M = 0. When the frame first passes the monitor, the monitor sets M = 1 ("I have seen this one"). If a frame with M = 1 reaches the monitor again, it has gone round once already without being removed, so something is wrong (the source is probably down). The monitor has the authority to discard it.
➕ Standard terms The standard calls it the active monitor; every other station is a standby monitor ready to take over. The active monitor also supplies the master clock, keeps a minimum latency buffer so the whole token fits on a short ring, and (18.10) regenerates lost tokens.

18.7Stray Packet Problem

🎓 From the lecture Stray packet: the frame gets so badly corrupted on its way round that when it returns, the source cannot recognise it: "this isn't mine, I didn't send it, someone else will remove it". So nobody removes it and it keeps circling.
Solution: the monitor again, using the CRC. When the frame was healthy and passed the monitor, its CRC pattern was correct. Now the CRC mismatches, so the monitor knows something went wrong while it was going round, detects it, and removes the frame from the ring.

18.8Destination-Related Problems (A, C, E Bits)

🎓 From the lecture The source is fine; the frame's destination address is S2. What can go wrong at S2?
• Destination down: like calling a phone that is switched off: no matter how many times you try, nobody answers.
• Destination busy: "the number you are calling is busy". Every station has a buffer for incoming frames; if it is full, the station cannot copy the frame.
• Error: the station is available, but its CRC check finds an error, so it does not copy the frame; it must be retransmitted.
• Success: the station copied the frame into its buffer.
Three bits record this: A = address recognised / available, C = frame copied, E = error detected. The sender reads them when the frame comes back.

18.9Token-Related Problems: Captured Token

🎓 From the lecture Working through these problems is really teaching us the frame format (the A, C, E bits just now).
Captured token: S1 grabs the token and won't let go. Everyone else is tired of waiting: "kab chhodega? Monopoly karna chahta hai? Yeh injustice nahi chalega!" So a maximum Token Holding Time of 10 ms is fixed. After 10 ms, whatever the situation, the station must release the token.

18.10Lost Token and Token Return Time

🎓 From the lecture How can a token be lost? S1 holds the token, sends data, and then goes down while holding it: "woh to dooba hi, lekin token ko leke dooba". Now there is no token on the ring and nobody can transmit.
The saviour (masiha) is again the monitor. It uses the Token Return Time (TRT), which has a range:
  • Minimum TRT = RL: nobody grabbed the token; it just went once round the ring.
  • Maximum TRT = N × THT + RL: the worst case, where every one of the N stations grabbed the token and held it for the full THT, plus the trip round the ring.
If the token reappears within this range, all is well. If no token is seen for longer than the maximum TRT, the monitor regenerates a new token and releases it into the ring. Without this, nobody could ever transmit again.
TRT(min) = RL TRT(max) = N × THT + RL monitor regenerates the token if none is seen within TRT(max)

18.11Corrupted Token

🎓 From the lecture The token is a small 3-byte packet, and its bits can get corrupted too. The ring then looks "disturbed" (noise). The monitor discards the corrupted token. Even though it discarded the token itself, it still follows procedure: it waits for the maximum TRT, and when no valid token appears, it regenerates one and releases it into the ring.

18.12Monitor-Related Problems

🎓 From the lecture The one who looks after everyone can fall sick too. Half the problems so far were solved by the monitor, so if it goes down, everyone panics.
Heartbeat: the monitor periodically circulates an AMP (Alive Monitor Packet) round the ring so that everyone knows "apna tiger zinda hai".
Monitor down: the AMPs stop arriving, the stations stop hearing the heartbeat and realise the monitor is gone. Solution: polling / election: another station on the ring is elected as the new monitor and takes over. "The show must go on."
Monitor malfunctioning (it works, but behaves strangely, e.g. hacked by a third party): the only option left is human intervention: someone must inspect and fix it.
➕ Standard names The standard name is AMP = Active Monitor Present frame (the lecture expands it as "Alive Monitor Packet"; same idea), sent about every 7 seconds. Standby monitors that miss it start the Claim Token process, an election in which the station with the highest MAC address wins and becomes the new active monitor. A station that detects a hard fault (e.g. a broken cable) sends Beacon frames to locate the fault.

18.13Token Ring Frame Format

🎓 From the lecture The numbers in circles are bytes, not bits: SD 1 · AC 1 · FC 1 · DA 6 · SA 6 · Data · CRC 4 · ED 1 · FS 1. Leaving out the data, that is 21 bytes. The token is just SD + AC + ED = 3 bytes.
SD is like Ethernet's SFD: it alerts every station to synchronise its clock because a frame is starting. The ED is new and important: Ethernet found the end of a frame with a length field, Token Ring uses an end delimiter (chapter 17).

18.14Start Delimiter (J and K Symbols)

🎓 From the lecture SD = J K 0 J K 0 0 0 ("thoda alag gaana ban raha hai"). In DME, a normal 0 and 1 each have a transition in the middle of the bit (high goes to low or low to high). J stays high for the entire bit and K stays low for the entire bit: no transition at all. So J and K can never be confused with data; they mark the start of a frame and alert every station.
➕ Exam wording J and K are code violations: patterns that break the Differential Manchester rule (a mid-bit transition in every bit), so they can never appear in data. This is the "physical-layer coding violation" framing method from chapter 17. (Strictly, J has no transition at the start of the bit and K does, relative to the previous bit; the lecture's "J high, K low" picture is a simplification.)

18.15Access Control Field: Priority, Token and Monitor Bits

AC (1 byte) = P P P | T | M | R R R priority token monitor reservation
🎓 From the lecture • PPP: priority bits. 3 bits give 000 to 111, so priorities 0 to 7. Generally, the bigger the number, the higher the priority: a station given 7 gets the best chance to transmit; 0, 1 or 2 means low priority.
• T: token bit. The AC byte is in both the token and the frame, so T says which one this is. The lecture says T = 1 means "this is the token"; for anything else (data or control frame) T = 0.
• M: monitor bit. The orphan-packet hero (18.6): 0 when sent, set to 1 by the monitor on the first pass, and the frame is discarded if it comes round again with M = 1.
• RRR: reservation bits, explained next.
⚠️ Exam trap In the IEEE 802.5 standard the T bit works the other way: T = 0 means token and T = 1 means frame. Some textbooks follow the lecture's convention. If the question names IEEE 802.5, use T = 0 for the token.

18.16Reservation Bits and Priority Scheduling

🎓 From the lecture Stations S1, S2, S3 have priorities 1, 2, 3 (S3 highest). S1 holds the token, transmits a frame, and writes its own priority 1 in the reservation field: "I want the token again next time."
The frame reaches S2 (each station holds and releases it). S2 sees "reservation 1? My priority is higher and I want the token next" and overwrites it with 2.
At S3: "S2 wants it, but my priority is higher still" → it changes 2 to 3.
With delayed token reinsertion, the frame comes back to S1. S1 sees that a higher-priority station (3) has reserved the token, so it has no option: it releases the token with that priority, and it goes to S3, which transmits next.
➕ The full rule A station may grab a token only if its frame's priority ≥ the token's priority (PPP). When the sender releases the token it sets PPP to the reserved value, so lower-priority stations must let it pass. The station that raised the priority must later lower it back (it is called the stacking station), so low-priority stations are not starved for ever.

18.17Frame Control and Address Fields

🎓 From the lecture FC (Frame Control, 1 byte) tells which kind of frame this is (when it is not a token). Its first two bits: 00 → a proper data frame; 11 → a control frame carrying control information, e.g. the AMP heartbeat or a beacon. The remaining 6 bits say which type of control frame it is; in a data frame they are all zeros.
DA / SA (6 bytes each): 48-bit MAC addresses of the destination and the source, exactly as in chapter 16. CRC (4 bytes): error detection, as in chapter 14.
⚠️ Exam trap The IEEE 802.5 standard codes the first two FC bits (the FF "frame type" bits) as 00 = MAC frame (control/management, e.g. AMP, beacon, claim token) and 01 = LLC frame (user data). The lecture's "00 = data, 11 = control" is a simplified teaching version. If a question quotes the standard, go with 00 = MAC/control, 01 = LLC/data.

18.18End Delimiter and Frame Status Fields

ED (1 byte) = J K 1 J K 1 | I | E FS (1 byte) = A C r r | A C r r intermediate error duplicated (not covered by CRC)
🎓 From the lecture ED uses J and K like the SD, but with 1s instead of 0s: J K 1 J K 1, followed by two new bits:
• I (intermediate): I = 1 means "I am an intermediate frame; more frames of this data are coming". I = 0 means "I am the last one, no more data".
• E (error): as explained in 18.8.
FS (Frame Status) carries the A and C bits (available, copied). Why do they appear twice? Because FS comes after the CRC, so the CRC does not protect it. If A and C were 1 1 and noise turned them into 0 0, the sender would get the wrong message. So the bits are repeated (100% redundancy): if the two copies don't match, the sender knows they were corrupted.
⚠️ Exam trap The E bit lives in the ED, not in the FS. The FS holds only A and C (twice) plus reserved bits. And A/C/E are set by the stations on the way, which is exactly why they must sit outside the CRC: changing them would otherwise break the checksum.

18.19Token Ring Data Field Size

🎓 From the lecture Data = 0 to max: much more flexible than Ethernet, which needed at least 46 bytes (64 − 18). Token Ring has no minimum; you can send even 2–3 bytes.
And the maximum? You may transmit only while you hold the token, so the maximum is however much you can send within the Token Holding Time. Because there is no minimum size, Token Ring suits interactive applications, exactly where Ethernet was weak (chapter 15.2).
Max data from THT
Max bits ≈ THT × data rate 4 Mbps × 10 ms = 40 000 bits = 5000 bytes (standard max ≈ 4500 bytes at 4 Mbps) 16 Mbps × 10 ms = 160 000 bits = 20 000 bytes (standard max ≈ 17 800 bytes at 16 Mbps)

18.20Efficiency Formulas, Ethernet vs Token Ring & Solved Numericals ADDED

Deriving the efficiency (N stations, each sends one frame per token turn)
a = RL / Tt Early (ETR): one cycle = N·Tt + RL η = N·Tt / (N·Tt + RL) = 1 / (1 + a/N) Delayed (DTR): each station waits for its own frame → N·(Tt + RL), plus the token's trip round the ring = RL η = N·Tt / (N·(Tt + RL) + RL) = 1 / (1 + a(N + 1)/N) Throughput = η × data rate
Solved numericals Q1. A 2 km ring, v = 2×10⁸ m/s, 20 stations each adding a 1-bit delay, 4 Mbps. Ring latency?
d/v = 2000 / 2×10⁸ = 10 µs; b = 1/4×10⁶ = 0.25 µs; N·b = 5 µs → RL = 15 µs (= 60 bits on the ring).

Q2. Same ring, 1000-bit frames. Efficiency with DTR and ETR?
Tt = 1000 / 4×10⁶ = 250 µs; a = 15/250 = 0.06.
DTR: η = 1/(1 + 0.06 × 21/20) = 1/1.063 ≈ 94.1%. ETR: η = 1/(1 + 0.06/20) ≈ 99.7%.

Q3. Same ring with THT = 10 ms. Minimum and maximum token return time?
Min = RL = 15 µs. Max = 20 × 10 ms + 15 µs = 200.015 ms. The monitor regenerates the token only after this.

Q4. A frame comes back with A = 1, C = 0, E = 0. What happened? The destination exists but its buffer was full (busy): retry later.

Q5. Number of priority levels in Token Ring? 3 bits → 8 levels (0–7).

Q6. Token size? 3 bytes (SD, AC, ED). Frame overhead? 21 bytes.
🎯 IBPS exam alert Common one-liners: Token Ring = IEEE 802.5; Token Bus = 802.4; FDDI uses a dual ring (fault tolerant) at 100 Mbps; Token Ring is deterministic / collision-free; its encoding is Differential Manchester; a MAU makes it a physical star but logical ring.

⚡ Rapid Revision — Chapter 18

  • 802.5: ring, unidirectional, token passing, no collisions, ACK via A/C bits, Differential Manchester, 4 / 16 Mbps.
  • Hold the token, then transmit; no token = no transmission. The sender removes its own frame.
  • RL = d/v + N·b. THT = 10 ms (default max).
  • Delayed TR: release the token after the frame returns; time Tt + RL; one frame on the ring; less efficient. Early TR: release immediately; time Tt; many frames, token always last; more efficient. η: DTR 1/(1 + a(N+1)/N), ETR 1/(1 + a/N).
  • Monitor station (class monitor): orphan packet (sender down) → M bit 0 → 1, discard on the second pass. Stray packet (unrecognisable) → CRC mismatch → discard.
  • A C E: 000 down/initial, 100 busy, 101 error, 110 copied ✔.
  • Captured token → THT limit. Lost token → TRT min = RL, max = N·THT + RL; monitor regenerates after the max. Corrupted token → discard, wait max TRT, regenerate.
  • Monitor heartbeat = AMP; monitor down → election (claim token); malfunction → human intervention.
  • Frame: SD 1 · AC 1 · FC 1 · DA 6 · SA 6 · Data 0–max · CRC 4 · ED 1 · FS 1 → 21 bytes overhead. Token = SD AC ED = 3 bytes.
  • SD = JK0JK000, ED = JK1JK1 I E; J/K = no mid-bit transition (code violation).
  • AC = PPP T M RRR: 8 priorities; reservation bits can only be raised; highest reservation gets the token next.
  • FC first 2 bits: data vs control (lecture 00/11; standard 01 LLC / 00 MAC). FS = A C r r A C r r, duplicated because it is outside the CRC.
  • Data 0 to max (limited by THT) → good for interactive apps.
