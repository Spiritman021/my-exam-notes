TCP (Transmission Control Protocol)

TCP turns IP's best-effort packet delivery into a reliable, ordered byte stream between two processes. It does this with three ideas: it numbers every byte (sequence numbers), the receiver says which byte it expects next (acknowledgment numbers), and both sides agree on starting numbers and buffer sizes before any data flows (the three-way handshake). Most exam numericals come from those numbers: data length, ACK number, wrap-around time.

29.1TCP Header Format

🎓 From the lecture TCP is connection-oriented, delivers in order and is reliable; to know its whole kundli (horoscope), just open its header. Like IPv4, it has 6 horizontal slots: 5 mandatory (each 32 bits = 4 bytes, bit positions 0–31) and the 6th optional (0–40 bytes). So the header is minimum 20 bytes, maximum 60 bytes. Fields: source port and destination port (16 bits each, the end-to-end idea), sequence number, acknowledgment number, header length, flags, window size, checksum, urgent pointer (with the URG flag), options, then the data.

29.2Segments and Source/Destination Port Fields

🎓 From the lecture The general word is "packet", but at the transport layer the unit is a segment; at the network layer it is a datagram; in the DLL a frame. A segment = TCP header + data/payload from the layer above.
Example: the receiving host runs processes P1–P4. A segment's header carries source port X (the sender's process) and destination port 80 (P2's port on the receiver), so on arrival it is delivered to P2: end-to-end delivery.

29.3Sequence Number: TCP as a Byte Stream Protocol

🎓 From the lecture The most important idea: TCP is a byte-stream protocol, while IP is a packet-stream protocol. Byte stream means every byte gets a number. In a segment, the first data byte is numbered 201, the next 202, 203 … 209: numbered in the order the bytes are arranged. The 32-bit sequence number field in the header stores the number of the first data byte of that segment.

29.4Acknowledgment Number

🎓 From the lecture Also a 32-bit field. The sender sends a segment with sequence number 201; the receiver opens it and finds the last data byte is 209. Which byte does it expect next? 210. That is what the acknowledgment number says: "the next byte I expect from you". The receiver sends ACK = 210; the sender's next segment then starts at byte 210, and 210 goes in its sequence number field.
➕ Cumulative ACK TCP's acknowledgment is cumulative: ACK = 210 means "I have received everything up to 209", not just the last segment. Ack number = last byte received in order + 1.

29.5Why the Initial Sequence Number Is Random

🎓 From the lecture "Sequence numbers should not start from zero" is not said lightly. Scenario: a sender (IPS, port X) and receiver (IPR, port Y) exchange 500-byte segments numbered 0, 500, 1000 … The segment numbered 500 gets stuck and delayed in the network, so long that the connection is terminated. A new connection is opened between the same IPs and ports, and again starts from 0. When the old segment 500 finally arrives, the receiver thinks "yes, I was expecting 500 after 0, from this very port" and accepts it, although it belongs to the previous connection and its data may be totally different. To avoid this conflict, each connection starts from a random number (10, 20, anything).
➕ Also a security reason A predictable ISN (Initial Sequence Number) lets an attacker forge segments that the receiver will accept (TCP sequence prediction / session hijacking). Modern stacks therefore pick the ISN pseudo-randomly (RFC 6528).

29.6Maximum Segment Size (MSS)

🎓 From the lecture Go back through the layers. An Ethernet frame's data field is at most 1500 bytes (whole frame 1518, ch 15). Inside it is the IP datagram: minimum IP header 20 bytes, leaving 1480. Inside that is the TCP segment: minimum TCP header 20 bytes, leaving 1460 bytes. That is the MSS (Maximum Segment Size): the largest amount of data one TCP segment carries. The 1500 is the datagram's whole transmission unit, the MTU.
⚠️ Exam trap MSS counts data only (no TCP header). 1500 − 20 = 1480 (the transcript slips to "480"), − 20 = 1460. With IPv6 (40-byte header) the MSS on Ethernet is 1440. MSS is announced in the SYN segments as a TCP option.

29.7Header Length Field and Scaling Factor

🎓 From the lecture Same as IPv4: 4 bits → values 0–15, but the header is 20–60 bytes. Scaling factor = 60 ÷ 15 = 4. Valid values 5–15: 5 × 4 = 20 bytes, 15 × 4 = 60 bytes.
TCP header length (bytes) = HLEN × 4 HLEN 5 … 15 → 20 … 60 bytes

29.8Numerical: Finding the Acknowledgment Number

🎓 From the lecture How does the receiver compute the ACK number? Peel the layers. The IP datagram's total length = IP header + X. Step 1: X = total length − IP header length. X is the TCP segment. Step 2: Y = X − TCP header length; Y = the number of data bytes. Step 3: the sequence number field gives the first byte's number, e.g. 100. Last byte = 100 + Y − 1; with Y = 6, last byte = 105. ACK = last byte + 1 = 106: "send 106 next". This also shows encapsulation: the TCP segment sits inside the IP datagram.
Worked example
IP Total Length = 46, IP HLEN = 5 (20 B), TCP HLEN = 5 (20 B), seq = 100 X = 46 − 20 = 26 Y = 26 − 20 = 6 data bytes bytes 100 … 105 → ACK = 106

29.9Sequence Number Wrap Around

🎓 From the lecture The sequence field is 32 bits → 2³² numbers = 4 × 2³⁰ = "4 G" sequence numbers. One byte consumes one number, so up to 4 GB of data there's no problem. With 4 GB + 1 byte, all numbers are used up: where does the extra byte get its number? Go round again: after the last number, start reusing from the beginning (or, with a random start x, go up to 2³² − 1 and wrap around to 0 … x). This reuse is wrap around.
Wrap-around time = the time taken to reuse the same sequence number again: from first using number 0 until the stream comes all the way round and uses 0 again.
People often think more bandwidth means more wrap-around time. No: wrap-around time ∝ 1 / bandwidth. Higher bandwidth uses up sequence numbers faster, so they repeat sooner.

29.10Numerical: Wrap Around Time

🎓 From the lecture Bandwidth 1 MBps = 10⁶ bytes per second → 10⁶ sequence numbers consumed per second. One number takes 1/10⁶ s. All 2³² numbers take 2³² / 10⁶ s. Three questions answered: numbers per second, time per number, and time for the whole space.
wrap-around time = 2^(sequence bits) / (bandwidth in BYTES per second) 1 MBps : 2³² / 10⁶ ≈ 4295 s ≈ 71.6 minutes 1 GBps : 2³² / 10⁹ ≈ 4.29 s
⚠️ Exam trap Divide by bandwidth in bytes/s, because sequence numbers count bytes. If given 10 Mbps (bits), first convert: 10 × 10⁶ / 8 = 1.25 × 10⁶ B/s → 2³² / 1.25×10⁶ ≈ 3436 s.

29.11Packet Lifetime vs Wrap Around Time

🎓 From the lecture Lifetime of a packet = t2 − t1, from leaving the sender to arriving at the receiver: at most 180 seconds (3 minutes). Suppose a segment is sent with sequence number 100; later, after the wrap-around time, number 100 is used again for new data.
The rule: wrap-around time must be greater than lifetime. If wrap-around were shorter, sequence number 100 could be reused while the old segment with 100 is still alive in the network; two segments with the same number could reach the receiver: a conflict.
Wrap-around time > Lifetime (MSL) otherwise old and new segments can carry the same sequence number

29.12Numerical: Sequence Number Bits for High Bandwidth

🎓 From the lecture Raise the bandwidth to 1 GBps: wrap-around = 2³² / 10⁹ ≈ 4.29 s, far below the 180 s lifetime. The feared case! Reduce bandwidth? "Are you mad? People go crazy for bandwidth." Instead add sequence-number bits.
In 180 s at 10⁹ B/s, 10⁹ × 180 numbers are consumed. We need at least that many: bits = ⌈log₂(bandwidth × lifetime)⌉ = ⌈log₂(1.8 × 10¹¹)⌉ = ⌈37.39⌉ = 38 bits. The header has only 32, so take the extra 6 bits from the options field: 32 + 6 = 38. Mission accomplished.
required sequence bits = ⌈ log₂ (bandwidth (B/s) × lifetime (s)) ⌉ 1 GBps, 180 s → ⌈log₂(1.8 × 10¹¹)⌉ = 38 bits
➕ How real TCP does it Real TCP does not lengthen the sequence field. It uses the Timestamps option (RFC 7323): every segment carries a timestamp, and PAWS (Protection Against Wrapped Sequences) rejects old segments whose timestamp is too old, so the timestamp effectively extends the numbering, in the options field as the lecture suggests. The same RFC defines the Window Scale option for windows above 65 535 bytes.

29.13TCP Connection Establishment: Three-Way Handshake

🎓 From the lecture Three phases: connection establishment, data transfer, connection termination. Communication will be full duplex, but someone must start: the client approaches the server with a request. Establishment takes three segments, hence the three-way handshake.

29.14SYN Segment: Sequence Number, MSS and Window Size

🎓 From the lecture ① SYN (client → server): starts with sequence number 500 (random) and SYN = 1. SYN (synchronise) is set only while establishing a connection: the server doesn't know which random number the client chose, so both sides synchronise sequence numbers. It also sends its MSS ("don't send bigger than this or you'll be broken up") and its window size, i.e. its buffer: e.g. window 14 600 bytes with MSS 1460 → 14 600 / 1460 = 10 segments at a time. "Don't send me more than I can receive."
② SYN+ACK (server → client): "I start from random 1000; please sync." SYN = 1 again, its own MSS (500) and buffer (1000), ACK flag = 1 and ack number = 501: "you used 500; your next segment's first byte should be 501". Note the ACK flag (field is valid) differs from the ACK number (32-bit field).
③ ACK (client → server): the client respects the reply: sequence 501, ACK = 1, ack number 1001 ("send me byte 1001 next"). It carries no data: a pure acknowledgement.

29.15Sequence Number Consumption (SYN/FIN vs Pure ACK)

🎓 From the lecture After SYN with 500, the client used 501 next, so 500 was consumed by the SYN. But in step ③ (a pure ACK) the client used 501, and right after the handshake it uses 501 again for data. Illegal? No: a pure ACK does not consume a sequence number, so it can be reused immediately.

29.16TCP Data Transfer and Piggybacking

🎓 From the lecture The client sends bytes 501–600 (first byte 501, last 600): seq 501, ACK flag 1, ack 1001. Data and acknowledgement travel together: piggybacked acknowledgement.
The server sends data 1001–1100: seq 1001 (exactly what the client asked for), ACK = 1, ack 601 (it decoded the last byte as 600, so it wants 601).
The client has nothing more to send, so it sends a pure ACK: seq 601, ack 1101.
Pattern: the ack number one side sends becomes the other side's next sequence number, both ways.

29.17TCP Connection Termination (FIN)

🎓 From the lecture The client is done: it no longer needs the buffers and link the server reserved for it. It sends FIN = 1 (terminate from my end) with seq 601 (reusable, since the pure ACK didn't consume it), ACK = 1, ack 1101.
After its FIN, the client may send only pure ACKs, no more data. The server is still connected and may still send data with piggybacked ACKs (this is a half-close).
When the server is also done, it sends FIN+ACK: seq 1101, ack 602 (the client's FIN consumed 601). The client sends the final ACK: seq 602, ack 1102. The connection is fully closed.
➕ Three-way vs four-way close In the general case termination takes four segments: FIN →, ← ACK, (the server may keep sending data), ← FIN, ACK →. When the server has nothing left to send it combines its ACK and FIN into one segment, giving the three-segment close shown in the lecture. The side that closes first waits in TIME-WAIT for 2 × MSL before forgetting the connection, so that a lost final ACK can be resent and old duplicates die out.

🎓 From the lecture The ACK flag says "the value in the acknowledgment number field is valid", so after the first segment it is set in practically every segment, during transfer and termination too.

29.19URG Flag and Urgent Pointer

🎓 From the lecture The sender has messages m1, m2, m3 queued, but m3 is very important and must reach first. Set its URG flag. But routers work only up to the network layer; they can't read transport-layer flags. So the lecture translates it into the network layer: give that packet IP precedence 7 (the highest, in TOS, ch 22); routers then forward m3 ahead of m1 and m2.
The urgent pointer works only when URG = 1. It tells how many bytes, counted from the first data byte, are urgent: last urgent byte = sequence number + urgent pointer. Everything from the first byte up to that point is urgent data.
Example seq = 100, URG = 1, urgent pointer = 10 → urgent data = bytes 100 … 110 (last urgent byte = 100 + 10, Forouzan's convention).
⚠️ Exam trap In the TCP standard, URG does not change how routers forward the segment (no IP priority is set automatically); the "precedence 7" mapping is the lecture's way of explaining. What URG really does is tell the receiving TCP to deliver the urgent bytes to the application out of band, ahead of the queued normal data (e.g. Ctrl+C in Telnet). Don't confuse it with PSH, which asks the receiver to pass buffered data to the application immediately.

29.20RST Flag (Connection Reset)

🎓 From the lecture RST = 1 resets the connection when something has gone wrong.
1. Receiver crashed and rebooted: it has forgotten the old connection (the synchronised numbers, all of it). Valid segments from the sender now look like a stranger's. It sends RST: "stop, I remember nothing; let's set up a new connection first".
2. Unexpected packets: host A keeps sending segments host B never asked for ("I didn't order this, I won't pay for it!"). B won't spend resources on them and sends RST.
3. Wrong sequence number: the receiver expects 100 and gets 300: "I called Suresh, and Ramesh turned up!" RST.
➕ Also A host replies with RST to a SYN aimed at a closed port (that is how port scanners detect closed ports). RST closes the connection immediately, without the FIN exchange and without waiting; any data in transit is discarded.

➕ Connection states (names to recognise) CLOSED → LISTEN (server) → SYN-SENT (client) / SYN-RECEIVED (server) → ESTABLISHED → FIN-WAIT-1 → FIN-WAIT-2 → TIME-WAIT → CLOSED (active closer); CLOSE-WAIT → LAST-ACK → CLOSED (passive closer). Attack to know: the SYN flood (many SYNs, never the final ACK, filling the server's half-open table); defence: SYN cookies.
Solved numericals Q1. TCP HLEN field = 8. Header size? Options? 8 × 4 = 32 bytes; options = 12 bytes.

Q2. A segment has seq 2000 and carries 500 data bytes. Its last byte number and the ACK the receiver sends? Last = 2499; ACK = 2500.

Q3. IP total length 1000, IP HLEN 5, TCP HLEN 8, seq 5000. ACK number? Data = 1000 − 20 − 32 = 948 → ACK = 5948.

Q4. Client SYN with seq 100, server SYN+ACK with seq 300. What are the ack numbers in step ② and ③? ② ack 101; ③ seq 101, ack 301.

Q5. Wrap-around time at 10 Mbps? 2³² / (10⁷/8) ≈ 3436 s.

Q6. Sequence bits needed for 10 Mbps with lifetime 180 s? ⌈log₂(1.25×10⁶ × 180)⌉ = ⌈log₂(2.25×10⁸)⌉ = 28 → 32 bits are enough.

Q7. Window 14 600 B, MSS 1460 B: how many full segments can be outstanding? 10.

Q8. Which flags consume a sequence number? SYN and FIN (and each data byte); a pure ACK does not.
🎯 IBPS exam alert Most asked: TCP header 20–60 bytes; sequence and ACK numbers 32 bits; window 16 bits; ACK = next byte expected; three-way handshake = SYN, SYN+ACK, ACK; SYN and FIN consume one number; MSS on Ethernet = 1460; TCP is full-duplex, connection-oriented, byte-stream.

⚡ Rapid Revision — Chapter 29

  • Header: 5 rows × 4 B = 20, + options ≤ 40 → 60. Ports 16+16, seq 32, ack 32, HLEN 4 (×4), flags 6, window 16, checksum 16, urgent pointer 16.
  • Byte stream: every byte numbered; seq field = first data byte. ACK = next byte expected (201–209 → ACK 210); cumulative.
  • Random ISN: an old delayed segment from a previous connection with the same IPs/ports must not be mistaken for new data.
  • MSS = 1500 − 20 − 20 = 1460 (data only).
  • ACK numerical: X = IP total − IP header; Y = X − TCP header; ACK = seq + Y.
  • Wrap-around: 2³² numbers; time = 2³² / bandwidth (B/s); ∝ 1/bandwidth. Must exceed lifetime (180 s). Bits needed = ⌈log₂(B × LT)⌉ (1 GBps → 38 bits; extra from options).
  • Handshake: SYN seq 500 (MSS, window) → SYN+ACK seq 1000 ack 501 → ACK seq 501 ack 1001.
  • SYN, FIN and each data byte consume a number; a pure ACK consumes none.
  • Data 501–600 (ack 1001, piggyback) ↔ 1001–1100 (ack 601) → pure ACK 601/1101. Close: FIN 601 → FIN+ACK 1101/602 → ACK 602/1102.
  • Flags: URG (+ urgent pointer), ACK, PSH, RST (crash, unexpected segments, wrong seq), SYN, FIN.
