Chapter 34

Application Layer

Every layer below exists to serve this one. The application layer holds the protocols that real programs speak: a browser uses DNS to find a server's address and HTTP(S) to fetch the page; a mail client uses SMTP to send and POP3/IMAP to collect; file tools use FTP or TFTP. For each protocol, exams ask four things: its port, whether it runs over TCP or UDP, whether it is stateful or stateless, and how it works step by step.

34.0The Top Layer

🎓 From the lecture The application layer is the last layer of this subject and of the OSI model. At the sender, the auspicious beginning (shubh aarambh) happens here: it is the first layer data passes through. At the receiver it is the final layer.

34.1Application Protocols: Transport Protocols and Port Numbers

🎓 From the lecture Many protocols run in this layer; the lecturer groups the exam-relevant ones by the transport protocol under them (TCP, UDP, or both, as for Echo) and lists their port numbers. FTP has separate lines (ports) for data and control: 20 and 21. Then Telnet, SMTP (very important), HTTP, POP3, DNS, TFTP, and RIP (the distance-vector routing protocol of ch 27). 34.2DNS: Components and Hierarchy

🎓 From the lecture DNS (Domain Name System): input = a domain name; output = its IP address. It works in two fashions: iterative and recursive.
Components: the DNS resolver (takes the host's domain name in the first step and returns the resolved IP address in the last), the root name server, the TLD (top-level domain) server, and the authoritative name server. Together they form a tree.
Flow: the browser asks for 5minutesengineering.com; the IP isn't known, so the resolver asks the root (every tree starts at the root). Root: "I don't know, but it ends in .com, so ask my child .com." The .com TLD server: "I don't have the IP either, but I know who does": the authoritative name server, which holds the authority: the full record of that domain, including its name-to-IP mapping. The question goes top-down; the answer (IP) comes bottom-up, back through the resolver to the host.

34.3DNS Iterative Resolution

🎓 From the lecture Step 1: the host gives the domain name to the resolver and asks for the IP; step 8: the resolver returns the answer. In between: the resolver doesn't know, so it asks the root (2). Root: "I don't have it, but I see .com, go to my child .com" (3). The resolver goes to the TLD (4): "Right place, but I don't have the IP directly; go to the authoritative name server, which holds that domain's data" (5). The resolver goes to the authoritative server (6), which searches its data, finds the IP and returns it (7). The resolver forwards it to the host (8). Each server only refers the resolver onward; the resolver itself makes every trip.

34.4DNS Recursive Resolution

🎓 From the lecture Steps 1 and 8 (host ↔ resolver) stay the same. In iterative mode the resolver had to keep running around: "go there", "not here, go there". In recursive mode the resolver relaxes ("chill karega"). It tells the root: "you don't have it? Fetch it for me (laake do)." Root asks its child .com; .com asks the authoritative server; the IP comes back up authoritative → TLD → root → resolver (step 7) → host. Recursive is best seen as the tree; iterative as the step diagram.

34.5HTTP: Stateless, Persistent vs Non-Persistent Connections

🎓 From the lecture Nothing new: you see http/https on every website. HTTP works on port 80. It is not reliable on its own, so it uses TCP for reliability.
Stateless: no information about the user or the session is saved on the server. (Stateful would save it; HTTP doesn't.)
It uses one port (80) for both data and commands/control: an in-band protocol.
Two versions differ in connections:
• HTTP 1.0 = non-persistent: one TCP connection per request–reply. After one exchange the connection is torn down; the next request needs a new connection. Slow, because time goes in making and breaking connections.
• HTTP 1.1 = persistent: the server leaves the connection open for one or more requests. It closes only when the client asks to close, or on a timeout.
HTTP has no built-in security.

34.6HTTPS

🎓 From the lecture Because HTTP has no security of its own, there is HTTPS: HTTP running over SSL, "HTTP Secure", which protects the crucial security properties of the data. You'll also often read that HTTP is "somewhat a combination of FTP and SMTP": it transfers files like FTP (but on one port, in-band), and its messages look like mail messages (headers + body) like SMTP's.
⚠️ Exam trap HTTPS = HTTP over SSL/TLS (today TLS 1.2/1.3), on port 443. It provides confidentiality (encryption), integrity and server authentication (certificates). It does not provide availability (the lecture lists the whole CIA triad); availability is about the service staying up, which encryption doesn't give.

34.7FTP (File Transfer Protocol)

🎓 From the lecture As the name says, FTP transfers files. It is not in-band: data and control have separate ports (20 and 21), unlike HTTP, which uses one port for everything. Because they are separate, the data connection is non-persistent while the control connection is persistent.
FTP is stateful: information about the session is stored (who is logged in, the current directory). HTTP says "not in my case": HTTP stays stateless.
➕ FTP extras Transfer modes: ASCII (text) and binary (images, programs). Connection modes: active (server opens the data connection from port 20 to the client) and passive (client opens it to a server port; works through firewalls/NAT). Plain FTP sends passwords in clear text; secure versions are FTPS (FTP over TLS) and SFTP (file transfer over SSH, port 22). Anonymous FTP allows public downloads.

34.8TFTP (Trivial File Transfer Protocol)

🎓 From the lecture A variant that is "trivial" by nature: very simple operations, only read and write. It runs over UDP, port 69. If the client needs security or long-distance transfer of files, don't use TFTP; it isn't built for that.

34.9SMTP and Mail Transfer (MTA/MAA)

🎓 From the lecture SMTP (Simple Mail Transfer Protocol) supports an asynchronous nature. Unlike a phone call, where the other person must be on the line, mail can be sent while the receiver is offline; it waits on the server, and the receiver logs in later to read it.
SMTP pushes mail, with the help of an MTA (Message/Mail Transfer Agent). Client 1's MTA client takes the mail from the client machine and pushes it to its mail server; the two clients may use different mail providers (e.g. Gmail and another), so the mail server's MTA pushes it on to the receiver's mail server. Both steps (① and ②) are handled by SMTP. The MTA has a client side and a server side (inside the mail server). After that the pull process begins, to bring the mail from the server to client 2.
➕ SMTP details Port 25 (server to server); 587 for client submission. Classic commands: HELO/EHLO, MAIL FROM, RCPT TO, DATA, QUIT. SMTP itself handles only 7-bit ASCII text; that's why MIME (34.11) exists. Software roles: UA (user agent: Outlook, Thunderbird), MTA (transfer), MAA (access).

34.10POP3 (Post Office Protocol)

🎓 From the lecture Who does the pull? POP (Post Office Protocol). It pulls the mails from the server and delivers them to the client, helped by the MAA (Message Access Agent). So: MTA = transfer = push; MAA = access = pull into client 2. The most popular version is POP3; it runs on TCP, port 110.

34.11MIME (Multipurpose Internet Mail Extensions)

🎓 From the lecture The last topic of the one-shot. We don't send only text from client 1 to client 2; we also send audio, video, images: non-text data. MIME is "multipurpose": not just the single purpose of text. At the sender, non-text data is converted into text form; at the receiver it is converted back to non-text, so the receiver sees the audio, video or image as a whole without any problem.
➕ How MIME does it MIME adds headers: MIME-Version, Content-Type (e.g. image/jpeg, text/html, multipart/mixed for attachments), and Content-Transfer-Encoding (e.g. base64, which turns every 3 bytes of binary into 4 printable ASCII characters, about 33% larger). The same Content-Type labels are used by HTTP. S/MIME adds signing and encryption to mail.

➕ HTTP essentials Methods: GET (fetch), POST (submit), PUT (replace), DELETE, HEAD (headers only), PATCH, OPTIONS. Status codes: 1xx informational, 2xx success (200 OK), 3xx redirect (301 moved permanently, 304 not modified), 4xx client error (400 bad request, 403 forbidden, 404 not found), 5xx server error (500 internal error, 503 unavailable). Cookies add state on top of stateless HTTP (login sessions, carts). Versions: HTTP/1.0 non-persistent, HTTP/1.1 persistent + pipelining, HTTP/2 multiplexed binary frames, HTTP/3 over QUIC (UDP). URL = protocol://host:port/path.
Solved numericals Q1. A web page has 1 base HTML file + 10 images, all small (ignore transmission time). How many RTTs to fetch everything?
• Non-persistent, one at a time: each object needs 2 RTT (handshake + request) → 11 × 2 = 22 RTT.
• Persistent, no pipelining: 1 RTT handshake + 1 RTT per object → 1 + 11 = 12 RTT.
• Persistent with pipelining: handshake 1 + base page 1 + all 10 images together 1 = 3 RTT.
• Non-persistent with 5 parallel connections: base page 2 RTT + two batches of 5 images × 2 RTT = 6 RTT.

Q2. In iterative DNS resolution with root → TLD → authoritative and no caching, how many queries does the resolver send? 3 (one to each server).

Q3. Which protocols are stateless: HTTP, FTP? HTTP stateless, FTP stateful.

Q4. Which mail protocol is push, which pull? SMTP push; POP3/IMAP pull.

Q5. Which DNS record gives the mail server of a domain? MX. Reverse lookup? PTR.

Q6. In-band or out-of-band: HTTP? FTP? HTTP in-band (one port); FTP out-of-band (two ports).
🎯 IBPS exam alert High-frequency facts: DNS 53/UDP · HTTP 80 · HTTPS 443 · FTP 20/21 · SMTP 25 · POP3 110 · IMAP 143 · Telnet 23 · SSH 22 · TFTP 69/UDP · DHCP 67/68/UDP · SNMP 161/UDP. HTTP stateless; FTP stateful and out-of-band; SMTP push, POP3 pull; MIME for non-text mail; 404 = not found.

⚡ Rapid Revision — Chapter 34

  • Application layer = OSI layer 7: first layer at the sender (shubh aarambh), last at the receiver.
  • Know each protocol's port + transport (Echo 7 both; FTP 20/21, Telnet 23, SMTP 25, HTTP 80, POP3 110 on TCP; DNS 53, TFTP 69, RIP 520 on UDP).
  • DNS: domain name → IP. Resolver, root, TLD, authoritative (holds the mapping). Question top-down, answer bottom-up.
  • Iterative: resolver runs to each server (referrals; 8 steps). Recursive: resolver "chills", root says "laake do" down the chain.
  • HTTP 80, over TCP, stateless, in-band. 1.0 = non-persistent (one TCP connection per request, slow); 1.1 = persistent (open until client closes / timeout). No security → HTTPS = HTTP over SSL/TLS, 443.
  • FTP 20 data (non-persistent) / 21 control (persistent): out-of-band, stateful. TFTP: UDP 69, only read/write, no security.
  • SMTP 25: asynchronous, push via MTA (client → server → server). POP3 110: pull via MAA. IMAP keeps mail on the server.
  • MIME: non-text (audio/video/images) → text for mail, and back (base64, Content-Type).
