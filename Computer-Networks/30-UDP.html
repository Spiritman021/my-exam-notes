Chapter 30

User Datagram Protocol (UDP)

Everything TCP does to be reliable (handshake, numbering every byte, acknowledging, retransmitting, flow and congestion control) costs time. UDP skips all of it. It adds just enough to IP to reach the right process (port numbers) and optionally detect corruption (a checksum). If a datagram is lost, duplicated or arrives out of order, UDP does nothing; the application deals with it, or doesn't care. That makes UDP ideal when speed matters more than perfection, or when the exchange is a single short question and answer.

30.0What UDP Is

🎓 From the lecture UDP = User Datagram Protocol. It is connectionless: no need to set up a connection first. None of TCP's phases (establish with the three-way handshake → transfer → terminate) are required. Naturally it is unreliable compared with TCP, since all those mechanisms are missing.

30.1UDP Use Cases: Simple Queries, Broadcast, Gaming and Multimedia

🎓 From the lecture The exam-hall pen. A tense Computer Networks exam; one student's pen is running out. He asks the neighbour "pen hai?" The expected answer is simply yes or no: no time to waste. That is UDP.
Now do it the TCP way: first build the relationship, establish the connection: "What's your name? Which class? Which village? Oh, I'm from nearby too! What does your father do? All well at home?" Request, response, acknowledgement, connection made. Then: "Pen hai?" "No, I don't have one." "You wasted all my time for that?!" UDP needs none of these formalities.
Broadcast. To broadcast data to every host, should a station first set up a connection with each one, then broadcast, then terminate each connection? TCP would be very expensive here. UDP: no connection, just broadcast, done.
Gaming and multimedia. Where speed is the requirement ("quick, yes or no, I have 5 minutes left to write an answer"), UDP is used.
➕ Why games and video prefer UDP In live voice, video or games, a late packet is useless: retransmitting a lost video frame would only freeze the picture while waiting for it. Applications would rather skip it and carry on. TCP's in-order delivery causes head-of-line blocking: one lost segment holds up everything behind it.

30.2UDP Port Delivery and Header Format

🎓 From the lecture Network layer below, application layer above; at the transport layer both TCP and UDP live. A datagram arrives for destination port X; the application layer has processes on ports X, Y, Z. UDP simply hands the data to process X and its story ends there: no SYN, no FIN, no acknowledgement, no sequence numbers, none of the TCP header machinery.
The header holds only:
  • Source port: 16 bits (which process sent it)
  • Destination port: 16 bits
  • Length: 16 bits, the length of header + data (not just the header)
  • Checksum: 16 bits, optional. Not using it? Put all 16 zeros. Using it? Compute it over the data, the UDP header and the pseudo IP header.
Total header = 2 + 2 + 2 + 2 = 8 bytes.

➕ "Message-oriented" explained UDP preserves message boundaries: each send() of 100 bytes arrives as one 100-byte datagram (or not at all). TCP is a byte stream: two sends of 100 bytes may arrive as one read of 200 bytes, or 150 + 50; the application must find its own boundaries.

30.4Checksum & Pseudo-header, Applications, Solved Questions ADDED

Pseudo-header: not sent on the wire; it is added temporarily, only for computing the checksum: source IP, destination IP, a zero byte, protocol number (17), UDP length. Including the IP addresses lets the receiver detect a datagram that was delivered to the wrong host. TCP uses the same trick (with protocol 6).
⚠️ Exam traps
  • UDP checksum is optional in IPv4 (all-zeros = not used) but mandatory in IPv6 (IPv6 has no header checksum of its own).
  • The Length field counts header + data, so its minimum is 8 (empty datagram). Max data in one UDP datagram over IPv4 = 65 535 − 20 (IP) − 8 (UDP) = 65 507 bytes; to fit one Ethernet frame without fragmentation, ≤ 1472 bytes (1500 − 20 − 8).
  • UDP is "unreliable" but not careless: with the checksum on, damaged datagrams are discarded (silently, no retransmission).

Solved questions Q1. A UDP header in hex is CB84 000D 001C 001C. Find source port, destination port, total length, data length, and the direction.
Source = 0xCB84 = 52100; destination = 0x000D = 13; length = 0x001C = 28 bytes; data = 28 − 8 = 20 bytes. The destination is a well-known port (13 = daytime) and the source an ephemeral port, so it goes from client to server. (The last field, 0x001C, is the checksum.)

Q2. UDP header size? 8 bytes (fixed).

Q3. Which transport protocol suits a DNS query? UDP. A file download over HTTP? TCP.

Q4. Is the UDP checksum compulsory? No in IPv4, yes in IPv6.

Q5. UDP Length field = 100. Data bytes? 92.

Q6. Which protocol supports broadcast and multicast: TCP or UDP? UDP.
🎯 IBPS exam alert Typical MCQs: "UDP header size?" (8 bytes), "connectionless transport protocol?" (UDP), "DNS uses which transport?" (UDP, port 53), "which is faster, TCP or UDP?" (UDP), "UDP provides flow control?" (no).

⚡ Rapid Revision — Chapter 30

  • UDP = User Datagram Protocol: connectionless, unreliable, no ordering, fast; none of TCP's three phases.
  • "Pen hai?": quick yes/no, no getting-to-know-you handshake. Broadcast without connecting to everyone. Gaming and multimedia want speed.
  • UDP just hands data to the destination port's process: no SYN/FIN/ACK/sequence numbers.
  • Header = source port 16 + destination port 16 + length 16 (header + data) + checksum 16 (optional; zeros if unused) = 8 bytes, fixed.
  • Checksum covers the pseudo-header (src/dst IP, protocol 17, length) + header + data; mandatory in IPv6.
  • TCP vs UDP: oriented vs less, reliable vs not, ordered vs not, slow vs fast, checksum mandatory vs optional, 20–60 vs 8, byte stream vs message.
  • UDP apps: DNS 53, DHCP 67/68, TFTP 69, SNMP 161, NTP 123, RIP 520, VoIP, streaming, games.
