Chapter 4

Integrity Constraints and Keys

A database is only as good as the rules that keep bad data out. Integrity constraints are those rules: a mark must be a number in a sensible range, every student must have a roll number, and a sports enrolment cannot name a student who does not exist. Keys are the attributes that make the rules enforceable, because they identify each row uniquely and link tables together. This chapter covers both, ending with the super key, which the next chapters (functional dependency and normalization) use constantly.

4.1Domain, Entity, Referential and Key Integrity (CHECK Marks > 35)

🎓 From the lecture
  • Domain integrity: deals with the domain of an attribute (chapter 3): the type of data, which values are allowed, and their limits. We can put a condition in a CHECK: say we want to store only students who passed, so marks must be greater than 35. That CHECK decides the domain: which values, of which type, within which limits.
  • Entity integrity: about the primary key. The primary key should never be NULL; this is an integral property of the primary key. There is no student without a roll number.
  • Referential integrity: about the foreign key. In the relationship tables of chapter 3, the columns took their values by referring to the primary key of another table; such a column is a foreign key, and its rules are referential integrity.
  • Key integrity: the unique identification idea that applies to all keys.

➕ Added for exam 
CREATE TABLE Student (
  RollNo INT PRIMARY KEY,                 -- entity + key integrity
  Name   VARCHAR(50) NOT NULL,            -- domain (no nulls)
  Marks  INT CHECK (Marks > 35)          -- domain integrity
);
Integrity constraints are part of the schema and are stored in the data dictionary. The DBMS checks them on every INSERT, UPDATE and DELETE and rejects any operation that would break them. Constraints that are more complex than these (e.g. "a customer may have at most 3 loans") are written as assertions or triggers.

4.2Candidate, Primary and Alternate Keys (Phone Face Unlock vs PIN)

🎓 From the lecture

Candidate key

In a Student table, RollNo, PhoneNo, GovernmentID, AdmissionNo, RegistrationNo are all characteristics of each student, and they have one more thing in common: each one alone can uniquely identify every record. These are the candidate keys. The table will also have Name, Age and City, but none of those is unique, so they are not candidate keys.

Primary key

Out of all the candidate keys, the database administrator selects one as the primary key: "this one attribute, RollNo, will be used for unique identification." It must never be NULL and never repeat. We pick the most eligible key for the scenario. Only one primary key is allowed per table.

Alternate keys

The candidate keys left over after choosing the primary key are the alternate keys.

Example: unlocking a phone

The phone opens only when your face is shown. There are many faces in the world, but the key to your phone's lock is your face. A phone can also be unlocked by fingerprint, pattern or PIN; all of these are candidate keys. The best one in the current scenario, easy and always unique, never ambiguous, is face unlock: the primary key. Fingerprint, pattern and PIN are the alternate keys.
➕ Added for exam
  • Formally, a candidate key is a minimal super key: it identifies tuples uniquely, and no proper subset of it does. A candidate key can be composite (more than one attribute), like (RollNo, SID) in chapter 3.
  • A table can have many candidate keys but only one primary key.
  • Attributes that are part of any candidate key are prime attributes; all others are non-prime. This distinction drives 2NF and 3NF (chapter 8).
  • UNIQUE key vs PRIMARY KEY: both reject duplicates, but a UNIQUE column may hold NULL and a table may have several UNIQUE constraints; a primary key never allows NULL and there is only one. In most DBMSs the primary key also creates a clustered index by default.
⚠️ Exam trap "A table can have more than one primary key" is false. "A primary key can consist of more than one column" is true (composite primary key). Don't confuse "one primary key" with "one column".

4.3Foreign Key (Student and Sports Tables)

🎓 From the lecture Two tables (always write the table name when you draw one, or you get confused):
  • Student(RollNo, Name) with primary key RollNo. The school has 4 students: roll numbers 1 to 4.
  • Sports(SportsID, SportsName, RollNo): cricket, football, hockey, kho-kho and so on, each with an ID, primary key SportsID. It also contains RollNo.

The scenario

Sports is a school facility, so only students who paid fees and took admission in this school should use it; students from other schools should not. The sports teacher sits with the school's sheet of roll numbers. Every student who comes to enrol first says their roll number, and the teacher checks it against the school records:
  • Roll 1: in the records → enrolled. Roll 2 → enrolled in 102. Roll 3 → enrolled in 103.
  • Roll 5: the teacher looks in the school records; nobody was given roll number 5. That student is not in the Student table, so no entry is allowed.
That is the referential-integrity constraint. Every time an entry with a RollNo is added to Sports, it refers to the Student table, where RollNo is the primary key. Written formally: Sports.RollNo references Student.RollNo.
➕ Added for exam 
CREATE TABLE Sports (
  SportsID   INT PRIMARY KEY,
  SportsName VARCHAR(30),
  RollNo     INT,
  FOREIGN KEY (RollNo) REFERENCES Student(RollNo)
);
  • The table holding the foreign key is the referencing (child) table; the table it points to is the referenced (parent / master) table.
  • A foreign key can be NULL (unless declared NOT NULL) and can repeat (many sports rows for one student).
  • A foreign key must reference a primary key or UNIQUE column, with the same data type.
  • A self-referencing foreign key points to its own table: Employee.ManagerID references Employee.EmpID.
  • A table can have many foreign keys.

4.4Insert, Delete and Update on Referenced vs Referencing Table (Taking a TC)

🎓 From the lecture Student is the table being referred to; Sports is the table that refers. Do insert, delete and update on each and see the impact on the other.

Changes in the referenced table (Student)

  • Insert (5, E) into Student: no impact on Sports at all.
  • Delete roll 2 from Student (the student took a TC and left the school): this does affect Sports. The Sports row with roll 2 now refers to nothing, so the constraint is violated. You can cascade the delete: propagate it from Student to Sports and delete that row too, so no inconsistency remains.
  • Update roll 5 to roll 6 in Student (the student didn't like 5 and 6 was vacant): if Sports has a row with roll 5, it now refers to a value that no longer exists. You must update it to 6 in Sports too; only then is the constraint satisfied in both tables.

Changes in the referencing table (Sports)

  • Insert (105, "F" / kho-kho, roll 6) into Sports: the constraint is violated, because 6 does not exist in Student, so the insert is not allowed. Student itself is not affected at all.
  • Delete a Sports row (the student lost interest and asked to have their name removed): no problem. Nothing to change in Student; roll 2 stays as it is.
  • Update roll 3 to roll 6 in Sports (roll 3 wants his friend with roll 6 enrolled in sport 103 instead): the sports teacher sees no 6 in the school records, so the update is refused. If 6 did exist in Student, the update would be valid.
OperationOn referenced table (Student)On referencing table (Sports)

➕ Added for exam SQL lets you choose what happens when a referenced row is deleted or updated (ON DELETE … / ON UPDATE …):
OptionEffect on child rows
CASCADEDelete (or update) the matching child rows too. The lecture's "cascade".

FOREIGN KEY (RollNo) REFERENCES Student(RollNo)
  ON DELETE CASCADE ON UPDATE CASCADE
🎯 IBPS exam alert The one-line rule: insert into the child and delete from the parent are the operations that can violate referential integrity (update can violate on both sides). Insert into the parent and delete from the child are always safe.

4.5Super Key (EmpID + Name)

🎓 From the lecture A super key is not some "super-power" key. Take a candidate key and combine it with any non-prime attribute (one that is not a key): the combination becomes a super key.
  • Employee table: EmpID is the primary key, so it is also one of the candidate keys.
  • EmpID + Name together is a super key.
  • Each employee also has a Location (where they work), a normal non-prime attribute. EmpID + Location is also a super key.
  • But non-prime + non-prime never makes a super key. Super key still contains "key", and a key must identify uniquely. If someone is named Akshay and is from Maharashtra, there will be many "Akshay–Maharashtra" combinations in the table, so it cannot identify a row uniquely.
➕ Added for exam The textbook definition is broader than the lecture's: a super key is any set of attributes that uniquely identifies each tuple. Any superset of a candidate key is a super key, including the candidate key itself and the set of all attributes. A candidate key is a minimal super key: remove any attribute and it stops being unique. So: Primary key ⊆ Candidate keys ⊆ Super keys.
⚠️ Exam trap "Every super key is a candidate key" is false; "every candidate key is a super key" is true. The candidate key alone (EmpID) also counts as a super key; you don't have to add anything to it.

Counting super keys

Relation with n attributes:
  • One candidate key with 1 attribute (say A): every super key contains A, and each of the other n − 1 attributes is either in or out. Number of super keys = 2n−1.
  • Two single-attribute candidate keys A and B: by inclusion–exclusion, |contains A| + |contains B| − |contains both| = 2n−1 + 2n−1 − 2n−2.
  • One candidate key with k attributes: 2n−k.

4.7Solved Exam QuestionsADDED

Q1The constraint that the primary key cannot be NULL is: (a) domain integrity (b) entity integrity (c) referential integrity (d) key integrity
Answer: (b) Entity integrity.
Q2A foreign key value must match a primary key value in another relation or be NULL. This is:
Answer: Referential integrity.
Q3Customer(CustID, PAN, Email, Name, City) — CustID, PAN and Email are each unique. CustID is chosen as the primary key. What are the alternate keys?
Answer: PAN and Email. All three are candidate keys.
Q4Account(AccNo, CustID) has CustID referencing Customer(CustID). Which operation can violate referential integrity? (a) Insert into Customer (b) Delete from Account (c) Insert into Account (d) None
Answer: (c) Insert into Account with a CustID that does not exist in Customer.
Q5Which clause automatically deletes child rows when the parent row is deleted?
Answer: ON DELETE CASCADE.
Q6R(A, B, C, D) has the single candidate key A. How many super keys does R have?
Answer: 24−1 = 8: A, AB, AC, AD, ABC, ABD, ACD, ABCD.
Q7R(A, B, C) has candidate keys A and B. How many super keys?
Answer: 22 + 22 − 21 = 6: A, AB, AC, ABC, B, BC.
Q8Which statement is true? (a) A table may have two primary keys (b) A UNIQUE column can hold NULL (c) A foreign key must be unique (d) Every super key is minimal
Answer: (b).

⚡ Rapid Revision

  • Domain integrity = type and allowed values (CHECK marks > 35). Entity integrity = PK never NULL. Referential integrity = FK refers to another table's PK. Key integrity = keys are unique.
  • Candidate keys = each can uniquely identify a record (RollNo, Phone, GovtID, AdmissionNo, RegNo); Name, Age, City cannot. ➕ Minimal super key; can be composite.
  • Primary key = one candidate key chosen by the DBA; unique, never NULL; only one per table (face unlock). Alternate keys = the remaining candidate keys (fingerprint, pattern, PIN).
  • Foreign key = attribute that refers to the PK of another table (Sports.RollNo → Student.RollNo; roll 5 refused by the sports teacher). ➕ Can be NULL, can repeat, can be self-referencing.
  • Referenced table (Student): insert ✓, delete ✗ → cascade (TC), update ✗ → update FK too. Referencing table (Sports): insert ✗ if roll missing, delete ✓, update ✗ if new roll missing.
  • ➕ ON DELETE / ON UPDATE: CASCADE, SET NULL, SET DEFAULT, RESTRICT / NO ACTION.
  • Super key = candidate key + any non-prime attribute (EmpID + Name, EmpID + Location). Non-prime + non-prime is never a super key (Akshay + Maharashtra). ➕ Any superset of a candidate key; PK ⊆ CK ⊆ SK.
  • ➕ Super keys with n attributes and one single-attribute CK = 2n−1.
