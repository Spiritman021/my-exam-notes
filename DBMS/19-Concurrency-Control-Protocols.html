Chapter 19

Concurrency Control Protocols

Chapter 18 tested a schedule after the fact. A real DBMS can't wait and check; it needs rules that make bad schedules impossible while transactions run. Those rules are concurrency control protocols. The two families are locking (a transaction must hold a lock on an item before touching it) and timestamp ordering (conflicting operations must run in the order the transactions started).

19.1Lock-Based Protocol: Shared and Exclusive Locks; Compatibility Matrix

🎓 Lecture topic (from outline) Before reading or writing an item, a transaction must ask the lock manager for a lock on it. If the lock can't be granted, the transaction waits.
  • Shared lock (S), lock-S(A): for reading only. Many transactions can hold S on the same item at once.
  • Exclusive lock (X), lock-X(A): for reading and writing. Only one transaction can hold it, and nobody else can hold any lock on that item meanwhile.
  • unlock(A) releases the lock.

🎓 Lecture topic (from outline) Only S with S is compatible, which mirrors chapter 18: only read–read pairs don't conflict.

Locks alone aren't enough

If T1 locks A, writes it, unlocks it immediately, then locks B, another transaction can slip in between and read the new A with the old B, the incorrect summary of chapter 17. Locking only works with a rule about when locks may be released. That rule is two-phase locking.
➕ Added for exam
  • Upgrade: S → X (a transaction that read A now wants to write it). Downgrade: X → S.
  • Starvation: a transaction waits forever because others keep getting the lock first (e.g. a stream of S requests keeps an X request waiting). The lock manager prevents this by granting requests in arrival order.

19.2Two-Phase Locking: Growing and Shrinking Phases — Solved

🎓 Lecture topic (from outline) Two-phase locking (2PL) splits each transaction's life into two phases:
  1. Growing phase: the transaction may acquire locks (and upgrade), but may not release any.
  2. Shrinking phase: once it releases its first lock, it may only release locks (and downgrade), never acquire a new one.
The moment a transaction acquires its last lock is its lock point.
2PL guarantees conflict serializability. Equivalent serial order = order of the transactions' lock points.

⚠️ Exam trap Basic 2PL guarantees serializability but does not prevent:
  • Deadlock: T1 holds X(A) and waits for B; T2 holds X(B) and waits for A. Both are still growing, so neither will release.
  • Cascading rollback: T1 may unlock A in its shrinking phase before committing; T2 reads A; T1 then aborts.
The variants in 19.5 fix these.

19.3Timestamp Ordering: TS, RTS and WTS (Bade Miyan, Chhote Miyan)

🎓 Lecture topic (from outline) Timestamp ordering uses no locks and never makes a transaction wait. Instead, it fixes the serial order in advance: the order in which transactions started.
  • Each transaction Ti gets a unique timestamp TS(Ti) when it starts (the system clock or a counter). An older transaction has a smaller timestamp.
  • Rule: conflicting operations must happen in timestamp order, so the schedule is equivalent to the serial order oldest → youngest.

Bade Miyan, Chhote Miyan

The elder (Bade Miyan, smaller TS) always goes first. If the younger one (Chhote Miyan) has already done something to an item that the elder should have done before him, the elder is too late, and the elder must go back and start again with a new, later timestamp.

Two timestamps per data item

  • RTS(X), read timestamp: the largest TS of any transaction that has read X so far (the youngest reader).
  • WTS(X), write timestamp: the largest TS of any transaction that has written X so far (the youngest writer).
Both start at 0.

Solved 2: same timestamps. Schedule R1(A), W1(A), R2(A), W2(A)

  • R1(A): 10 ≥ WTS 0 → allowed, RTS = 10.
  • W1(A): 10 ≥ RTS 10 and ≥ WTS 0 → allowed, WTS = 10.
  • R2(A): 20 ≥ WTS 10 → allowed, RTS = 20.
  • W2(A): 20 ≥ RTS 20 and ≥ WTS 10 → allowed, WTS = 20.
All allowed: the elder did everything first, exactly the serial order T1 → T2.
⚠️ Exam trap
  • The check is always "is the requesting transaction older (smaller TS) than someone who already acted?" A younger transaction acting after an older one is always fine.
  • Reads only check WTS. Writes check both RTS and WTS.
  • RTS is updated with max: an older reader arriving later doesn't lower it.

19.52PL Variants, Deadlock Prevention and Thomas Write RuleADDED

➕ Added for exam: variants of 2PL
VariantRuleSerializableNo cascading rollbackNo deadlock
Basic 2PLGrowing, then shrinking✅❌❌
Strict 2PLHold all X locks until commit/abort✅✅ (schedules are strict)❌
Rigorous 2PLHold all locks (S and X) until commit/abort✅ (serial order = commit order)✅❌
Conservative (static) 2PLAcquire every lock needed before starting✅❌✅
➕ Added for exam: deadlock prevention using timestamps When Ti requests a lock held by Tj:
  • Wait-die (non-preemptive): if Ti is older, it waits; if Ti is younger, it dies (rolls back and restarts with the same timestamp).
  • Wound-wait (preemptive): if Ti is older, it wounds Tj (forces Tj to roll back); if Ti is younger, it waits.
In both, the older transaction is never rolled back, so it eventually finishes: no starvation. Other approaches detect deadlocks instead: build a wait-for graph (Ti → Tj if Ti waits for Tj); a cycle means deadlock, and one transaction (the victim) is rolled back.

Thomas write rule

A relaxation of timestamp ordering: if TS(Ti) < WTS(X) on a write (and the RTS check passed), ignore the write instead of rolling back Ti. A younger transaction has already written a newer value that nobody older needed, so Ti's write is obsolete. This allows some view-serializable schedules that basic timestamp ordering rejects (chapter 18.4's blind writes).

19.6Solved Exam QuestionsADDED

Q1T1 holds a shared lock on A. Which requests by T2 are granted immediately?
Answer: only a shared lock. An exclusive lock must wait.
Q2In 2PL, during which phase can locks be released?
Answer: the shrinking phase.
Q3Which protocol guarantees freedom from deadlock? (a) basic 2PL (b) strict 2PL (c) conservative 2PL (d) rigorous 2PL
Answer: (c) conservative 2PL.
Q4Which 2PL variant holds exclusive locks until commit?
Answer: strict 2PL.
Q5TS(T1) = 5, TS(T2) = 8. WTS(A) = 8. T1 issues R(A). Result?
Answer: T1 is rolled back (5 < WTS 8: a younger transaction already wrote A).
Q6TS(T1) = 5, RTS(A) = 3, WTS(A) = 2. T1 issues W(A). Result?
Answer: allowed; WTS(A) becomes 5.
Q7In wait-die, an older transaction requesting a lock held by a younger one:
Answer: waits. (In wound-wait, it would roll back the younger one.)
Q8Under the Thomas write rule, an obsolete write (TS(Ti) < WTS(X)) is:
Answer: ignored, and Ti continues.

⚡ Rapid Revision

  • S lock = read, shareable. X lock = read + write, exclusive. Only S–S is compatible.
  • Locks without a release rule don't guarantee serializability.
  • 2PL: growing (acquire only) → shrinking (release only). Lock point = last lock acquired. Guarantees conflict serializability; order = lock points. Doesn't stop deadlock or cascading rollback.
  • A lock taken after any unlock ⇒ not 2PL.
  • ➕ Strict 2PL: X locks till commit (no cascading). Rigorous: all locks till commit. Conservative: all locks up front (no deadlock).
  • Timestamp ordering: older = smaller TS = goes first (Bade Miyan before Chhote Miyan). RTS(X) / WTS(X) = youngest reader / writer.
  • R(X): reject if TS < WTS(X); else RTS = max(RTS, TS). W(X): reject if TS < RTS(X) or TS < WTS(X); else WTS = TS. Rejected ⇒ restart with a new TS.
  • TS 10, 20: R1 R2 W2 W1 → W1 rejected (10 < RTS 20). R1 W1 R2 W2 → all allowed.
  • ➕ TO is deadlock-free, can starve. Thomas write rule: ignore obsolete writes. Wait-die: old waits, young dies. Wound-wait: old wounds young, young waits.
