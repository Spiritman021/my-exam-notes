Chapter 16

Transactions and ACID Properties

Chapters 16 to 19 are about what happens when many users change the database at the same time, and when the system crashes halfway through a change. The unit of work is the transaction. This chapter defines it and its four guarantees; chapter 17 shows what goes wrong when transactions overlap, chapter 18 how to test a schedule for safety, and chapter 19 how the DBMS enforces it.

16.1Need for Concurrency and What a Transaction Is (UPI Transfer)

🎓 Lecture topic (from outline)

What a transaction is

A transaction is a set of operations that together do one logical job, and must either all happen or not happen at all. In the theory it's written using two operations:
  • R(A): read data item A from the database into memory.
  • W(A): write the in-memory value of A back to the database.

Example: a UPI transfer of ₹500 from account A to account B

A has ₹1,000 and B has ₹2,000.
StepOperationAB
1R(A)10002000
2A = A − 500500 (in memory)2000
3W(A)5002000
4R(B)5002000
5B = B + 5005002500 (in memory)
6W(B)5002500

🎓 Lecture topic (from outline) Before: A + B = 3,000. After: A + B = 3,000. In between (after step 3), the money has left A but not reached B, and the total is 2,500. That in-between state must never be visible to anyone or left behind by a crash.

Why allow concurrency at all?

Running transactions strictly one after another would be safe, but slow. Thousands of UPI payments arrive every second. Running them concurrently (interleaved):
  • raises throughput: more transactions finish per second;
  • cuts waiting time: a short transaction doesn't queue behind a long one;
  • uses resources better: while one transaction waits for the disk, another can use the CPU.
The price is that interleaving can produce wrong results (chapter 17), so the DBMS must control it.

16.2ACID: Atomicity, Consistency, Isolation, Durability

🎓 Lecture topic (from outline) Every transaction must have four properties:

Atomicity: all or nothing

If the system fails after W(A) but before W(B), ₹500 has vanished. Atomicity says the transaction either completes fully or has no effect at all: on failure, the DBMS undoes W(A) and A goes back to ₹1,000.

Consistency: valid state to valid state

If the database is correct before the transaction, it must be correct after it. Here the rule is "the total money stays 3,000". Integrity constraints (chapter 4) are part of this too, e.g. balance can't go negative.

Isolation: as if alone

Even when transactions run concurrently, each must behave as if it were running alone. Nobody else may see A = 500 and B = 2,000, the half-done state. The result of concurrent execution must equal some serial order (chapter 18).

Durability: once committed, permanent

After COMMIT and the "payment successful" message, the transfer must survive a power cut or crash one second later. The DBMS writes it to stable storage (via the log) before confirming.

⚠️ Exam trap Consistency is the one property the DBMS can't fully guarantee by itself: if the programmer writes B = B + 400 instead of + 500, every other property holds and the database is still wrong. Questions asking "which ACID property is the responsibility of the programmer/user?" expect Consistency.

16.3Transaction States (Publishing a Video)

🎓 Lecture topic (from outline) A transaction moves through these states. Think of uploading and publishing a video:
StateMeaningVideo analogy
ActiveExecuting its reads and writesUploading, adding title and thumbnail
Partially committedLast operation done; changes still only in memory/bufferUpload finished, "Publish" pressed, still processing
CommittedChanges permanently savedVideo is live
FailedAn error means it can't continueUpload failed / processing error
AbortedRolled back; database restored to before it startedDraft discarded, channel unchanged
TerminatedFinished, either way; leaves the systemDone
⚠️ Exam trap
  • Partially committed is not committed. The last statement has run, but the changes may still be only in memory. A crash now can still send it to Failed.
  • A committed transaction can never go to Aborted. To reverse it, you run a new compensating transaction (e.g. a refund).

16.4Serial vs Concurrent Schedules

🎓 Lecture topic (from outline) A schedule is the order in which the operations of several transactions are actually executed. Within each transaction, its own operations keep their order.

Serial schedule

One transaction runs completely, then the next starts. No interleaving. Always correct (each transaction sees a consistent database), but slow.

Concurrent (non-serial) schedule

Operations of different transactions are interleaved. Faster, but only some interleavings give correct results.

16.5Counting Schedules; Who Guarantees Each ACID PropertyADDED

➕ Added for exam: counting schedules
  • n transactions can be run serially in n! orders. 3 transactions → 3! = 6 serial schedules.
  • Two transactions with m and n operations can be interleaved (keeping each one's own order) in (m + n)! ÷ (m! × n!) ways.
  • Example: T1 has 3 operations, T2 has 2 → 5! ÷ (3! × 2!) = 120 ÷ 12 = 10 schedules in total, of which 2 are serial, so 8 are non-serial.
  • For three transactions with a, b, c operations: (a + b + c)! ÷ (a! × b! × c!).
➕ Added for exam
  • The log (journal) records every change with old and new values before it's applied (write-ahead logging). Undo uses old values (atomicity); redo uses new values (durability).
  • Read-only transactions are always consistent and never need undo.
  • Many NoSQL systems relax ACID in favour of BASE (Basically Available, Soft state, Eventually consistent).
🎯 IBPS exam alert Expect: expand ACID, match a property to an example or to the component that enforces it, the order of transaction states, "which state comes right after the last statement executes?" (partially committed), and counting serial schedules (n!).

16.6Solved Exam QuestionsADDED

Q1"Either all operations of a transaction are reflected in the database, or none are." Which property?
Answer: Atomicity.
Q2Which property ensures committed changes survive a system crash?
Answer: Durability.
Q3Which component ensures isolation?
Answer: the concurrency control manager.
Q4After its final statement executes, a transaction is in which state?
Answer: partially committed.
Q5How many serial schedules are possible for 4 transactions?
Answer: 4! = 24.
Q6T1 has 2 operations and T2 has 2. How many non-serial schedules?
Answer: 4. Total = 4! ÷ (2! × 2!) = 6; minus 2 serial = 4.
Q7A transaction in the failed state next moves to:
Answer: aborted (after rollback), then terminated.
Q8Why does a DBMS allow concurrent execution?
Answer: higher throughput, lower waiting/response time and better resource use.

⚡ Rapid Revision

  • Transaction = one logical unit of work, all or nothing; written with R(X) and W(X). UPI ₹500 A → B: R(A), W(A), R(B), W(B), COMMIT; A + B stays 3,000.
  • Concurrency → more throughput, less waiting, better CPU/disk use; needs control.
  • Atomicity: all or nothing (recovery, undo). Consistency: valid → valid (programmer + constraints). Isolation: as if alone (concurrency control). Durability: committed = permanent (recovery, redo).
  • States: Active → Partially committed → Committed → Terminated; Active / Partially committed → Failed → Aborted → Terminated (restart or kill). Video: uploading → processing → live; or failed → draft discarded.
  • Schedule = execution order of operations of several transactions. Serial: one after another, always correct, slow. Concurrent: interleaved, fast, may be wrong.
  • ➕ n transactions → n! serial schedules. m and n operations → (m+n)! ÷ (m! n!) schedules in total.
