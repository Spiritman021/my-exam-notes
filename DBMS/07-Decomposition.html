Chapter 7

Decomposition

Normalization (chapter 8) fixes redundancy by splitting one table into smaller ones. That split is called a decomposition. A split is only useful if it is safe, and "safe" has two parts. Lossless join: joining the pieces back gives exactly the original table, no more and no less. Dependency preservation: every FD of the original can still be checked inside the pieces, without joining them. Both checks use the tools from chapters 5 and 6: keys and attribute closure.

7.1Lossless vs Lossy Decomposition (Movie Story with Extra Scenes)

🎓 Lecture topic (from outline) Decomposing R means replacing it with smaller relations R1, R2, … whose attributes together make up R. To get the original data back, we natural-join the pieces.
  • Lossless: R1 ⋈ R2 = R. The join gives back exactly the original tuples.
  • Lossy: R1 ⋈ R2 ⊃ R. The join gives back the original tuples plus extra ones that were never in R. These are called spurious tuples.

Analogy: a movie story with extra scenes

You cut a film into reels and stitch them back together. If the stitched film has scenes that were never in the original story, you can no longer tell which scenes are real. Nothing was deleted, yet the story is ruined. A lossy join works the same way: it doesn't drop rows, it adds fake ones, and the information about which rows were genuine is what gets lost.

Example: R(A, B, C) = {(1, a, x), (2, a, y)}

Split it as R1(A, B) and R2(B, C). The common attribute is B, and B = a appears in both rows.
R1(A, B)R2(B, C)R1 ⋈ R2 (on B)
(1, a)
(2, a)		(a, x)
(a, y)		(1, a, x) ✅
(1, a, y) ❌ spurious
(2, a, x) ❌ spurious
(2, a, y) ✅

The original had 2 rows; the join returns 4. The split R1(A, B), R2(A, C) instead joins on A, which is unique in both pieces, so it returns exactly the 2 original rows: lossless.

⚠️ Exam trap "Lossy" does not mean the join has fewer rows. A natural join of projections always contains every original row (R ⊆ R1 ⋈ R2). Lossy means it has more rows than R. If an option says "lossy decomposition loses tuples", it's wrong.

7.2Lossless Condition: Common Attribute Must Be a Key — Solved

🎓 Lecture topic (from outline) Checking with sample data only shows a split is lossy; to prove it's lossless for every possible instance, use the FDs. A decomposition of R into R1 and R2 is lossless if all three hold:
  1. R1 ∪ R2 = R: no attribute is left out.
  2. R1 ∩ R2 ≠ ∅: there's a common attribute to join on.
  3. The common attribute is a (super) key of R1 or of R2: (R1 ∩ R2) → R1 or (R1 ∩ R2) → R2.
Condition 3 is the heart of it. If the common value is a key on one side, each row on the other side matches at most one row there, so no spurious combinations can form. In 7.1, B = a matched two rows on both sides, which is why the join exploded.

Solved: R(A, B, C, D), F = {A → B, C → D}

  • R1(A, B), R2(C, D): R1 ∩ R2 = ∅. Nothing to join on, so the join is a cross product → lossy.
  • R1(A, B, C), R2(C, D): union = ABCD ✅, common = {C} ✅. C⁺ = {C, D} ⊇ R2, so C is a key of R2 ✅ → lossless.
  • R1(A, B), R2(B, C, D): common = {B}. B⁺ = {B}: not a key of R1 (needs A) and not of R2 (needs C, D) → lossy.

More than two pieces: join two at a time

R(A, B, C, D), F = {A → B, B → C, C → D}, split into R1(A, B), R2(B, C), R3(C, D).
  • R2 ⋈ R3 on C: C⁺ = {C, D} ⊇ R3 → lossless, giving (B, C, D).
  • R1 ⋈ (B, C, D) on B: B⁺ = {B, C, D} ⊇ BCD → lossless, giving (A, B, C, D) = R.
Every step is lossless, so the whole decomposition is lossless.
Lossless ⇔ R1 ∪ R2 = R, R1 ∩ R2 ≠ ∅, and (R1 ∩ R2)⁺ ⊇ R1 or (R1 ∩ R2)⁺ ⊇ R2
➕ Added for exam
  • The common attribute needs to be a key of only one of the two pieces, not both, and not of R.
  • For three or more pieces where pairwise merging gets stuck, textbooks use the chase (tableau / matrix) test: one row per piece, fill "a" for attributes the piece has, then apply the FDs to equate cells. If some row becomes all "a", the decomposition is lossless. For IBPS-level questions, merging two at a time is enough.
  • Lossless join is mandatory. A lossy decomposition is never acceptable, however good its normal form.
⚠️ Exam trap Compute the closure of the common attribute with the full F of R, then compare it with the attribute list of R1 or R2. Don't stop at "C appears on the left of some FD"; C must determine every attribute of that piece.

7.3Dependency-Preserving Decomposition — Solved R(A,B,C)

🎓 Lecture topic (from outline) After a split, each piece can only enforce the FDs whose attributes all sit inside it. Call Fi the FDs of F⁺ that fall entirely inside Ri. The decomposition is dependency preserving if those pieces together still imply everything F did:
(F1 ∪ F2 ∪ … ∪ Fn)⁺ = F⁺
If an FD is lost, the database can only check it by joining tables on every insert or update, which defeats the purpose of splitting.

Solved: R(A, B, C), F = {A → B, B → C, C → A}, split into R1(A, B), R2(B, C)

Step 1: find what each piece can enforce (use closures, not just the FDs as written).
  • R1(A, B): A⁺ = {A, B, C} → A → B. B⁺ = {B, C, A} → B → A. So F1 = {A → B, B → A}.
  • R2(B, C): B⁺ = {B, C, A} → B → C. C⁺ = {C, A, B} → C → B. So F2 = {B → C, C → B}.
Step 2: check each original FD using F1 ∪ F2 = {A → B, B → A, B → C, C → B}.
  • A → B: in F1 ✅
  • B → C: in F2 ✅
  • C → A: not written anywhere, but C⁺ = C, B (C → B), A (B → A). A is reached ✅
All three survive → dependency preserving. C → A looked lost because no piece has both C and A, but it is implied by the pieces.
⚠️ Exam trap Don't just look for each original FD inside a single piece. An FD that spans two pieces (like C → A here) can still be preserved through FDs that are derived on each piece (C → B, B → A). Always project F⁺, not F.
➕ Added for exam: the quick per-FD test To check whether X → Y is preserved without listing F1, F2 in full:
  1. result = X
  2. For each piece Ri: result = result ∪ ((result ∩ Ri)⁺ ∩ Ri), with closures computed under F.
  3. Repeat until result stops changing. X → Y is preserved if Y ⊆ result.
For C → A above: result = {C}; piece R2: (C)⁺ ∩ BC = {B, C} → result = {B, C}; piece R1: (B)⁺ ∩ AB = {A, B} → result = {A, B, C}. A is in it ✅.

7.4Dependency Not Preserved — Solved R(A,B,C,D)

🎓 Lecture topic (from outline)

Solved: R(A, B, C, D), F = {A → B, B → C, C → D}, split into R1(A, B), R2(A, C), R3(C, D)

Lossless? R1 ⋈ R2 on A: A⁺ = {A, B, C, D}, a key of both → (A, B, C). Then ⋈ R3 on C: C⁺ = {C, D} ⊇ R3 → R. Lossless ✅

Dependency preserving?
  • F1 on R1(A, B): A → B. (B⁺ = {B, C, D}: no A.)
  • F2 on R2(A, C): A → C (A⁺ contains C). C⁺ = {C, D}: no A.
  • F3 on R3(C, D): C → D.
F1 ∪ F2 ∪ F3 = {A → B, A → C, C → D}. Check each original FD:
  • A → B ✅ (F1)
  • C → D ✅ (F3)
  • B → C: B⁺ under {A → B, A → C, C → D} = {B}. B is on the left of nothing → not preserved ❌
The split is lossless but not dependency preserving. B and C never sit in the same table, so the database can't stop two rows with the same B and different C without joining R1 and R2.
➕ Added for exam The fix is to choose the pieces along the FDs: R1(A, B), R2(B, C), R3(C, D) is lossless (7.2) and keeps all three FDs, one in each table. As a rule of thumb, a piece built from an FD's left side plus its right side keeps that FD.

7.5Decomposition and the Normal FormsADDED

➕ Added for exam
PropertyMeaningRequired?Test
Lossless joinR1 ⋈ R2 = R, no spurious tuplesAlwaysCommon attribute is a key of R1 or R2
Dependency preserving(F1 ∪ … ∪ Fn)⁺ = F⁺Desirable, can be traded offClosure of each FD's left side using the projected FDs
  • 3NF: a decomposition that is both lossless and dependency preserving always exists (the 3NF synthesis algorithm, built from the minimal cover of chapter 6).
  • BCNF: a lossless decomposition always exists, but it may not preserve dependencies.
  • Classic case: R(A, B, C), F = {AB → C, C → B}. C → B breaks BCNF (C is not a key). Splitting into (C, B) and (A, C) is lossless (C is a key of CB) but AB → C is lost: no piece has A, B and C together.
🎯 IBPS exam alert The most-asked one-liner: "BCNF decomposition is always lossless but not always dependency preserving; 3NF can always be both." Expect it as a true/false statement or as "Which normal form guarantees a lossless, dependency-preserving decomposition?" → 3NF.

7.6Solved Exam QuestionsADDED

Q1A decomposition is lossy when the natural join of the pieces:
Answer: produces extra (spurious) tuples not in the original relation.
Q2R(A, B, C) with F = {A → B}. Is the split R1(A, B), R2(A, C) lossless?
Answer: Yes. Common = {A}; A⁺ = {A, B} ⊇ R1, so A is a key of R1.
Q3R(A, B, C) with F = {A → B}. Is the split R1(A, B), R2(B, C) lossless?
Answer: No. Common = {B}; B⁺ = {B}, a key of neither piece.
Q4R(A, B, C, D), F = {A → B, C → D}, split into (A, B) and (C, D). Lossless?
Answer: No. The pieces share no attribute, so the join is a Cartesian product.
Q5R(A, B, C, D), F = {AB → C, C → D}, split into R1(A, B, C), R2(C, D). Lossless and dependency preserving?
Answer: Both. Common C, C⁺ = {C, D} ⊇ R2 → lossless. AB → C lives in R1 and C → D in R2 → preserved.
Q6Which property must every decomposition satisfy? (a) lossless join (b) dependency preservation (c) both (d) neither
Answer: (a). Dependency preservation is sometimes given up (BCNF); lossless join never is.
Q7Which normal form always allows a lossless, dependency-preserving decomposition? (a) 2NF only (b) 3NF (c) BCNF (d) 4NF
Answer: (b) 3NF.

⚡ Rapid Revision

  • Decomposition = splitting R into smaller relations; rebuild with natural join.
  • Lossless: R1 ⋈ R2 = R. Lossy: R1 ⋈ R2 ⊃ R, extra spurious tuples (a movie stitched back with scenes that were never in the story). Lossy adds rows, it never drops them.
  • Lossless test: R1 ∪ R2 = R, R1 ∩ R2 ≠ ∅, and the common attribute is a key of R1 or R2 ((R1 ∩ R2)⁺ ⊇ R1 or R2).
  • 3+ pieces: merge two at a time, each merge must be lossless. ➕ Or use the chase/tableau test.
  • Dependency preserving: (F1 ∪ … ∪ Fn)⁺ = F⁺, where Fi = FDs of F⁺ inside Ri.
  • R(A, B, C), F = {A → B, B → C, C → A} → (A, B), (B, C): preserved, since C → B, B → A rebuild C → A.
  • R(A, B, C, D), F = {A → B, B → C, C → D} → (A, B), (A, C), (C, D): lossless, but B → C lost.
  • ➕ 3NF: lossless + dependency preserving always possible. BCNF: lossless always, preservation not guaranteed (AB → C, C → B).
