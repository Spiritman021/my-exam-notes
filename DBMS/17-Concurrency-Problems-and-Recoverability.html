Chapter 17

Concurrency Problems and Recoverability

Chapter 16 showed an interleaving that worked. This chapter shows the ones that don't. Each problem below is a schedule read top to bottom in time order, with T1's operations on the left and T2's on the right. Unless stated otherwise, A starts at ₹1,000 and B at ₹2,000. The second half of the chapter asks a different question: if a transaction fails, can the DBMS undo it cleanly?

17.1Dirty Read Problem (Copying Answers in the Exam Hall)

🎓 Lecture topic (from outline) A dirty read happens when a transaction reads a value written by another transaction that has not committed yet. If the writer then aborts, the reader has used a value that officially never existed.
TimeT1T2A in database
1R(A) → 10001000
2A = A − 500; W(A)500 (uncommitted)
3R(A) → 500 (dirty)500
4uses 500 in its own work
5fails → ROLLBACK1000
🎓 Lecture topic (from outline)

Analogy: copying answers in the exam hall

You copy an answer from your neighbour's sheet. A minute later they realise it's wrong and erase it. Their sheet is now correct, but your sheet still has the wrong answer you copied, and you've built the next steps on it. T2 copied a value T1 hadn't finalised.

Also called the temporary update problem, or a W–R conflict (T1 writes, T2 reads before T1 commits).

17.2Incorrect Summary and Lost Update Problems

🎓 Lecture topic (from outline)

Incorrect summary (inconsistent analysis)

T2 computes the bank's total balance while T1 moves ₹500 from A to B. T2 reads A after the debit and B before the credit.
TimeT1 (transfer)T2 (sum)
1R(A); A = A − 500; W(A) → 500
2sum = 0; R(A) → 500; sum = 500
3R(B) → 2000; sum = 2500
4R(B); B = B + 500; W(B) → 2500
🎓 Lecture topic (from outline) The true total is 3,000 before and after, but T2 reports 2,500: it saw half of T1's work. No transaction failed; the interleaving alone caused it.

Lost update

Two transactions read the same value, both change it, and the second write overwrites the first. T1 withdraws ₹500; T2 deposits ₹200.
TimeT1 (−500)T2 (+200)A in database
1R(A) → 10001000
2R(A) → 10001000
3A = 500; W(A)500
4A = 1200; W(A)1200
🎓 Lecture topic (from outline) The correct result is 1,000 − 500 + 200 = 700. T2 calculated from the old value 1,000, so T1's withdrawal is lost. This is a W–W conflict (two writes on A with no commit between them).

17.3Unrepeatable Read and Phantom Read Problems

🎓 Lecture topic (from outline)

Unrepeatable read

A transaction reads the same item twice and gets different values, because another transaction changed it in between.
TimeT1T2
1R(A) → 1000
2R(A); A = A − 500; W(A); COMMIT
3R(A) → 500
🎓 Lecture topic (from outline) T1 hasn't changed anything, yet A is different on the second read. Here T2 even committed, so nothing was dirty; the problem is purely that T1's view didn't stay fixed. This is an R–W conflict.

Phantom read

A transaction runs the same query twice and gets a different set of rows, because another transaction inserted (or deleted) matching rows in between.
TimeT1T2
1SELECT COUNT(*) FROM Emp WHERE Dept = 'IT' → 5
2INSERT INTO Emp VALUES (…, 'IT'); COMMIT
3SELECT COUNT(*) FROM Emp WHERE Dept = 'IT' → 6
⚠️ Exam trap Unrepeatable read = an existing row's value changed (UPDATE). Phantom read = new or vanished rows appear in the result (INSERT/DELETE). Locking the rows you read stops the first, but not the second, because the phantom row didn't exist when you locked.

17.4Cascading vs Cascadeless Schedules

🎓 Lecture topic (from outline)

Cascading rollback

If T2 read T1's uncommitted value, and T3 read T2's, then when T1 aborts, T2 must abort too (it used a value that never existed), and so must T3. One failure cascades into many rollbacks. That wastes a lot of work.
TimeT1T2T3
1W(A)
2R(A); W(B)
3R(B)
4ABORTmust abortmust abort
🎓 Lecture topic (from outline)

Cascadeless schedule

A schedule is cascadeless (avoids cascading aborts, ACA) if every transaction reads only values written by committed transactions. No dirty reads, so one abort never drags others down.
Cascadeless: if Tj reads X written by Ti, then Ti has already committed (or aborted) before that read
Fix for the example above: T2 waits to read A until T1 commits.

17.5Recoverable vs Irrecoverable Schedules

🎓 Lecture topic (from outline)

Irrecoverable schedule

T2 reads T1's dirty value and commits; then T1 aborts. T2 should be rolled back, but it's committed, and durability says committed changes can't be undone. The database is stuck in a wrong state.
TimeT1T2
1W(A)
2R(A) (dirty)
3COMMIT
4ABORTcan't roll back ❌
🎓 Lecture topic (from outline)

Recoverable schedule

Recoverable: if Tj reads X written by Ti, then Ti commits before Tj commits
Swap steps 3 and 4 above, so T2 can't commit until T1 does. If T1 commits, T2 can commit. If T1 aborts, T2 is still uncommitted and can be rolled back (a cascading rollback, but a possible one).
⚠️ Exam trap A dirty read alone doesn't make a schedule irrecoverable. What matters is the commit order: the reader committing before the writer. A schedule with dirty reads where every writer commits first is recoverable (but not cascadeless).

17.6Strict Schedule and the Schedule Hierarchy

🎓 Lecture topic (from outline)

Strict schedule

A schedule is strict if no transaction reads or writes X until the last transaction that wrote X has committed or aborted. Cascadeless only bans dirty reads; strict also bans overwriting uncommitted data.

Why it matters: to undo an aborted write in a strict schedule, the DBMS just restores X's old value (its before-image). No other transaction can have touched X in between.

Example: cascadeless but not strict

TimeT1T2
1W(A)
2W(A) (blind write, no read)
3COMMIT
4COMMIT
🎓 Lecture topic (from outline) No one reads uncommitted data → cascadeless ✅. But T2 writes A while T1's write is uncommitted → not strict ❌. If T1 had aborted, restoring A's old value would also wipe out T2's write.

The hierarchy

ClassRulePrevents
RecoverableReader commits after the writer it read fromCommitting on top of data that later vanishes
CascadelessRead only committed dataCascading rollbacks
StrictRead or write only committed dataMessy undo of overwritten values

17.8Solved Exam QuestionsADDED

Q1T2 reads a value written by T1 before T1 commits, and T1 then aborts. Which problem?
Answer: dirty read (temporary update).
Q2Two transactions update the same item and one update is overwritten. Which problem?
Answer: lost update.
Q3A transaction re-runs a query and finds new rows inserted by another transaction. Which problem?
Answer: phantom read.
Q4Schedule: W1(A), R2(A), C2, C1. Recoverable?
Answer: No. T2 read from T1 but committed first.
Q5Schedule: W1(A), R2(A), C1, C2. Recoverable? Cascadeless?
Answer: Recoverable, not cascadeless (T2 read uncommitted A).
Q6Schedule: W1(A), C1, R2(A), W2(A), C2. Which classes?
Answer: strict (and therefore cascadeless and recoverable).
Q7Which relation is correct? (a) Recoverable ⊂ Cascadeless (b) Strict ⊂ Cascadeless ⊂ Recoverable (c) Cascadeless ⊂ Strict (d) Recoverable ⊂ Strict
Answer: (b).
Q8Which isolation level allows dirty reads?
Answer: READ UNCOMMITTED.

⚡ Rapid Revision

  • Dirty read (W–R): read uncommitted data, writer aborts. Copying an answer the neighbour later erases.
  • Incorrect summary: SUM sees A after debit, B before credit → 2,500 instead of 3,000.
  • Lost update (W–W): both read 1,000; −500 then +200 written → 1,200 instead of 700.
  • Unrepeatable read (R–W): same row read twice, different value. Phantom: same query twice, new/vanished rows.
  • Cascading rollback: one abort forces readers of its dirty data to abort. Cascadeless: read only committed data.
  • Irrecoverable: reader commits before the writer it read from, then the writer aborts. Recoverable: writer commits first.
  • Strict: no read or write of X until X's last writer finishes. W1(A) W2(A) C1 C2 is cascadeless, not strict.
  • Hierarchy: Serial ⊂ Strict ⊂ Cascadeless ⊂ Recoverable ⊂ All.
  • ➕ Isolation levels: READ UNCOMMITTED (all 3 problems) → READ COMMITTED (no dirty) → REPEATABLE READ (no unrepeatable) → SERIALIZABLE (no phantom).
