Chapter 3

ER Model

Before a single table is created, the database designer sketches what the database is about: the things it stores, the facts about each thing, and how the things are connected. The Entity-Relationship (ER) model is that sketch. It lives at the conceptual level of the three-schema architecture (chapter 2), and every ER diagram can be converted mechanically into tables. This chapter builds the vocabulary and shows exactly how each kind of relationship turns into tables and keys.

3.1ER Diagram: Entity, Entity Type and Entity Set (Student Table)

🎓 From the lecture
  • An ER diagram is a visualisation that captures entities and the relationships between them. Its advantages: very easy to make, simple notation with few symbols, and easy to understand; a third person looking at a finished ER diagram can understand how the entities are related.
  • Entity: a real-world object that has an existence, either physical or logical. Student, teacher, administrator exist physically; you can see and touch them. A bank account exists only logically.
  • Entities have attributes (roll number, name, father's name, mother's name, phone number, city). Entities differ from each other by the values of their attributes, which is how we identify a particular student.

Entity vs entity type vs entity set

Students often confuse these three. Take a Student table:
  • Entity: one row (record). Roll no 1, name "Shridhar" is one entity; 1 and "Shridhar" are the values of its attributes.
  • Entity type: the table's name plus the attributes it contains: Student(RollNo, Name). Every entity of it will be of type Student with those attributes.
  • Entity set: a set of entities, e.g. {S1, S2, S3}.
➕ Added for exam The ER model was proposed by Peter Chen in 1976. It is a conceptual (high-level) data model. Standard Chen notation:

3.2Attributes and Domain

🎓 From the lecture
  • Attributes give information about an entity: they are its properties or characteristics. Every student has a roll number (a characteristic) and a name (a property).
  • Domain: the allowed set of values for an attribute. It is very important and used a lot later. If the school has roll numbers only up to 99, the domain of RollNo is two-digit positive integers; no characters allowed. That is a strict domain; usually we just say "integer" or "character".
➕ Added for exam A domain is atomic in the relational model: each value is indivisible. The domain is enforced in SQL by the data type plus a CHECK constraint, e.g. RollNo INT CHECK (RollNo BETWEEN 1 AND 99). This is domain integrity (chapter 4). A NULL value means "unknown" or "not applicable" and is not part of any domain.

3.3Types of Attributes: Single/Multi-Valued, Simple/Composite, Derived, Key, Descriptive (Calling "Akshay" at Attendance)

🎓 From the lecture
  • Single-valued: has exactly one value. RollNo; have you ever seen a student with two roll numbers? Drawn as a normal ellipse (oval).
  • Multi-valued: can hold more than one value. Phone number (main number + alternate number). Drawn as a double ellipse.
  • Simple (atomic): cannot be divided further. RollNo 1, 2, 3; what would you divide?
  • Composite: can be divided further. Address: you never answer "Flat number XYZ"; you say which street it is on, which city, which state. City + street + state together make the address.
  • Derived: computed from another attribute. Age derived from date of birth: if you doubt someone's age, you ask their birth year and calculate it.
  • Key (prime) attribute: uniquely identifies each entity; drawn in an ellipse with its name underlined. Attendance is taken by roll number because if you call "Rakesh", 10 Rakeshes stand up; "Suresh", 20; call "Akshay" (a very common name) and 50 Akshays stand up.
  • Descriptive attribute: attached to a relationship, not to an entity. All the other attributes belong to entities.
➕ Added for exam
  • Attributes can combine: Address is composite + single-valued; a list of degrees, each with (name, year), is a composite multi-valued attribute.
  • A stored attribute is the opposite of a derived one: DOB is stored, Age is derived.
  • When converting to tables, a multi-valued attribute becomes a separate table (key + that attribute), and a composite attribute is flattened into its components (Street, City, State columns).
  • Example of a descriptive attribute: Date_of_enrolment on the relationship "Student enrolls in Course", or Grade on "Student takes Subject". It belongs to the pair, not to either entity alone.
⚠️ Exam trap Double ellipse = multi-valued; dashed ellipse = derived; double rectangle = weak entity; double diamond = identifying relationship. Don't swap "double" and "dashed". And "simple" is the opposite of composite, while "single-valued" is the opposite of multi-valued; they are two separate classifications.

3.4Relationships and One-to-One Cardinality (Student Enrolled in Course)

🎓 From the lecture
  • A relationship (also called an association) answers "yeh rishta kya kehlata hai?" — what is the relation between two entities? It is drawn as a diamond with the relation written inside: "Student studies in College".
  • Entities, relationships and attributes in an ER diagram help us understand the tables of the database better, and so does the cardinality of the relationship: one-to-one, many-to-one, one-to-many, many-to-many.

One-to-one (1:1)

"One candidate standing on each side." Student enrolled in Course, with a rule: a student enrols in only one course and each course has only one student. Another example: I am alone in this room teaching, and you are alone watching the video: one on each end.

The relationship table

The Student table (RollNo, Name) and the Course table (CourseID, Name) describe two separate things. Neither shows which student joined which course. That information goes in a relationship table, made of the prime attribute of each side: RollNo and CourseID. These columns refer to the other tables, so they are foreign keys (concept coming in chapter 4).

3.5One-to-Many and Reducing Tables (Parent–Child)

🎓 From the lecture One-to-many (1:N): Parent and Child entities (rectangles), where "parent" means the biological mother-father pair. One parent pair can have many children, but biologically a child cannot have more than one parent pair. So: parent has many children; child has one parent.

Relationship table

Parent table (ID = government ID, Name) and Child table (CID, Name). The relationship table takes ID and CID, both foreign keys. Parent 1 has two children, parent 2 has one, parent 3 has two (104, 105).
  • The ID column repeats: to show one parent with many children, the parent ID must be repeated. That is the nature of 1:N.
  • The CID column is unique, because each child has only one parent.
  • So CID (the "many" side's key) is the primary key of the relationship table.

🎓 From the lecture — solved problem: reduce the number of tables
QThere are three tables. Can the relationship table be merged with one of the others to reduce the count? With which one?
Answer: Merge it with the Child table (the "many" side).
  • In the relationship table, CID is unique and is its primary key. In the Child table, CID is also unique and is the primary key. Both are unique on the common column: "the horoscopes match" (kundli mil gayi), so join them.
  • Do not merge with Parent: ID repeats in the relationship table but is unique in Parent.
  • Result: Child(CID, Name, ID) with CID as primary key and ID as foreign key. The meaning has not changed; we still know each child's parent, plus the child's name.
So a 1:N relationship needs only 2 tables.

3.6Many-to-Many and Composite Primary Key (Students–Subjects)

🎓 From the lecture Many-to-many (M:N): Student and Subject. A student can study many subjects (one side of the story); a subject can be studied by many students (the other side). "A fierce war from both sides, weapons flying in both directions."

Relationship table

RollNo and SID, both foreign keys referring to the primary keys of Student and Subject.
  • Roll 1 studies S1 and S3: one student, more than one subject.
  • S1 is studied by 1 and 2; S2 by 3 and 5: one subject, more than one student.
  • Neither column is unique: values repeat in RollNo and in SID.
  • So the primary key is the combination (RollNo, SID), a composite key. Check the whole table: 1-S1 never appears twice, nor 2-S1, 1-S3, 3-S2 or 4-S1. Combined, every record is uniquely identified.

⚠️ Exam trap For 1:N, the foreign key goes on the many side (Child gets Parent's ID), never the other way round; putting many child IDs into one Parent row would violate 1NF. And in M:N, neither foreign key alone can be the primary key.

3.7Generalization and Specialization (Person → Student, Teacher)

🎓 From the lecture Questions have been asked on this, which is why it is covered.
  • Generalization: going from a low level to a high level, from the personal/specific level to the general level. It is a bottom-up approach. Student is an entity, Teacher is an entity (specific level); taken together, both are human beings, both are Person. "Student is a Person", "Teacher is a Person".
  • Specialization: the reverse, from a high level to a low level, a top-down approach. You are not talking generally but specifically. Two persons stand in front of you. One wears a school uniform, so "this person is a Student". The other carries books and an attendance register, so "this person is a Teacher". You moved from a general statement to a specific one.
➕ Added for exam
  • The higher-level entity is the superclass; lower-level ones are subclasses. Subclasses inherit all attributes and relationships of the superclass (attribute inheritance): Student and Teacher both get Name and Address from Person, and add their own (RollNo; EmpID, Salary).
  • Disjoint vs overlapping: disjoint means an entity belongs to at most one subclass (an Account is either Savings or Current); overlapping means it can be in several (a Person can be both Student and Employee).
  • Total vs partial (completeness): total means every superclass entity must belong to some subclass; partial means some may belong to none.
  • Generalization emphasises common features; specialization emphasises differences.
⚠️ Exam trap Generalization = bottom-up (think "grouping up"); Specialization = top-down ("splitting down"). Exams frequently swap these two in the options.

3.8Weak Entities, Participation, Degree and AggregationADDED

➕ Added for exam
  • Strong entity: has its own primary key (Employee with EmpID). Weak entity: has no primary key of its own; it depends on an owner (identifying) entity. Example: Dependent (an employee's family member, identified by name only within that employee) or Loan Payment (payment no. 1, 2, 3 repeats across loans). Drawn as a double rectangle, linked by a double diamond. Its partial key / discriminator (dashed underline) plus the owner's key forms its primary key: (EmpID, DependentName).
  • A weak entity always has total participation in its identifying relationship.
  • Participation constraint: total (double line) means every entity must take part (every Loan must have a Customer); partial (single line) means some may not (not every Customer has a Loan).
  • Degree of a relationship = number of entity sets taking part: unary (recursive; Employee manages Employee), binary (Student–Course, the most common), ternary (Supplier–Part–Project).
  • Aggregation: treating a relationship (with its entities) as a single higher-level entity so it can take part in another relationship. Example: (Employee works on Project) is aggregated, then monitored by Manager.
  • Cardinality is also shown with min–max (structural) notation (0..1, 1..N) or with crow's-foot notation in industry tools.
⚠️ Exam trap The lecture says "degree or cardinality" loosely. In exams they are different: degree of a relationship = how many entity sets participate (unary, binary, ternary); cardinality ratio = how many instances map (1:1, 1:N, M:N).

3.9Solved Exam QuestionsADDED

Q1In an ER diagram, a multi-valued attribute is shown by: (a) dashed ellipse (b) double ellipse (c) double rectangle (d) underlined ellipse
Answer: (b) Double ellipse.
Q2Age, computed from date of birth, is a ____ attribute.
Answer: Derived.
Q3Entity sets A and B have a 1:N relationship R (one A, many B). What is the minimum number of tables, and where does A's key go?
Answer: 2 tables; A's key becomes a foreign key in B (the many side).
Q4The primary key of the relationship table for an M:N relationship between Student(RollNo) and Subject(SID) is:
Answer: (RollNo, SID), a composite key.
Q5An entity set that does not have sufficient attributes to form a primary key is a:
Answer: Weak entity set.
Q6Creating a superclass "Vehicle" from existing classes "Car" and "Truck" is: (a) specialization (b) generalization (c) aggregation (d) association
Answer: (b) Generalization (bottom-up).
Q7"Employee manages Employee" is a relationship of degree:
Answer: 1 (unary / recursive).
Q8Who proposed the ER model?
Answer: Peter Chen (1976).

⚡ Rapid Revision

  • ER diagram = entities + relationships; easy to draw, simple notation, easy to read. ➕ Peter Chen, 1976; conceptual level.
  • Entity = real-world object with physical (student) or logical (bank account) existence. Entity = row; entity type = Student(RollNo, Name); entity set = {S1, S2, S3}.
  • Attribute = property/characteristic. Domain = allowed values (2-digit positive integers for roll no ≤ 99).
  • Attribute types: single (ellipse) / multi-valued (double ellipse, phone); simple / composite (address); derived (age from DOB, ➕ dashed); key (underlined; "50 Akshays stand up"); descriptive (on a relationship).
  • Relationship = association, diamond ("Student studies in College").
  • 1:1 (Student–Course): nothing repeats; either key can be PK. 1:N (Parent–Child): parent ID repeats, CID unique → CID is PK; merge relationship into the many side ("kundli mil gayi") → 2 tables. M:N (Student–Subject): both repeat → composite PK (RollNo, SID) → 3 tables.
  • Generalization = bottom-up, low → high (Student, Teacher → Person). Specialization = top-down, high → low (Person → uniform = Student, register = Teacher).
  • ➕ Weak entity = double rectangle + double diamond, PK = owner key + partial key, total participation. Degree = unary/binary/ternary; cardinality = 1:1/1:N/M:N. Aggregation = relationship treated as an entity.
