Chapter 8

Normalization

A table that stores too many facts at once repeats data, and repeated data goes out of sync. Normalization is the step-by-step process of splitting such a table, using the decomposition rules of chapter 7, until each table holds one kind of fact. Each normal form is a rule that forbids one kind of bad dependency. Every check uses chapter 5's tools: candidate keys, prime attributes and attribute closure.

8.1Purpose of Normalization and the Normal Forms

🎓 Lecture topic (from outline) Normalization removes redundancy, and with it the three anomalies that redundancy causes. Take one table that mixes student and course facts:
RollNameCourseIDCourseNameFee
1AshaC1DBMS5000
2RaviC1DBMS5000
3NehaC2OS4000
🎓 Lecture topic (from outline)
  • Insertion anomaly: a new course C3 can't be added until some student joins it, because Roll is part of the key and can't be NULL.
  • Deletion anomaly: deleting Neha (the only C2 student) also deletes the fact that course C2 is "OS" with fee 4000.
  • Update anomaly: changing the DBMS fee means updating every row with C1. Miss one and the data contradicts itself.

The normal forms, in order

Each one includes the one before it and adds one more rule:
  • 1NF: every cell holds a single (atomic) value.
  • 2NF: 1NF + no partial dependency.
  • 3NF: 2NF + no transitive dependency.
  • BCNF: every determinant is a super key.
  • 4NF: BCNF + no non-trivial multi-valued dependency.
  • 5NF: 4NF + no join dependency that isn't implied by the keys.
➕ Added for exam: terms you need for every check
  • Prime attribute: part of at least one candidate key. Non-prime attribute: part of no candidate key.
  • Normalization trades redundancy for joins: more tables, more joins at query time. That's why reporting systems (OLAP, chapter 1) are often deliberately denormalized.
  • Every split must be lossless (chapter 7). Up to 3NF it can also always be dependency preserving.

8.2First Normal Form: Three Approaches (Employee Projects)

🎓 Lecture topic (from outline) A relation is in 1NF if every attribute holds only atomic (indivisible) values: no lists, no sets, no repeating groups in one cell.

Not in 1NF: an employee works on several projects

EIDNameProjects
101AmitP1, P2
102SaraP3
🎓 Lecture topic (from outline) Three ways to bring it to 1NF:
  1. One row per value: (101, Amit, P1), (101, Amit, P2), (102, Sara, P3). The key becomes (EID, Project). Simple, but Amit's name now repeats.
  2. One column per value: Project1, Project2, Project3. EID stays the key, but you must guess the maximum number of projects, and short lists leave NULLs.
  3. Separate table (best): Employee(EID, Name) and EmpProject(EID, Project), with EmpProject.EID a foreign key to Employee. No repetition, no NULLs, no limit.
ApproachKeyDownside
1. One row per value(EID, Project)Name repeats → redundancy
2. One column per valueEIDFixed limit, many NULLs
3. Separate tableEID; (EID, Project)Needs a join to see both (usually the right choice)
⚠️ Exam trap In theory questions, a relation (as defined in the relational model) is always in 1NF by definition. If a question gives you FDs and asks for the highest normal form, assume 1NF and start from 2NF.

8.3Second Normal Form: Partial Dependency

🎓 Lecture topic (from outline) A relation is in 2NF if it is in 1NF and has no partial dependency.
Partial dependency: (proper subset of a candidate key) → (non-prime attribute)
In other words, a non-prime attribute must depend on the whole key, not on part of it.

Example: R(Roll, CourseID, Name, Fee), key = (Roll, CourseID)

  • Roll → Name: Name depends on only part of the key → partial ❌
  • CourseID → Fee: also partial ❌
Fix: move each partial dependency into its own table, and keep the key in a table of its own.
  • Student(Roll, Name)
  • Course(CourseID, Fee)
  • Enrolment(Roll, CourseID)
Each split is lossless: the common attribute is the key of the new table.
➕ Added for exam
  • If every candidate key is a single attribute, the relation is automatically in 2NF: a single attribute has no proper subset to depend on.
  • A dependency on part of the key is only a 2NF violation if the right side is non-prime. If it's prime, it's not a partial dependency.

8.4Third Normal Form: Transitive Dependency

🎓 Lecture topic (from outline) A relation is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on a key.
Transitive dependency: Key → X → Y, where X is not a super key and Y is non-prime

Example: Emp(EID, Name, DeptID, DeptName), key = EID

EID → DeptID and DeptID → DeptName, so EID → DeptName holds only through DeptID. DeptID is not a key, DeptName is non-prime → transitive ❌. Every employee in a department repeats its name.

Fix: move the second hop into its own table.
  • Emp(EID, Name, DeptID)
  • Dept(DeptID, DeptName)
3NF test: for every non-trivial X → Y, either X is a super key or Y is a prime attribute
➕ Added for exam The formal test above covers 2NF and 3NF in one go: a partial dependency and a transitive dependency both have a non-super-key on the left and a non-prime on the right. Use it in exams instead of hunting for chains. "Y is prime" is the escape clause that separates 3NF from BCNF.

8.5BCNF and the Normal-Form Hierarchy

🎓 Lecture topic (from outline) Boyce–Codd Normal Form drops 3NF's escape clause:
BCNF: for every non-trivial X → Y, X is a super key

Example: R(Student, Course, Teacher)

Each teacher teaches one course; a student takes a course from one teacher. F = {(Student, Course) → Teacher, Teacher → Course}.
  • Candidate keys: (Student, Course) and (Student, Teacher). All three attributes are prime.
  • Teacher → Course: Teacher is not a super key, but Course is prime → 3NF ✅, BCNF ❌.
Fix: TeacherCourse(Teacher, Course) and StudentTeacher(Student, Teacher). Lossless (Teacher is a key of the first), but (Student, Course) → Teacher is lost. This is the BCNF trade-off from chapter 7.
Normal formRemovesRule
1NFMulti-valued / composite cellsAtomic values only
2NFPartial dependencyNo non-prime depends on part of a candidate key
3NFTransitive dependencyX → Y: X super key or Y prime
BCNFAny non-key determinantX → Y: X super key
4NFMulti-valued dependencyX →→ Y: X super key
5NFJoin dependencyEvery join dependency implied by keys
➕ Added for exam
  • A relation with only two attributes is always in BCNF.
  • If every attribute is prime, the relation is at least in 3NF (but may not be in BCNF, as above).
  • If every candidate key is a single attribute and the relation is in 3NF, it is also in BCNF.

8.64NF (Multi-Valued Dependency) and 5NF

🎓 Lecture topic (from outline)

Multi-valued dependency (MVD)

X →→ Y ("X multi-determines Y") means each X value has a set of Y values, and that set is independent of the other attributes. It shows up when one table stores two unrelated lists about the same thing.

Example: Faculty(Name, Subject, Hobby)

Amit teaches DBMS and OS, and his hobbies are chess and music. Subjects and hobbies have nothing to do with each other, yet the table must store every combination:
NameSubjectHobby
AmitDBMSChess
AmitDBMSMusic
AmitOSChess
AmitOSMusic
🎓 Lecture topic (from outline) Name →→ Subject and Name →→ Hobby. The only key is all three attributes, and there are no FDs, so the table is in BCNF but still redundant. Adding one new hobby means adding one row per subject.

4NF: BCNF + for every non-trivial MVD X →→ Y, X is a super key. Fix: FacultySubject(Name, Subject) and FacultyHobby(Name, Hobby).

5NF (Project-Join Normal Form)

A relation is in 5NF if it can't be split into three or more smaller tables and losslessly joined back, except in ways that follow from its keys. It targets join dependencies: cases where a table can only be rebuilt losslessly from three or more of its projections, never from two.
➕ Added for exam
  • Every FD is also an MVD (X → Y implies X →→ Y), but not the other way round.
  • X →→ Y is trivial if Y ⊆ X or X ∪ Y = all attributes of R.
  • 5NF example: Agent(Agent, Company, Product) under the rule "if an agent sells for a company, and sells a product, and the company makes that product, then the agent sells that product for that company". Then it splits into (Agent, Company), (Company, Product), (Agent, Product), and only all three joined together give R back.
  • 5NF is also called PJNF. It's the final normal form in the standard hierarchy.

8.7Finding the Highest Normal Form — SolvedADDED

➕ Added for exam: the method
  1. Find all candidate keys (chapter 5 closures). List the prime attributes.
  2. For each FD X → Y, check from the top down:
    • X is a super key → fine for BCNF.
    • Otherwise, Y is prime → fine for 3NF, breaks BCNF.
    • Otherwise, X is a proper subset of a candidate key → partial → breaks 2NF.
    • Otherwise → transitive → 2NF, breaks 3NF.
  3. The relation's normal form is the lowest level that every FD passes.
R and FCandidate keysWorst FDHighest NF
R(A,B,C,D), {A → B}ACDA → B: A ⊂ key, B non-prime → partial1NF
R(A,B,C,D), {AB → C, C → D}ABC → D: C not a key, not part of AB, D non-prime → transitive2NF
R(A,B,C,D), {AB → CD, D → A}AB, DBD → A: D not a super key, but A is prime3NF
R(A,B,C), {A → B, B → C, C → A}A, B, CEvery left side is a keyBCNF
⚠️ Exam trap Find every candidate key before deciding what's prime. In the third row, if you stop at AB you'll think A is the only prime part, miss DB, and wrongly call D → A a partial dependency. D is prime because DB is a key.
🎯 IBPS exam alert "Highest normal form of R" is the most common normalization question. The second most common is a definition match: "removes partial dependency" → 2NF, "removes transitive dependency" → 3NF, "every determinant is a candidate key" → BCNF, "removes multi-valued dependency" → 4NF, "removes join dependency" → 5NF.

8.8Solved Exam QuestionsADDED

Q1Deleting the last student of a course also deletes the course details. This is a(n):
Answer: deletion anomaly.
Q2A relation in 1NF whose candidate keys are all single attributes is always in:
Answer: 2NF. A partial dependency needs a composite key.
Q3Which normal form is based on transitive dependency? (a) 1NF (b) 2NF (c) 3NF (d) BCNF
Answer: (c) 3NF.
Q4R(A, B, C, D), F = {AB → C, B → D}. Highest normal form?
Answer: 1NF. Key = AB. B → D: B is part of the key and D is non-prime → partial dependency.
Q5Every relation in BCNF is also in 3NF. True or false?
Answer: True. The converse is false (Student, Course, Teacher in 8.5).
Q6Any relation with exactly two attributes is in:
Answer: BCNF (and in fact 4NF).
Q74NF deals with which dependency? (a) functional (b) multi-valued (c) join (d) transitive
Answer: (b) multi-valued. 5NF deals with join dependency.
Q8Which normal form guarantees a lossless, dependency-preserving decomposition always exists?
Answer: 3NF. BCNF guarantees only lossless (chapter 7).

⚡ Rapid Revision

  • Purpose: remove redundancy and the insertion, deletion and update anomalies it causes.
  • 1NF: atomic values. Employee projects: one row per value, one column per value, or (best) a separate table.
  • 2NF: no partial dependency (part of a candidate key → non-prime). All single-attribute keys ⇒ automatically 2NF.
  • 3NF: no transitive dependency. Test: X → Y has X super key or Y prime.
  • BCNF: every X → Y has X super key. (Student, Course, Teacher) with Teacher → Course is 3NF, not BCNF.
  • Hierarchy: 5NF ⊂ 4NF ⊂ BCNF ⊂ 3NF ⊂ 2NF ⊂ 1NF.
  • 4NF: no non-trivial MVD X →→ Y unless X is a super key (Faculty, Subject, Hobby → split into two tables).
  • 5NF / PJNF: no join dependency except those implied by keys.
  • ➕ Highest NF: find all candidate keys → prime attributes → test every FD; the weakest FD decides.
  • ➕ Two-attribute relation ⇒ BCNF. All attributes prime ⇒ at least 3NF.
