Chapter 14

Indexing

A table lives on disk, and the disk is read one block at a time. Reading a block is slow compared with anything done in memory, so the cost of a query is measured in block accesses. An index is a small extra file that tells the DBMS which block to read, so it doesn't have to scan them all. One example file runs through the whole chapter, so you can see each index type cut the number of block accesses.

14.1Why Indexing (Book Index); Records in Blocks — Solved Numerical

🎓 Lecture topic (from outline)

Analogy: the index at the back of a book

To find "deadlock" in a 900-page book, you don't read every page. You look it up in the index at the back, which says "page 412", and jump straight there. The index is small and sorted, so it's quick to search, and it points to where the real content is. A database index works the same way: search key → pointer to the block.

Records are stored in blocks

  • The disk is divided into blocks (pages) of fixed size, e.g. 1024 bytes. One read fetches one whole block.
  • Blocking factor (bfr) = number of records that fit in one block = ⌊block size ÷ record size⌋.
  • Number of blocks = ⌈number of records ÷ bfr⌉.
SolvedA file has 30,000 records of 100 bytes each. Block size is 1024 bytes. Find the blocks needed and the block accesses to find a record.
bfr = ⌊1024 ÷ 100⌋ = 10 records per block (24 bytes per block are unused).
Blocks = ⌈30,000 ÷ 10⌉ = 3,000 blocks.
No index, unsorted file: linear search. Worst case 3,000 block accesses; average 3,000 ÷ 2 = 1,500.
No index, file sorted on the search key: binary search on blocks = ⌈log₂ 3,000⌉ = 12 block accesses (2¹¹ = 2,048 < 3,000 ≤ 4,096 = 2¹²).
➕ Added for exam
  • Unspanned organization: a record never crosses a block boundary, so leftover space is wasted. Use ⌊ ⌋ for bfr. This is the default in exam questions.
  • Spanned: a record may continue into the next block. No space is wasted, but reading one record may need two blocks.
  • Round down for "how many fit" (bfr), round up for "how many are needed" (blocks, log₂).

14.2Index Table Structure and Primary Indexing (Anchor Records) — Solved

🎓 Lecture topic (from outline)

Structure of an index

An index is itself a small, sorted file with two columns:
Index entry = < search key value, block pointer >
Because its entries are much smaller than full records, many more fit in a block, so the index occupies far fewer blocks than the data.

Primary index

Used when the data file is sorted on its primary key (an ordered, unique field).
  • One index entry per data block, not per record.
  • The key stored for each block is the key of the first record in that block, called the anchor record (block anchor).
  • To find key K: search the index for the last entry with key ≤ K, then read that one block.
SolvedSame file (3,000 blocks). The key is 9 bytes and a block pointer is 6 bytes. How many block accesses with a primary index?
Index entry size = 9 + 6 = 15 bytes.
Index bfr = ⌊1024 ÷ 15⌋ = 68 entries per block.
Index entries = one per data block = 3,000.
Index blocks = ⌈3,000 ÷ 68⌉ = 45 blocks.
Binary search on the index = ⌈log₂ 45⌉ = 6 accesses, + 1 to read the data block = 7 block accesses (down from 12 for binary search on the data file, and 1,500 for a linear scan).

14.3Single-Level vs Multi-Level Indexing

🎓 Lecture topic (from outline)

Single-level index

One index file over the data, searched by binary search. When the data is huge, the index itself can run to thousands of blocks, and binary search on it still costs many reads.

Multi-level index

The index is a sorted file, so we can build a primary index on the index. Keep adding levels until the top level fits in one block. A search then reads exactly one block per level, plus the data block. Like a big book with a short contents page that points to sections of the detailed index.
  • Fan-out (fo) = index entries per block (68 above). Each level is about fo times smaller than the one below.
  • Number of levels ≈ ⌈logfo(first-level entries)⌉.
  • Block accesses = number of levels + 1.
SolvedMake the primary index above multi-level (fo = 68).
Level 1: 3,000 entries → 45 blocks.
Level 2: 45 entries (one per level-1 block) → ⌈45 ÷ 68⌉ = 1 block. It fits in one block, so stop.
Levels = 2. Block accesses = 2 + 1 = 3 (down from 7 with a single-level index).
➕ Added for exam A static multi-level index is hard to keep balanced as rows are inserted and deleted. B-trees and B+ trees (chapter 15) are multi-level indexes that rebalance themselves automatically. That's what real databases use.

14.4Dense vs Sparse Index; Clustered Indexing

🎓 Lecture topic (from outline)

Dense index

One index entry for every search-key value (every record, if the key is unique). Works on any file, sorted or not. Bigger, but it can answer "does this value exist?" from the index alone.

Sparse index

Index entries for only some values, typically one per block (the anchor). Only possible when the data file is sorted on the search key, because you rely on the order to find records between anchors. Smaller and cheaper to maintain.

Clustered (clustering) index

Used when the data file is sorted on a non-key field, one with duplicates (e.g. records sorted by Dept, with many employees per department).
  • One index entry per distinct value of the field.
  • The pointer goes to the first block containing that value; the rest follow in order.
  • It's sparse: one entry per value, not per record.

⚠️ Exam trap A file can be physically sorted in only one order, so it can have at most one primary or clustering index (not both), but any number of secondary indexes.

14.5Secondary Indexing on Key and Non-Key Attributes

🎓 Lecture topic (from outline) A secondary index is built on a field the file is not sorted by. With no order to rely on, it must be dense.

On a key (unique) field

e.g. Aadhaar number in a file sorted by Roll. One entry per record, each pointing to the block (or record) holding it.

On a non-key field (duplicates)

e.g. City. Many records share each value, scattered across many blocks. Three ways to handle it:
  1. One entry per record, repeating the value (a dense index with duplicate keys).
  2. One entry per value with a variable-length list of pointers.
  3. One entry per value pointing to a separate block of record pointers (an extra level of indirection). This is the most common, because index entries stay fixed in size.
SolvedSame file (30,000 records, 3,000 blocks), secondary index on a unique 9-byte field with 6-byte pointers.
Index entries = one per record = 30,000. Index bfr = 68.
Index blocks = ⌈30,000 ÷ 68⌉ = 442 blocks (68 × 441 = 29,988, so one more block).
Binary search = ⌈log₂ 442⌉ = 9 (2⁹ = 512), + 1 data block = 10 block accesses, against an average of 1,500 for a linear scan (the file isn't sorted on this field, so binary search on the data isn't possible).
Made multi-level: 442 → ⌈442 ÷ 68⌉ = 7 → 1 block. 3 levels + 1 = 4 block accesses.

➕ Added for exam
  • Indexes speed up reads but slow down INSERT, UPDATE and DELETE, because every index must be updated too. They also take disk space.
  • In SQL: CREATE INDEX idx_city ON Student(City); and DROP INDEX idx_city;. Most DBMSs create an index on the primary key automatically.
  • Hashing is the alternative to an ordered index: it finds an exact key in about 1 block access, but it can't do range queries (BETWEEN, <, >).
🎯 IBPS exam alert Expect a numerical: compute bfr, blocks, index entries, index blocks, and block accesses (⌈log₂ index blocks⌉ + 1). Then theory: dense vs sparse, which index needs a sorted file, and how many primary/clustering/secondary indexes a file can have.

14.7Solved Exam QuestionsADDED

Q1Block size 512 bytes, record size 50 bytes, unspanned. Blocking factor?
Answer: 10 (⌊512 ÷ 50⌋).
Q210,000 records at a blocking factor of 10. Blocks needed? Block accesses for binary search?
Answer: 1,000 blocks; ⌈log₂ 1,000⌉ = 10 accesses.
Q3A primary index on a file of 1,000 blocks has how many entries?
Answer: 1,000, one per block (anchor record).
Q4Which index needs the data file to be sorted on the search key? (a) dense (b) sparse (c) secondary (d) all
Answer: (b) sparse.
Q5A secondary index on a key field is:
Answer: dense, one entry per record.
Q6How many clustering indexes can a file have?
Answer: at most one, and only if it has no primary index.
Q7A multi-level index has 3 levels. Block accesses to fetch a record?
Answer: 4 (one per level + the data block).
Q8Index entry = 10-byte key + 6-byte pointer, block size 2,048 bytes. Fan-out?
Answer: 128 (⌊2,048 ÷ 16⌋).

⚡ Rapid Revision

  • Index = book's back index: search key → block pointer. Cost is counted in block accesses.
  • bfr = ⌊block ÷ record⌋; blocks = ⌈records ÷ bfr⌉. 30,000 × 100 B, 1,024 B blocks → bfr 10, 3,000 blocks.
  • No index: linear = b/2 average (1,500); sorted file binary = ⌈log₂ b⌉ (12).
  • Primary index: file sorted on key, one entry per block (anchor record = first record of the block), sparse. 15-B entries → 68/block → 45 blocks → 6 + 1 = 7 accesses.
  • Multi-level: index on the index until the top fits in one block; accesses = levels + 1 (45 → 1 ⇒ 3 accesses). Leads to B/B+ trees.
  • Dense = entry per record, any file. Sparse = entry per block, sorted file only.
  • Clustering index: file sorted on a non-key field; one entry per distinct value → first block with it.
  • Secondary index: on an unsorted field, dense. Key: one entry per record (442 blocks → 10 accesses). Non-key: usually one entry per value → block of record pointers.
  • One primary or clustering index per file; many secondary.
  • ➕ Indexes speed reads, slow writes. Hashing: ~1 access for exact match, no range queries.
