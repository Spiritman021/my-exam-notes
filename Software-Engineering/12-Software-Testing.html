Chapter 12

Software Testing Fundamentals and Levels

Coding is done; now the bugs have to be found before the users find them. Testing is not a single step at the end. It happens at four levels, each matching a design level in the V-model from chapter 2: unit (one module), integration (modules together), system (the whole product) and acceptance (the client's sign-off). On top of these sit non-functional tests that ask not "does it work?" but "does it keep working under pressure?". Chapter 13 covers the techniques, white-box and black-box, used at these levels.

12.1Goal of Testing

🎓 From the lecture Testing comes after coding. Its goal is to find bugs using minimum cost and time.
➕ Added for exam Testing is the process of executing a program with the intent of finding errors (Glenford Myers). A good test case has a high probability of finding an as-yet-undiscovered error, and a successful test is one that finds one. The key terms:
TermMeaningExample
Error / mistakeA human action that produces a wrong resultThe developer types > instead of >=
Fault / defect / bugThe flaw in the code caused by the errorThe wrong condition sitting in the code
FailureVisible deviation from expected behaviour when the fault executesA student with exactly 35 marks is shown "Fail"
Chain: error → fault → failure. Not every fault causes a failure: the faulty line may never run.

12.2Verification vs Validation (Building a Car)

🎓 From the lecture Recall the two arms of the V-model. While a car is being built, each stage is checked as it goes: verification. When it is finished, someone drives it: validation.
VerificationValidation
Question"Are we building the product right?""Are we building the right product?"
WhenPhase by phase, earlyAfter the code is ready
Code executed?No: staticYes: dynamic
MethodsReviews, walkthroughs, inspections, desk checksWhite-box, black-box, user acceptance testing
Done byDevelopers, the QA teamThe testing team, users
AimPrevent errorsFind errors
Checks againstSpecifications, design documentsThe user's actual needs
⚠️ Exam trap The lecture puts some unit and integration testing under verification. In the strict textbook sense, anything that executes code is validation, and verification is purely static (reviews, inspections, walkthroughs). These definitions come from Boehm. The IEEE standard for verification and validation is IEEE 1012.

12.3Principles of Testing

🎓 From the lecture
  • Testing shows that bugs are present. Skipping it means a bad user experience and bad reviews.
  • Test early to save time, budget and cost.
  • Start with a proper plan (test cases and test design), not at random.
  • Test against user requirements first.
  • Defect clustering: concentrate where bug density is high.
  • Test both functional and non-functional requirements.
➕ Added for exam The seven principles of testing (ISTQB):
  1. Testing shows the presence of defects, not their absence. You can never prove software bug-free.
  2. Exhaustive testing is impossible. Test by risk and priority instead.
  3. Early testing saves time and money (shift-left).
  4. Defect clustering: most defects sit in a few modules (the Pareto 80/20 rule).
  5. Pesticide paradox: running the same tests repeatedly stops finding new bugs, so tests must be reviewed and refreshed.
  6. Testing is context-dependent: a banking app and a game are tested differently.
  7. Absence-of-errors fallacy: a bug-free system that doesn't meet the users' needs is still useless.
🎯 IBPS exam alert "Running the same set of tests repeatedly will eventually find no new defects" → pesticide paradox. "80% of defects are found in 20% of modules" → defect clustering.

12.4Unit Testing

🎓 From the lecture Test the software module by module, which is why it is also called module testing. It is early-phase testing.
➕ Added for exam Unit testing is normally done by the developer, mostly with white-box techniques (chapter 13). It checks the module's interface, local data structures, boundary conditions, independent paths and error-handling paths. Because a unit can't run on its own, it needs drivers and stubs (see 12.5). Typical tools: JUnit (Java), NUnit (.NET), pytest (Python).

12.5Integration Testing: Big Bang, Top-Down (Stubs), Bottom-Up (Drivers)

🎓 From the lecture Integration testing checks the interaction, connectivity, data flow and compatibility between modules that have already passed unit testing.
  • Non-incremental (big bang): join all modules at once and test. The problem is that you must wait until every module is ready, and when something fails it's hard to tell where.
  • Incremental, top-down: start from the high-level modules and add lower ones one by one. Lower modules that aren't ready yet are replaced by stubs, dummy programs that simulate the missing sub-modules.
  • Incremental, bottom-up: start from the low-level modules and work upward. Higher modules that aren't ready yet are replaced by drivers, dummy programs that simulate the caller.
Big bangTop-downBottom-up
OrderAll at onceHigh → lowLow → high
Dummy codeNoneStubsDrivers
StrengthNo dummy code neededA working skeleton early; design flaws found earlyLow-level utilities tested thoroughly; no stubs
WeaknessFaults hard to locate; must wait for everythingMany stubs; low-level bugs found lateNo working program until the end
➕ Added for exam Sandwich (hybrid) integration combines both: top-down from the top and bottom-up from the bottom, meeting at a middle layer. It uses both stubs and drivers.
⚠️ Exam trap Stub = called (replaces a module below; used in top-down). Driver = caller (replaces a module above; used in bottom-up). Memory aid: "Driver Drives from above; Stub Sits below."

12.6System Testing

🎓 From the lecture The whole car is ready: test it as a complete system, using only its inputs and outputs and ignoring its internals. It resembles black-box testing. The aim is to verify the overall functionality against the user requirements.
➕ Added for exam System testing is done by an independent test team in an environment close to production. It covers both functional and non-functional requirements. Pressman's system-test types:
  • Recovery testing: force the system to fail and check that it recovers.
  • Security testing: check its protection against penetration.
  • Stress testing: demand abnormal quantities of resources.
  • Performance testing: measure run-time performance.
  • Deployment (configuration) testing: check it on every target platform.

12.7Acceptance Testing: Alpha, Beta, UAT, Regulatory, Business

🎓 From the lecture The final testing phase, deciding whether the product is accepted.
TypeWho / whereFocusLecture example
AlphaIn-house developers and testers, in a controlled environmentTechnicalThe car maker's internal team tests the car on its own track
BetaReal end users, in an uncontrolled environmentUser experience, ease of useEnd users drive the car on open roads
User acceptance (UAT)The clientAre the client's original requirements met, and how fully?—
RegulatoryAgainst laws of the target marketLegal complianceA film banned in one country but allowed in another
BusinessAgainst business goalsMarket fit and sizeShark Tank: "Good product, but there's no market for it"
⚠️ Exam trap Alpha testing happens at the developer's site, with users or testers working under the developer's eye. Beta testing happens at the customer's site, without the developer present. Alpha comes before beta. A "beta version" is a release given to real users for feedback before the final launch.
➕ Added for exam Other acceptance types: Operational Acceptance Testing (OAT) checks operational readiness (backups, recovery, maintenance). Contract acceptance testing checks the criteria written into the contract. Two quick checks often confused:
  • Smoke testing: a shallow, wide test of the main functions on a new build, asking "does it even start?"
  • Sanity testing: a narrow, deep check of one fixed area after a small change.

12.8Non-Functional Testing: Performance, Load, Stress, Scalability (Five-Seater Car)

🎓 From the lecture Non-functional tests check how well the system works rather than what it does. The lecture's running example is a five-seater car.
  • Performance testing: measure lag, delay and throughput. Is it fast and responsive?
  • Load testing: seat five people in the five-seater. Test at the maximum load the system claims, and check that it still runs as efficiently as promised.
  • Stress testing: squeeze seven or eight people into the five-seater. Push beyond the limit with unrealistic load to see how and when it breaks.
  • Scalability testing: how easily does the system scale up and down as demand changes?
➕ Added for exam
TestQuestion it answers
VolumeDoes it cope with a huge amount of data (a table of 10 crore rows)?
Endurance / soakDoes it stay stable under normal load for a long time (memory leaks over 48 hours)?
SpikeDoes it survive a sudden burst of users (a sale or exam-results day)?
UsabilityCan real users perform tasks easily?
CompatibilityDoes it work across browsers, devices and operating systems?
RecoveryDoes it recover after a crash or power cut?
Common tools: JMeter and LoadRunner for performance and load testing.
⚠️ Exam trap Load testing stays within the expected maximum and checks that performance holds. Stress testing goes beyond it and checks that the system fails gracefully and recovers. Both are kinds of performance testing.

12.9Solved Exam QuestionsADDED

Q1"Are we building the product right?" refers to:
Answer: Verification. "Are we building the right product?" is validation.
Q2In top-down integration, the dummy modules that simulate lower-level modules are called:
Answer: Stubs. Drivers simulate higher-level callers in bottom-up integration.
Q3Testing done by end users at their own site, without the developer present, is:
Answer: Beta testing.
Q4Testing a system beyond its normal operational capacity to observe how it fails is:
Answer: Stress testing.
Q5Which testing principle says that repeating the same tests eventually stops finding new bugs?
Answer: Pesticide paradox.
Q6Arrange the testing levels in order:
Answer: Unit → Integration → System → Acceptance.

⚡ Rapid Revision

  • Goal: find bugs at minimum cost and time. Error (human) → fault (in code) → failure (visible).
  • Verification = building it right; static; reviews; prevents errors. Validation = building the right thing; dynamic; executes code; finds errors.
  • Principles: defects present (not absent), exhaustive testing impossible, test early, defect clustering (80/20), pesticide paradox, context-dependent, absence-of-errors fallacy.
  • Levels: Unit (module, developer) → Integration (big bang · top-down with stubs · bottom-up with drivers · sandwich) → System (whole, I/O only) → Acceptance.
  • Acceptance: alpha (developer's site, controlled) · beta (users' site, uncontrolled) · UAT · regulatory (banned film) · business (Shark Tank: no market).
  • Five-seater car: load = 5 people (up to the limit) · stress = 7–8 people (beyond it) · scalability = scale up and down. Also volume, soak, spike.
  • Smoke = wide and shallow on a new build; sanity = narrow and deep after a fix.
