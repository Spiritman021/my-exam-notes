Chapter 5

Requirement Analysis Tools

Gathered requirements arrive as a messy pile of notes, interview answers and wish lists. The analysis step (chapter 4) turns that pile into something precise by drawing it. A picture makes gaps and contradictions obvious in a way paragraphs never do. The lecture covers five tools, each showing a different side of the system: control flow (flowchart), data flow (DFD), data meaning (data dictionary), data relationships (ER diagram) and decision logic (decision table).

5.1Flowchart (Sum of Two Numbers; Pass/Fail Decision)

🎓 From the lecture A flowchart shows the flow of control: the order in which steps run and where decisions branch. The lecture's two examples:
  • Sum of two numbers: Start → read x, y → sum = x + y → print sum → End.
  • Pass/fail: a decision diamond "marks < 35?". Yes → "Not promoted"; No → "Promoted".

5.2Data Flow Diagram: Notation and Valid/Invalid Flows

🎓 From the lecture A DFD shows how data moves through the system: where it comes from, which processes transform it, and where it is stored.
ElementSymbolMeaning
ProcessCircle (bubble)A function that transforms input data into output data
External entity (terminator)RectangleA source or sink of data outside the system: a customer, a bank
Data storeTwo parallel lines (a box without its vertical sides)Data at rest: a file or database table
Data flowArrowData in motion, labelled with what it carries

Valid and invalid flows

A process must sit between any two non-process elements.
  • Valid: entity ↔ process, process ↔ data store, process → process.
  • Invalid: entity → entity, entity → data store (an outsider writing straight to the database is dangerous), data store → data store.
➕ Added for exam
  • A DFD is also called a bubble chart or process model.
  • The circle notation is Yourdon–DeMarco; Gane–Sarson notation uses rounded rectangles for processes and open-ended rectangles for data stores.
  • A process must have at least one input and one output:
    • a process with only inputs is a black hole;
    • a process with only outputs is a miracle;
    • a process whose inputs can't produce its outputs is a grey hole.
  • Name processes with a verb ("Generate bill"), and entities, stores and flows with nouns.
⚠️ Exam trap A DFD shows data flow, not control flow. It has no loops, decisions or sequence. "When" and "if" belong in flowcharts and decision tables. A DFD does not show the order in which processes run.

5.3DFD Levels (Level 0, 1, 2) — Food Ordering System Example

🎓 From the lecture
  • Level 0 (context diagram / overview): the whole system as one process, surrounded by its external entities.
  • Level 1: breaks that process into its major processes (1, 2, 3…) and shows the data stores.
  • Level 2: breaks one Level-1 process into sub-processes 1.1, 1.2, 1.3.
  • Level 3: goes further, to 1.1.1 and so on.
Worked example: Food Ordering System.
  • Level 0: entities Customer, Kitchen and Manager. The customer sends an order and receives a bill; the system sends a food order to the kitchen and a report to the manager.
  • Level 1: processes 1 Order Processing and 2 Generate Report, with data stores D1 Inventory and D2 Orders.
  • Level 2 (of process 1): 1.1 Receive Order, which sends the food order to the kitchen, and 1.2 Generate Bill, which sends the bill to the customer.
➕ Added for exam Balancing: the data flows entering and leaving a process at one level must match the flows of its child diagram at the next level. In the example, "order" in and "bill" out of process 1 must still appear around 1.1 and 1.2. The context diagram has exactly one process and normally no data stores. Each level shows more detail without changing the system's boundary.
⚠️ Exam trap "Level 0 DFD" and "context diagram" are the same thing. Level-1 processes are numbered 1, 2, 3; Level-2 processes are numbered 1.1, 1.2. Data stores appear from Level 1 onward.

5.4Data Dictionary (Marks Out of 100)

🎓 From the lecture A data dictionary is a list of every data item in the DFD with its full details, the "kundli" of each data item:
  • name and aliases (other names for it);
  • description;
  • range of values;
  • relationships with other items;
  • type and size.
Example: for an exam out of 100, the dictionary says marks is an integer from 0 to 100, so values like 105 or −5 are clearly invalid. It removes ambiguity by giving everyone standard terminology: whenever a term's meaning is unclear, look it up.
➕ Added for exam Standard data-dictionary notation (DeMarco):

The data dictionary is the repository that ties DFDs, ER diagrams and the SRS together. It is also called metadata, "data about data".

5.5ER Diagram (Student Studies in College)

🎓 From the lecture Covered briefly here; details belong to DBMS.
  • Entities (rectangles): Student, College.
  • Attributes (ellipses): name; roll no, the primary key, shown underlined; phone, multivalued, shown as a double ellipse; college id; address, composite, made of street + city.
  • Relationship (diamond): studies in.
  • Cardinality: 1:1, M:1 (many students, one college), M:N.
➕ Added for exam The ER model was proposed by Peter Chen (1976). More notation:
  • dashed ellipse = derived attribute (age from date of birth);
  • double rectangle = weak entity;
  • double diamond = identifying relationship;
  • double line = total participation.

5.6Decision Table / Cause-Effect Table (Login Example)

🎓 From the lecture A decision table (also called a cause-effect table) lays out if-then-else logic as a grid:
  • Conditions C1, C2, C3… (causes) in the top rows;
  • Actions A1, A2… (effects) in the bottom rows;
  • Rules R1, R2, R3… as columns. Each column says "if these conditions hold, take these actions". For example, if C1 and C3 are true, do A2.
Login example:
R1R2R3R4
C1: Username valid?FTFT
C2: Password valid?FFTT
Actions
A1: Show "Invalid"✓✓✓
A2: Log in (home page)✓
➕ Added for exam
  • With n independent yes/no conditions, a complete decision table has 2ⁿ rules: 2 conditions → 4 rules, 3 conditions → 8. Rules with the same actions can be merged using a "–" (don't care) entry.
  • The four parts of a decision table are condition stub, condition entries, action stub and action entries.
  • A decision tree shows the same logic as a branching tree, which is easier to read when there are few conditions.
  • Structured English writes it as IF-THEN-ELSE pseudo-text.
  • In testing (chapter 13), decision tables drive decision-table-based testing, and the cause-effect idea becomes the cause-effect graph.
🎯 IBPS exam alert "How many rules does a decision table with 4 binary conditions have?" → 2⁴ = 16. "Which tool is best for complex logic with many combinations of conditions?" → Decision table.

5.7Solved Exam QuestionsADDED

Q1In a DFD, a data store is represented by: (a) circle (b) rectangle (c) two parallel lines (d) diamond
Answer: (c) two parallel lines (open-ended box).
Q2Which of these is NOT a valid DFD flow? (a) Entity → Process (b) Process → Data store (c) Data store → Data store (d) Process → Process
Answer: (c). Data must pass through a process.
Q3A Level 0 DFD is also called:
Answer: the context diagram. It contains one process.
Q4A repository that stores the meaning, type, range and aliases of every data item is the:
Answer: data dictionary.
Q5A decision table has 3 binary conditions. How many rules does it have in full?
Answer: 2³ = 8.
Q6In an ER diagram, a multivalued attribute is shown by a:
Answer: double ellipse. The primary key is underlined; a derived attribute uses a dashed ellipse.

⚡ Rapid Revision

  • Flowchart = control flow. Oval start/end · parallelogram I/O · rectangle process · diamond decision.
  • DFD = data flow (no control). Circle = process · rectangle = external entity · two parallel lines = data store · arrow = data flow.
  • Invalid flows: entity→entity, entity→store, store→store. Black hole (inputs only), miracle (outputs only).
  • Levels: 0 = context (1 process) → 1 (major processes + stores) → 2 (1.1, 1.2) → 3 (1.1.1). Parent and child levels must balance.
  • Food ordering: Customer, Kitchen, Manager → 1 Order Processing, 2 Generate Report, D1 Inventory, D2 Orders → 1.1 Receive Order, 1.2 Generate Bill.
  • Data dictionary = "kundli" of each data item (name, aliases, description, range, type, size). Notation = + [|] {} ().
  • ER (Chen 1976): rectangle entity, ellipse attribute, diamond relationship; underline key, double ellipse multivalued.
  • Decision table = conditions × rules → actions; 2ⁿ rules for n binary conditions. Login: only valid + valid → log in.
