Chapter 13

White-Box and Black-Box Testing

Chapter 12 covered when to test (the levels). This chapter covers how to design the tests. There are two viewpoints. In white-box testing you can see the code and design tests to exercise its statements, branches and paths. In black-box testing you see only the inputs and outputs and design tests from the requirements. The two are complementary: white-box finds logic errors inside, and black-box finds missing or wrong behaviour as the user sees it.

13.1White-Box Testing (Transparent Glass of Water)

🎓 From the lecture Picture a transparent glass of dirty water. You can see the dirt inside, so you filter it out before drinking. White-box testing works the same way: the tester can see the code.
  • Also called glass-box, transparent, structural, clear-box testing.
  • Focuses on the internal structure of the code.
  • Used mainly at unit and integration level.
  • Needs programming-language knowledge.
The lecture also names some white-box tools, but the transcript garbles them (they appear to be SQLMap, NUnit and Veracode-type tools), so they are left out here.
➕ Added for exam White-box testing is done mostly by developers. Other names: logic-driven or code-based testing. Its weakness is that it cannot find missing functionality, because it only tests the code that exists. Typical tools: JUnit, NUnit (unit tests) and JaCoCo, gcov (coverage measurement).

13.2Statement, Branch and Path Coverage; Data-Flow Testing

🎓 From the lecture
TechniqueGoal
Statement coverageExecute every statement at least once.
Branch coverageTake every branch, conditional and unconditional, at least once (both the true and false outcome of each decision). Also look for invalid or redundant branches.
Data-flow testingTrack how data changes as it moves through the code. If x starts at 5 and ends up 50, trace exactly how. Look for redundant or invalid data use.
Path coverageExercise every path from start to end. Look for redundant paths or paths that can be optimised.
Example · how the criteria differ
void f(int a, int b) { if (a > 0) x = 1; // decision D1 if (b > 0) y = 1; // decision D2 }
  • Statement coverage: 1 test, (a = 1, b = 1), runs every statement.
  • Branch coverage: 2 tests, (1, 1) and (0, 0), give D1 and D2 both a true and a false outcome.
  • Path coverage: 4 tests, (1, 1), (1, 0), (0, 1), (0, 0), cover TT, TF, FT and FF.
➕ Added for exam Coverage criteria get stronger in this order: statement < branch (decision) < condition < multiple-condition < path. 100% branch coverage guarantees 100% statement coverage, but not the other way round. Full path coverage is often impossible for loops, so basis-path testing (13.2a) tests a manageable set of independent paths instead. Data-flow testing tracks def–use (DU) pairs: where a variable is defined and where that value is used.
⚠️ Exam trap "100% statement coverage implies 100% branch coverage" is false. An if with no else can have every statement executed while its false branch is never taken. "100% branch coverage implies 100% statement coverage" is true.

13.2aCyclomatic Complexity (McCabe)ADDED

➕ Added for exam Proposed by Thomas McCabe (1976). Cyclomatic complexity V(G) is the number of linearly independent paths through a program's control-flow graph. It equals the minimum number of test cases needed for basis-path testing, and it is also a measure of code complexity. Three equivalent formulas:
V(G) = E − N + 2P E = edges, N = nodes, P = connected components (1 for one program) V(G) = P + 1 P = number of predicate (decision) nodes V(G) = R R = number of regions in the planar flow graph (outside region included)
Guideline: V(G) ≤ 10 is fine; above about 10 the module should be split.
Worked example · GCD by subtraction
1 read x, y 2 while (x != y) 3 if (x > y) 4 x = x − y else 5 y = y − x 6 print x
Three independent paths, so a minimum of 3 test cases:
  • 1 → 2 → 6: x = y initially, e.g. (4, 4).
  • 1 → 2 → 3 → 4 → 2 → 6: x > y, e.g. (8, 4).
  • 1 → 2 → 3 → 5 → 2 → 6: x < y, e.g. (4, 8).
🎯 IBPS exam alert Cyclomatic complexity questions give either the code or the edge and node counts. "A flow graph has 10 edges and 8 nodes" → V(G) = 10 − 8 + 2 = 4. "A program has 3 if-statements and 1 while loop" → 4 predicates + 1 = 5. A switch with k cases counts as k − 1 predicates.

13.3Black-Box Testing (Brass Glass)

🎓 From the lecture Now picture a brass glass (peetal ka gilaas). You can't see inside, so you drink, and if it tastes dirty you spit it out. You judge only by the output.
  • Slogan: "don't poke into internal matters". Inputs and outputs only; internals are hidden.
  • Also called outer, external, behavioural or functional testing.
  • Little or no programming knowledge is needed.
  • Tools: Selenium and others (the other names are garbled in the transcript).

➕ Added for exam Grey-box testing mixes the two: the tester has partial knowledge of the internals (the database schema or architecture) but tests from the outside. It is common in integration and web-application testing.

13.4Cause-Effect Graph, Requirement-Based Testing and Boundary Value Analysis

🎓 From the lecture
  • Cause-effect graph: spitting the water out is the effect; dirt in the water is the cause. The graph maps input conditions (causes) to outputs (effects).
  • Requirement-based testing: check each feature against the user requirements.
  • Boundary value analysis (BVA): for a valid range of 1–99, test the boundaries 1 and 99 and the values just outside them, 0 and 100. Valid output is expected at the boundaries and an error just outside them.
➕ Added for exam

Why boundaries?

Programmers often slip on < vs <= (off-by-one errors), so defects cluster at the edges of ranges.

Counting BVA test cases (n input variables)

  • Normal BVA: min, min+, nominal, max−, max for each variable, with the other variables held at nominal → 4n + 1 tests.
  • Robust BVA: adds min− and max+ → 6n + 1.
  • Worst-case BVA: every combination of 5 values → 5ⁿ.

Equivalence class partitioning (ECP)

Divide the input domain into classes that the program should treat the same way, and test one value from each class. For the range 1–99 there are three classes: < 1 (invalid, e.g. −5), 1–99 (valid, e.g. 50) and > 99 (invalid, e.g. 150). ECP and BVA are usually used together.

Other black-box techniques

  • Decision-table testing (chapter 5): one test per rule.
  • State-transition testing: for systems whose behaviour depends on state, such as an ATM card blocked after 3 wrong PINs.
  • Error guessing: an experienced tester's intuition (empty input, division by zero).
  • Use-case testing.
⚠️ Exam trap For a single variable with range [1, 99], normal BVA gives 4(1) + 1 = 5 tests: 1, 2, 50, 98, 99. Robust BVA gives 7, adding 0 and 100. With two variables, normal BVA gives 4(2) + 1 = 9, not 10, because the all-nominal case is counted once.

13.5Regression Testing: Full vs Partial

🎓 From the lecture After a bug fix, update, enhancement or new feature, check that the existing core functions and behaviour still work unchanged. The new change must not break old features.
  • Full regression: re-test the whole system after the update.
  • Partial regression: re-test only the module or part that was updated, and what it affects.
➕ Added for exam Regression-test strategies: retest-all (full, expensive), regression test selection (only the tests affected by the change) and test-case prioritisation (run the most important first). Because regression suites run again and again, they are the prime candidates for test automation (Selenium, CI pipelines).
⚠️ Exam trap Re-testing (confirmation testing) runs the failed test again to confirm that a specific bug is fixed. Regression testing checks that the fix did not break anything else. Re-testing comes first, then regression.

13.6Solved Exam QuestionsADDED

Q1Which of these is a white-box technique? (a) Boundary value analysis (b) Equivalence partitioning (c) Basis path testing (d) Cause-effect graphing
Answer: (c) Basis path testing. The rest are black-box.
Q2A control-flow graph has 13 edges and 10 nodes. Find the cyclomatic complexity.
Answer: V(G) = 13 − 10 + 2 = 5.
Q3An input field accepts ages 18–60. Which values does BVA test?
Answer: 17, 18, 19, (nominal, e.g. 39), 59, 60, 61. The core boundary checks are 17, 18, 60, 61.
Q4Normal BVA test cases for a function with 3 input variables?
Answer: 4 × 3 + 1 = 13.
Q5Testing performed after a code change to ensure existing functionality is unaffected is:
Answer: Regression testing.
Q6Which coverage criterion is the strongest? (a) Statement (b) Branch (c) Path (d) Function
Answer: (c) Path.

⚡ Rapid Revision

  • White-box (transparent glass; also called glass, structural, clear-box): internal structure, needs code knowledge, unit and integration level, done by developers.
  • Coverage: statement < branch < condition < path. 100% branch ⇒ 100% statement (not the reverse). Data-flow = def–use tracking.
  • Cyclomatic complexity (McCabe 1976) = E − N + 2 = predicates + 1 = regions = number of independent paths = minimum basis-path tests. Keep it ≤ 10.
  • Black-box (brass glass; "don't poke into internal matters"): I/O only, based on requirements, no code knowledge.
  • Techniques: cause-effect graph (dirt → spit), requirement-based, BVA (1–99 → 0, 1, 99, 100; 4n + 1 normal, 6n + 1 robust, 5ⁿ worst-case), ECP (one value per class), decision table, state transition, error guessing.
  • Grey-box = partial knowledge of the internals.
  • Regression: after any change, old features must still work. Full = whole system; partial = changed part. Re-testing ≠ regression.
