Chapter 2

SDLC and Process Models

Every software project passes through the same broad stages: decide what to build, design it, build it, test it and ship it. The Software Development Life Cycle (SDLC) names those stages. A process model decides how you move through them: once in a straight line, in loops, in increments, or around a spiral. The lecture's refrain is that no model is perfect; each fits a certain project size and a certain level of clarity in the requirements.

2.1SDLC Phases

🎓 From the lecture
  1. Planning: communicate with the stakeholders, fix the scope, study market demand, and check feasibility (is the project realistic?).
  2. Defining: gather and analyse requirements. The output is the SRS (Software Requirement Specification).
  3. Designing: turn the SRS into a design document: the architecture and the modules.
  4. Building: write the code.
  5. Testing: unit, integration and system testing.
  6. Deployment: release to the client, then maintain. The cycle then repeats for the next version.
Many SDLC models exist. None is perfect, and each suits small, medium or large projects differently.
➕ Added for exam Pressman's generic process framework has five activities: Communication, Planning, Modeling, Construction, Deployment. "Modeling" covers analysis and design; "Construction" covers coding and testing. The lecture uses these names too when it describes the Waterfall model. Umbrella activities run across all phases: project tracking, risk management, quality assurance, configuration management, reviews and measurement.

2.2Waterfall Model (Real Waterfall; Class 1 to 12)

🎓 From the lecture Water in a waterfall only falls down; it never flows back up. In the same way, each phase finishes before the next begins, and you cannot go back. It is like passing class 1, then 2, up to 12, in strict order. The model is sequential and serial, with no parallel work. It is the base model: every later model borrows from it.

Phases: Feasibility study → Requirement gathering → Analysis → Design → Coding → Testing → Maintenance. Using framework names: communication → planning → modeling → construction → deployment → maintenance.

Disadvantages

  • No going back is the biggest flaw. An error made in an early phase carries into all later phases.
  • High risk and no room for experimentation. Requirements are fixed at the start.
  • The client sees the product only at the end. If they reject it, you start all over again.
Suits only small or very small projects with clear, stable requirements, and is rarely used in real projects today.
➕ Added for exam Also called the classical or linear sequential model. It is usually credited to Winston W. Royce (1970), who in fact described it as risky. Advantages: simple to understand and manage, each phase has clear deliverables and a review, and it works well when requirements are clear, fixed and well understood and the technology is known. Every phase ends with documentation, which makes it document-driven.

2.3Iterative Waterfall Model (Feedback Paths)

🎓 From the lecture The phases are the same as the waterfall, but each phase sends feedback to the phase before it, so a mistake found later can be corrected by going back.

Disadvantages

  • Requirements are locked after the feasibility study and still cannot change mid-way.
  • It is still serial: no parallel work.
Ideal for small projects and weaker for medium or large ones.
⚠️ Exam trap In the standard textbook version (Rajib Mall), feedback paths go from every phase to the phases before it except the feasibility study; there is no feedback into feasibility. "Iterative waterfall allows requirement changes at any time" is false. It allows correcting errors found later, not accepting new requirements freely.

2.4V-Shaped Model (Verification and Validation)

🎓 From the lecture One "V" for verification and one for validation. The model's emphasis is testing in every phase.
  • Left arm (verification), going down: requirement analysis → system design → architecture design → module design → coding at the bottom.
  • Right arm (validation), going up, each test level mapped to the design level opposite it:
    • unit testing ↔ module design
    • integration testing ↔ architecture design
    • system testing ↔ system design
    • user acceptance testing ↔ requirement analysis
It needs clear, fixed requirements, suits small and medium projects, is simple, and saves some time because test plans are written early.
➕ Added for exam The V-model is an extension of the waterfall. Test planning for each level starts alongside the matching design phase, so defects are caught early. It is a good fit for safety-critical systems (medical, aviation). Its weakness is the same as the waterfall's: it is rigid, offers no early prototype, and copes poorly with changing requirements. Verification vs validation is covered in detail in chapter 12.

2.5Prototyping Model (Unclear Requirements)

🎓 From the lecture Used when the client's requirements are unclear or fuzzy: the client can't say exactly what they want, but will know it when they see it.

Flow: rough requirements → quick design → build prototype → client evaluates → refine, repeated until the client accepts. After that the normal design → coding → testing → maintenance follows to build the real product.

Drawbacks: high development cost and time spent on repeated prototypes, which can cause delays. Suits small and medium projects.
➕ Added for exam
  • Throwaway (rapid) prototyping: the prototype is discarded once requirements are clear, and the real system is built from scratch.
  • Evolutionary prototyping: the prototype is refined step by step until it becomes the final system.
Advantages: users get involved early, missing functions are spotted early, and the risk of building the wrong system falls. A typical risk is that the client sees a working-looking prototype and expects the product to be "almost done".

2.6Incremental Model (House Room by Room)

🎓 From the lecture A house is built room by room and floor by floor; a wall is built brick by brick. Here the requirements are locked first (the SRS is in hand), and then the product is delivered in Build 1, Build 2 … Build N. Each build adds features or modules and goes through its own analysis → design → development → testing → implementation.

Can be used for medium and large projects. Time and cost can be high.

➕ Added for exam The first increment is usually the core product, delivering the basic requirements; later increments add supplementary features. Advantages: a working product early, easier testing and debugging of smaller pieces, and the client can give feedback after each build. It needs a good overall design so that increments fit together.

2.7Evolutionary Model (Iterative + Incremental)

🎓 From the lecture The evolutionary model combines iterative and incremental: the product grows build by build (incremental), and within each build there is feedback between phases (iterative).
  • Good risk analysis; changes are easy to accommodate.
  • Used for large, complex projects.
  • Cost is high.
⚠️ Exam trap Incremental = requirements fixed up front, delivered in parts. Evolutionary = requirements are allowed to evolve as the product grows, with feedback driving each new version. Spiral and prototyping are both counted as evolutionary process models in Pressman.

2.8Spiral Model (Four Quadrants, Risk Analysis)

🎓 From the lecture Each loop of the spiral passes through four quadrants:
  1. Determine objectives, the scope and alternative feasible solutions.
  2. Identify and resolve risks. This is the model's key selling point.
  3. Develop and test the next version of the product.
  4. Review with the client, take feedback, and plan the next loop.
Cost is directly proportional to the radius of the spiral: every loop outward costs more. It suits large, complex, high-risk projects, and its strength is risk management.
➕ Added for exam
  • Proposed by Barry Boehm (1986).
  • Called a meta-model because it can contain other models: a single loop behaves like the waterfall, and the risk-reduction step often uses prototyping.
  • The radial dimension is cumulative cost; the angular dimension is progress through each loop.
  • The number of loops is not fixed; it depends on the risk.
  • Drawbacks: expensive, needs risk-assessment expertise, and is overkill for small projects.
🎯 IBPS exam alert "Which model is best for high-risk projects?" → Spiral. "Which model emphasises risk analysis?" → Spiral. "Which is a meta-model?" → Spiral.

2.9Unified Process

🎓 From the lecture
PhaseWhat happens
InceptionCommunication with the client, basic planning, initial requirements, scope and feasibility.
ElaborationDetailed planning, workflow and estimates; modeling and design (SRS → SDD).
ConstructionCoding plus some testing.
TransitionDeploy and release to the customer in increments.
ProductionSoftware increments in use: feedback, further iterations, monitoring and support.
➕ Added for exam The Unified Process comes from Jacobson, Booch and Rumbaugh, the creators of UML. Its three defining traits: use-case driven, architecture-centric, and iterative and incremental. IBM's commercial version, RUP (Rational Unified Process), has only four phases: Inception, Elaboration, Construction, Transition. Pressman adds Production as a fifth phase.
⚠️ Exam trap "How many phases does RUP have?" → 4 (Production is not one of them). If the question says "Unified Process (Pressman)", five phases including Production is accepted. The order is always I-E-C-T.

2.10RAD Model and Choosing a ModelADDED

➕ Added for exam RAD (Rapid Application Development) is a high-speed incremental model that uses component reuse and parallel teams to deliver in a very short cycle (typically 60–90 days). Its phases are business modeling, data modeling, process modeling, application generation, and testing and turnover. It needs well-understood requirements, a project that can be modularised, and enough skilled people for several teams. It is unsuitable for high-technical-risk projects. Big Bang is the model with no formal process: all resources go into coding and the product appears at once. It is only fit for tiny or academic projects.

2.11Solved Exam QuestionsADDED

Q1Which model is most suitable when the customer's requirements are not clear? (a) Waterfall (b) V-model (c) Prototyping (d) RAD
Answer: (c) Prototyping.
Q2The spiral model was proposed by: (a) Royce (b) Boehm (c) Brooks (d) Jacobson
Answer: (b) Barry Boehm, 1986.
Q3In the V-model, integration testing corresponds to which design phase?
Answer: Architecture (high-level) design. Unit ↔ module design, system ↔ system design, acceptance ↔ requirements.
Q4In the spiral model, the radius of the spiral represents:
Answer: Cumulative cost. The angular dimension represents progress.
Q5Which phase of RUP establishes the architecture baseline? (a) Inception (b) Elaboration (c) Construction (d) Transition
Answer: (b) Elaboration.
Q6Which model delivers a fully functional system in a very short time (60–90 days) using component reuse?
Answer: RAD.

⚡ Rapid Revision

  • SDLC (lecture): Planning → Defining (SRS) → Designing → Building → Testing → Deployment. Pressman's framework: communication, planning, modeling, construction, deployment.
  • Waterfall: sequential, no going back, base model (Royce 1970). Clear requirements, small projects.
  • Iterative waterfall: feedback to earlier phases (not to feasibility). Requirements still locked.
  • V-model: test level mirrors design level. Unit↔module, integration↔architecture, system↔system, acceptance↔requirements.
  • Prototyping: unclear requirements, loop until the client accepts. Throwaway vs evolutionary prototyping.
  • Incremental: fixed requirements, Build 1 … N, first build = core product.
  • Evolutionary = iterative + incremental, for large projects with changing requirements.
  • Spiral (Boehm 1986): 4 quadrants (objectives, risk, develop, review/plan). Radius = cost. Meta-model.
  • Unified Process: Inception, Elaboration, Construction, Transition (+ Production). RUP has 4 phases. Use-case driven, architecture-centric.
  • RAD: 60–90 days, component reuse, parallel teams.
