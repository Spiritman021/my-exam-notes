Chapter 10

Project Estimation and Resource Management

Before a single line of code is written, the client wants to know how much the project will cost and when it will be ready. Answering that is estimation, done during the planning phase. Everything hangs on one number, the size of the software. From size you derive effort, from effort the duration and team size, and from those the cost. This chapter covers how size is measured and how estimates are made. Chapter 11 turns it into formulas with COCOMO.

10.1Project Estimation in the Planning Phase (Size, Cost, Duration, Effort)

🎓 From the lecture During planning, before development starts, the team estimates four things:
  • Size: how big the software is.
  • Effort: how much work it needs.
  • Duration: how long it will take.
  • Cost: how much money it needs.
The more accurate the estimates, the better the project is completed and managed.
➕ Added for exam Estimation is uncertain by nature. Barry Boehm's cone of uncertainty shows that early estimates can be off by a factor of 4 in either direction, and the range narrows as the project proceeds. Good practice is to estimate with more than one technique, re-estimate as you learn more, and use historical data from past projects.

10.2Size Metrics: LOC and Function Points

🎓 From the lecture Project size is measured in two main ways:
  • Lines of code (LOC), or thousands of lines (KLOC). This is a direct count of the source code.
  • Function points (FP). This is an indirect measure, based on the functionality the software provides.
COCOMO (chapter 11) uses LOC.

➕ Added for exam Function Point Analysis was introduced by Allan Albrecht at IBM (1979). It counts five components:
ComponentMeaningSimpleAverageComplex
EI: External InputsInput screens or forms that update data346
EO: External OutputsReports and messages with derived data457
EQ: External InquiriesInput–output pairs that retrieve data without processing it346
ILF: Internal Logical FilesData groups maintained inside the system71015
EIF: External Interface FilesData referenced from other systems5710
UFP = Σ (count × weight) (Unadjusted Function Points) VAF = 0.65 + 0.01 × Σ Fi (Fi = 14 general system characteristics, each rated 0–5) FP = UFP × VAF (VAF ranges 0.65 to 1.35)
The 14 general system characteristics include data communications, distributed processing, performance, heavily used configuration, transaction rate, online data entry, end-user efficiency, online update, complex processing, reusability, installation ease, operational ease, multiple sites, and facilitating change.
Worked example · function points Counts, all of average complexity: EI = 24, EO = 46, EQ = 8, ILF = 4, EIF = 2. All 14 characteristics are rated 3 (average).
UFP = 24×4 + 46×5 + 8×4 + 4×10 + 2×7 = 96 + 230 + 32 + 40 + 14 = 412 Σ Fi = 14 × 3 = 42 VAF = 0.65 + 0.01 × 42 = 1.07 FP = 412 × 1.07 ≈ 440.84
If the team's historical productivity is 10 FP per person-month, effort ≈ 440.84 / 10 ≈ 44 person-months.
⚠️ Exam trap The VAF constant is 0.65 and the multiplier is 0.01. With every Fi = 0, VAF = 0.65; with every Fi = 5, VAF = 0.65 + 0.70 = 1.35. So the adjustment can change the UFP by at most ±35%. The highest weight in the table belongs to the ILF (15 for complex).

10.3Cost Estimation Factors

🎓 From the lecture Cost depends on:
  • software and hardware size and requirements;
  • tools and licences;
  • the salaries of skilled staff;
  • travel and communication;
  • training and support.
Time and effort estimation lead into COCOMO in three forms: basic, intermediate and complete (chapter 11).
➕ Added for exam Effort cost (the salaries of the people working on the project) is usually the largest component of software cost. Hardware, software, travel and training are often smaller. Overheads such as office space, power, networking and HR are added on top of salaries.

10.4Resource Management: Advance Allocation, On-Demand Allocation, Reuse

🎓 From the lecture Resources are human resources (technical and support staff), tools, software libraries and hardware. The job is to balance what is available against what the project demands. Three approaches:
  1. Advance allocation: work out beforehand which resources each phase or stage needs, and make them available in time.
  2. On-demand allocation: allocate a resource when it is needed, and deallocate it as soon as it is no longer needed, so someone else can use it.
  3. Reuse: like reusing pages from a senior's assignment that was already checked and approved. Reuse design components, code and test cases, but only when they are compatible. Reuse lowers effort, cost and time.
➕ Added for exam Pressman pictures project resources as a pyramid: people at the top (the most important resource), reusable software components in the middle, and the environment (hardware and software tools) at the base. Reusable components are classified as:
  • off-the-shelf (ready to use, from third parties or past projects);
  • full-experience (needs little modification);
  • partial-experience (needs substantial modification);
  • new (built from scratch).

10.5Estimation Techniques: Empirical, Heuristic, Analytical

🎓 From the lecture
TechniqueHow it worksExamples
EmpiricalThe most primitive form: an educated guess from experience of similar past projects. Also called common-sense estimation.Expert judgement; Delphi (group consensus, chapter 4)
HeuristicUses mathematical equations relating project parameters: estimate the independent parameter (size) first, then compute the dependent ones (effort, time).COCOMO (chapter 11)
AnalyticalNamed in the lecture but not covered.—
➕ Added for exam Analytical estimation starts from basic assumptions about the problem and derives results scientifically. The standard example is Halstead's Software Science (1977), which works from counts of operators and operands in the code:
n1 = distinct operators N1 = total operators n2 = distinct operands N2 = total operands Vocabulary n = n1 + n2 Length N = N1 + N2 Est. length N̂ = n1·log₂n1 + n2·log₂n2 Volume V = N · log₂ n (bits) Difficulty D = (n1 / 2) · (N2 / n2) Effort E = D · V
Other estimation approaches:
  • Decomposition: estimate each module or function separately and add the results.
  • Analogy: compare with a similar finished project.
  • Putnam's SLIM model: based on the Rayleigh curve of staffing over time.
  • Planning poker: Agile teams use it to size stories in story points.
🎯 IBPS exam alert Common one-liners:
  • "Delphi is a type of?" → empirical estimation.
  • "COCOMO is?" → heuristic.
  • "Halstead's software science is?" → analytical.
  • "Function points were proposed by?" → Albrecht.
  • "Which size measure is language-independent?" → FP.

10.6Solved Exam QuestionsADDED

Q1Function point analysis does NOT count: (a) external inputs (b) internal logical files (c) lines of code (d) external inquiries
Answer: (c) lines of code.
Q2UFP = 300 and the sum of the 14 complexity adjustment values is 30. Find FP.
Answer: VAF = 0.65 + 0.01 × 30 = 0.95; FP = 300 × 0.95 = 285.
Q3The maximum value of the VAF is:
Answer: 1.35 (all 14 factors rated 5: 0.65 + 0.70).
Q4Expert judgement and Delphi belong to which category of estimation?
Answer: Empirical.
Q5Which is the largest cost component in most software projects?
Answer: Effort (staff salaries).

⚡ Rapid Revision

  • Estimate in planning: size → effort → duration → cost. More accurate estimates mean better management.
  • LOC/KLOC = direct, language-dependent. FP = indirect, language-independent (Albrecht, IBM 1979).
  • FP components and average weights: EI 4 · EO 5 · EQ 4 · ILF 10 · EIF 7. FP = UFP × (0.65 + 0.01 ΣFi), 14 factors rated 0–5, VAF from 0.65 to 1.35.
  • Cost factors: size, tools and licences, salaries (the largest), travel, communication, training, support.
  • Resources: people, tools, libraries, hardware. Allocate in advance, on demand (and deallocate), or reuse (the senior's assignment).
  • Techniques: empirical (expert judgement, Delphi) · heuristic (COCOMO) · analytical (Halstead: n = n1 + n2, N = N1 + N2, V = N log₂ n).
