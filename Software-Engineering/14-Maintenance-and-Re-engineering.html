Chapter 14

Software Maintenance and Re-engineering

Deployment is not the end of a software product's life; it is the start of the longest phase. Users find bugs, operating systems change, competitors add features, and attackers find holes. All the work done after release is maintenance, and it consumes most of the total lifetime effort, which is why chapter 1 called "the job is done once the program works" a myth. When maintenance alone is not enough, the software is re-engineered.

14.1Software Maintenance (App Update Notes)

🎓 From the lecture Open the Play Store and read any app's update notes: "Bug fixes, performance improvements, now more lightweight." That is maintenance.
  • It starts once the software is deployed and in use.
  • It takes the majority of the SDLC's time and effort.
  • It covers updates, upgrades, improvements, enhancements and bug fixes.
Software maintenance (IEEE 1219 / ISO 14764): modifying a software product after delivery to correct faults, improve performance or other attributes, or adapt it to a changed environment.

14.2Types: Corrective, Perfective, Adaptive, Preventive

🎓 From the lecture
TypeWhat it doesLecture's line
CorrectiveFixes bugs reported by users; removes lag and delaySomething is broken, so fix it
PerfectiveImproves performance and efficiency even when the software already works, from 80% towards perfect. Adds or refines features users ask for."Perfection is a myth", so this never stops
AdaptiveAdapts to new technology and environments: new OS versions, hardware, platforms, or AI and data-science featuresThe world changed, so keep up
PreventiveSecurity patches and changes that stop future problems before they happen"Prevention is better than cure"
⚠️ Exam trap
  • The largest share of maintenance effort is perfective (about 50%), not corrective. Bug fixing is only about a fifth.
  • Moving an app to a new operating system or database is adaptive, not perfective.
  • In textbooks, preventive maintenance mainly means improving maintainability to stop future failures: refactoring, updating documentation, restructuring. The lecture's security-patch example fits this too.
  • Some books call the adaptive, perfective and preventive types together "enhancement" and treat corrective as "repair".

14.3Software Re-engineering (Melody: Something More)

🎓 From the lecture Remember the Melody toffee ad: "Melody itni chocolaty kyun hai?" It's still a chocolate, but something more. Re-engineering is likewise something more than maintenance: you examine and rework existing software to improve its performance and efficiency substantially, without throwing it away.
➕ Added for exam Re-engineering is applied to legacy systems: old software that is still business-critical but hard to maintain because of outdated technology, poor structure or missing documentation. Re-engineering is cheaper and less risky than rewriting from scratch, because the existing system already encodes years of business rules.

14.4Reverse Engineering, Restructuring/Refactoring and Forward Engineering

🎓 From the lecture Re-engineering has three parts:
  1. Reverse engineering: go backwards from the code to modules and components, then to the design, then to the requirements. You recover what the system does and how it was built.
  2. Restructuring / refactoring: keep the core functions intact, but reorganise the code to be more optimal and understandable. Update the documents too (SRS, SDD).
  3. Forward engineering: follow the normal SDLC for the new or improved requirements, building the improved system.
➕ Added for exam Pressman's software re-engineering process model is a cycle of six activities:
  1. Inventory analysis: list all applications and rank them for re-engineering.
  2. Document restructuring.
  3. Reverse engineering.
  4. Code restructuring.
  5. Data restructuring.
  6. Forward engineering.
Reverse engineering recovers information at rising levels of abstraction: procedural (code), program and data structures, the object/data-flow model, and the ER model. Its completeness is how much detail is recovered at each level.
⚠️ Exam trap
  • Reverse engineering does not change the system; it only analyses it to recover design and specifications.
  • Refactoring (Martin Fowler) changes the internal structure without changing external behaviour.
  • Forward engineering is the normal direction, from requirements to code.
  • So: reverse = understand; restructure = clean up; forward = rebuild.

14.5Maintenance Cost, Lehman's Laws and Configuration ManagementADDED

➕ Added for exam

How much maintenance costs

Maintenance typically accounts for 60–80% of total lifetime cost (the lecture said 50–60% of effort). Boehm's Annual Change Traffic (ACT) model estimates it:
ACT = (KLOC added + KLOC deleted) / total KLOC (fraction changed per year) Annual maintenance cost = ACT × development cost
Worked example · ACT A 100 KLOC system cost ₹80 lakh to develop. Each year about 10 KLOC are added and 5 KLOC deleted.
ACT = (10 + 5) / 100 = 0.15 Cost = 0.15 × 80 lakh = ₹12 lakh per year
➕ Added for exam

Lehman's laws of software evolution

The key laws:
  • Continuing change: a program in real use must keep changing or it becomes progressively less useful.
  • Increasing complexity: as it changes, its structure degrades unless work is done to prevent it. This is the "deterioration" of chapter 1.
  • Continuing growth: functionality must keep growing to keep users satisfied.
  • Declining quality: quality appears to decline unless it is actively maintained.

Maintenance process models

  • Quick-fix: patch the code first, update documents later or never.
  • Iterative enhancement: analyse, classify changes, redesign and implement in cycles.
  • Reuse-oriented: rebuild from reusable components.

Software Configuration Management (SCM)

SCM controls change across versions:
  • Configuration items (code, documents, data) are placed under control.
  • A baseline is an approved, frozen version that can only change through formal change control, approved by a Change Control Board (CCB).
  • Version control (Git, SVN) tracks every revision.
  • Configuration audits and status accounting report on what changed.
🎯 IBPS exam alert Common one-liners:
  • "Which maintenance type takes the most effort?" → perfective.
  • "Modifying software to run on a new OS?" → adaptive.
  • "Process of analysing a system to recover its design?" → reverse engineering.
  • "An approved work product that can be changed only through formal change control?" → baseline.

14.6Solved Exam QuestionsADDED

Q1Fixing a bug reported by a customer after release is: (a) adaptive (b) perfective (c) corrective (d) preventive
Answer: (c) Corrective.
Q2Adding a feature requested by users to an already working system is:
Answer: Perfective maintenance.
Q3Changing the structure of code without changing its external behaviour is called:
Answer: Refactoring (restructuring).
Q4A system's development cost was ₹2 crore and its annual change traffic is 10%. Estimate the annual maintenance cost.
Answer: 0.10 × 2 crore = ₹20 lakh.
Q5Which activity derives the design and specification from existing source code?
Answer: Reverse engineering.

⚡ Rapid Revision

  • Maintenance = everything after deployment ("bug fixes, performance improvements"). It is the largest share of lifetime effort and cost (60–80%).
  • Corrective = fix bugs · Perfective = improve or enhance (≈50%, the largest; "perfection is a myth") · Adaptive = new environment or technology · Preventive = stop future problems ("prevention is better than cure").
  • Re-engineering = "something more" than maintenance (Melody), applied to legacy systems.
  • Reverse (code → design → requirements, analysis only) → restructure / refactor (same behaviour, cleaner code) → forward (normal SDLC).
  • Pressman's cycle: inventory analysis, document restructuring, reverse engineering, code restructuring, data restructuring, forward engineering.
  • ACT: annual maintenance cost = ACT × development cost.
  • Lehman: continuing change, increasing complexity. SCM: baseline, change control (CCB), version control.
