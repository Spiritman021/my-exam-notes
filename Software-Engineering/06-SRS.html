Chapter 6

Software Requirement Specification (SRS)

Everything gathered in chapter 4 and cleaned up in chapter 5 ends up in one document: the SRS. It is the contract between the client and the development team. The client signs off on it, the designers design from it, and the testers test against it. It says what the system must do, not how it will do it.

6.1IEEE 830 Standard and SRS Structure

🎓 From the lecture Students working under different project guides each end up with a different report format. That is fine for college, but not for industry. A single globally accepted standard, IEEE 830, gives every SRS clarity, completeness, consistency and uniformity.

Sections named in the lecture:

  1. Introduction
  2. Overall description
  3. Specific requirements
  4. Change / update management
  5. Document approval
➕ Added for exam The actual IEEE 830-1998 template:
SectionContents
1. Introduction1.1 Purpose · 1.2 Scope · 1.3 Definitions, acronyms and abbreviations · 1.4 References · 1.5 Overview
2. Overall description2.1 Product perspective · 2.2 Product functions · 2.3 User characteristics · 2.4 Constraints · 2.5 Assumptions and dependencies
3. Specific requirementsExternal interfaces (user, hardware, software, communication), functional requirements, performance requirements, design constraints, software system attributes (reliability, availability, security, maintainability, portability), other requirements
Supporting informationAppendices, index
IEEE 830 was superseded in 2011 by ISO/IEC/IEEE 29148 (requirements engineering), but exams still quote IEEE 830.
🎯 IBPS exam alert "IEEE standard for SRS?" → IEEE 830. Related standards that also come up: IEEE 829 (test documentation), IEEE 1016 (software design descriptions), IEEE 1012 (verification and validation), IEEE 730 (software quality assurance plans).

6.2Requirement Review (Re-checking the Exam Paper)

🎓 From the lecture The review is the "final call" before sign-off. In an exam, you use the last 10–15 minutes to re-check your answer sheet and catch silly mistakes. In the same way, the team and the client read through the SRS one last time to find and correct mistakes. It is technically optional, but it is very good practice.
➕ Added for exam Formally this is requirements validation: checking that the SRS describes the system the customer actually wants. Techniques: requirements reviews (formal or informal walkthroughs and inspections), prototyping (show a mock-up to the client), test-case generation (if you can't write a test for a requirement, it isn't verifiable) and consistency checks, often supported by tools. Validation checks completeness, consistency, realism, verifiability and validity.

6.3Functional vs Non-Functional Requirements and Goals of Implementation

🎓 From the lecture An SRS has three kinds of content:
  • Functional requirements: the input → output transformations, the features the system must provide. They are mandatory and come directly from user requirements.
  • Non-functional requirements: desired properties or characteristics of the system rather than features: usability, maintainability, scalability and so on. They improve the user experience.
  • Goals of Implementation (GOI): guidelines for building the software so that likely future goals (5–10 years ahead) are partly provided for already, making later versions and updates easier.
FunctionalNon-functional
DescribesWhat the system doesHow well it does it (quality, constraints)
Example (banking app)Transfer money; show statement; generate OTPRespond in < 2 s; 99.9% uptime; AES-256 encryption; handle 10,000 concurrent users
If missingThe feature doesn't existThe system works but is slow, unsafe or hard to use
Tested byFunctional testing (black-box)Performance, load, security and usability testing
➕ Added for exam Sommerville classifies non-functional requirements as:
  • Product requirements: performance, reliability, usability, space, portability.
  • Organisational requirements: delivery, implementation and process standards.
  • External requirements: legal, ethical and interoperability requirements.
Non-functional requirements are often grouped under the label "-ilities": scalability, availability, maintainability and so on. A third category in some books is domain requirements, which come from the application domain (banking regulations, medical standards).
⚠️ Exam trap The lecture calls non-functional requirements "desired, not mandatory". In practice many are hard constraints: a bank system that violates a security or response-time requirement fails acceptance just as surely as one with a missing feature. Treat non-functional requirements as part of the contract. Also, "The system shall allow the user to log in" is functional, but "The login must complete within 3 seconds" is non-functional (performance).

6.4Characteristics of a Good SRS

🎓 From the lecture
  • Complete: nothing is missing.
  • Consistent: no requirement contradicts another.
  • Unambiguous: each requirement has only one meaning.
  • Verifiable: each requirement can be checked or tested.
  • Relevant: no irrelevant information.
  • Understandable and readable: clear, grammatically correct language.
➕ Added for exam IEEE 830 lists eight characteristics of a good SRS: Correct, Unambiguous, Complete, Consistent, Ranked for importance and/or stability, Verifiable, Modifiable, Traceable.
  • Ranked: each requirement is tagged by priority (essential, conditional, optional) and by how likely it is to change.
  • Modifiable: the structure lets changes be made easily and consistently, with no redundancy.
  • Traceable: the origin of each requirement is clear (backward traceability), and each one can be referenced by later design, code and tests (forward traceability).
An SRS should state what, not how: it treats the system as a black box and leaves design decisions to the SDD.
⚠️ Exam trap "The system should be user-friendly" or "respond quickly" is not verifiable: there is no way to test it. A verifiable version is "a new user completes registration in under 2 minutes without help" or "95% of searches return within 1 second".

6.5Consequences of Not Having an SRS

🎓 From the lecture
  • The wrong system gets developed.
  • There are doubts at every step: "What exactly did the client mean here?"
  • The overall flow of the system is hard to understand.
  • Time and budget are wasted on rework.
➕ Added for exam Who uses the SRS: customers (to confirm their needs are captured), managers (to plan, bid and estimate cost and schedule), developers (to know what to build), testers (to derive test cases), and maintenance engineers (to understand the system later). The SRS is also the base for user acceptance testing and for resolving contract disputes.

6.6Solved Exam QuestionsADDED

Q1The IEEE standard for software requirement specifications is: (a) IEEE 829 (b) IEEE 830 (c) IEEE 1016 (d) IEEE 802
Answer: (b) IEEE 830. 829 is test documentation, 1016 is design descriptions, 802 is LAN.
Q2"The system shall generate a monthly sales report." This is a:
Answer: functional requirement.
Q3"The system shall be available 99.95% of the time." This is a:
Answer: non-functional requirement (availability).
Q4An SRS should specify: (a) how the system will be built (b) what the system must do (c) the source code (d) the test results
Answer: (b).
Q5Which property means each requirement can be linked back to its source and forward to design and tests?
Answer: Traceability.

⚡ Rapid Revision

  • SRS = the "what" document and the client–developer contract. Standard: IEEE 830 (now ISO/IEC/IEEE 29148).
  • IEEE 830 layout: Introduction (purpose, scope, definitions, references, overview) → Overall description (perspective, functions, users, constraints, assumptions) → Specific requirements → appendices.
  • Review = re-check the exam paper in the last 10 minutes; formally, requirements validation.
  • Functional = what (features, I/O). Non-functional = how well (performance, security, usability…). GOI = provisions for future goals.
  • Good SRS (IEEE 830's 8): correct, unambiguous, complete, consistent, ranked, verifiable, modifiable, traceable.
  • No SRS → wrong system, constant doubts, confusing flow, wasted time and money.
  • IEEE numbers: 830 SRS · 829 test docs · 1016 design · 1012 V&V · 730 SQA.
