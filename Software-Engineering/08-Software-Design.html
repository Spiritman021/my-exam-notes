Chapter 8

Software Design

The SRS says what the system must do. Design decides how: which parts the system is made of, how they talk to each other and how each part works inside. The lecture splits design into three levels, zooming in from the outside. Interface design treats the system as a closed box. Architectural design opens the box to show its components. Detailed design opens each component.

8.1Design Phase Input/Output: SRS to SDD

🎓 From the lecture
  • Input: the SRS document.
  • Output: the Software Design Document (SDD).
  • The SDD covers three kinds of design: interface, architectural and detailed.
➕ Added for exam The IEEE standard for design documents is IEEE 1016 (Software Design Descriptions). In industry the design is usually split into HLD (High-Level Design), which covers the system architecture, modules and their interfaces and is roughly the lecture's interface plus architectural design, and LLD (Low-Level Design), which covers the internal logic, algorithms, data structures and class details of each module and is the lecture's detailed design.

8.2Characteristics of a Good Design Document

🎓 From the lecture
  • Covers all the client's requirements in the SRS.
  • Is free from conflict, ambiguity and incompleteness.
  • Explains every feature, both functional and non-functional, clearly, using clear terminology.
➕ Added for exam Textbooks add: a good design is correct (implements the SRS), understandable, efficient, maintainable, and has high cohesion and low coupling (chapter 9). It should be traceable back to the requirements and should not reinvent the wheel: reuse existing components and patterns where possible.

8.3Interface Design (System as a Black Box)

🎓 From the lecture Interface design shows the interaction between the system and its environment: users, other systems and devices. The system is treated as a black box. Only its inputs and outputs matter; its internals are ignored.

8.4Architectural Design (Components and Their Interaction)

🎓 From the lecture Architectural design goes inside the system and shows its major components, the responsibility of each, the interfaces between them and how they interact, much like a microprocessor architecture diagram shows the ALU, registers and control unit. The internals of each component are still ignored.

8.5Detailed Design (Algorithms and Data Structures)

🎓 From the lecture The innermost level: the internal elements of each major component. It includes the algorithms, data structures and exactly how each component works.

8.6All Three Designs Together (Hostage Rescue Analogy)

🎓 From the lecture A rescue team must free hostages held inside a house. It needs all three levels of information:
Design levelRescue-team information
Interface designThe surroundings of the house and the ways in and out: a secret path or pipeline leading inside. Only the outside matters.
Architectural designThe blueprint of the house: where the rooms, kitchen, hall and doors are and how they connect.
Detailed designWhat is inside each room: furniture, a bat, a table, anything the team can use to deal with the attackers.

8.7Top-Down vs Bottom-Up Design Approach

🎓 From the lecture

Top-down: divide and conquer (decomposition)

To pass 40-plus engineering subjects, split them into 4 years, each year into 2 semesters, and each subject into 6 units. Then tackle one unit at a time. In design, start from the high-level features and decompose them into lower-level ones.
  • The problem statement must be clear from the start.
  • Suits small and medium projects.

Bottom-up: composition

The night before the exam, you study unit 1, unit 2 … unit 6, and together they make up the whole subject. In design, build and solve the low-level modules first, then combine them upward into the full system.
  • A full understanding of the problem is not needed at the start.
Top-downBottom-up
DirectionSystem → subsystems → modulesModules → subsystems → system
TechniqueDecomposition, stepwise refinementComposition, reuse
NeedsClear problem statement up frontExisting or well-understood low-level parts
Typical forStructured / function-oriented designObject-oriented design, reusing libraries
Testing counterpartTop-down integration with stubsBottom-up integration with drivers (chapter 12)
➕ Added for exam Most real projects use a hybrid (sandwich) approach: top-down for the overall structure, bottom-up for reusable low-level components. Top-down design builds on Niklaus Wirth's idea of stepwise refinement (1971).

8.8Design Concepts and Architectural StylesADDED

➕ Added for exam

Fundamental design concepts (Pressman)

ConceptMeaning
AbstractionFocus on the essential and hide the details. Procedural abstraction ("open door") and data abstraction (a "door" object with attributes).
Stepwise refinementElaborate a high-level statement step by step into detail (Wirth). It is the complement of abstraction.
ModularityDivide the software into separately named, addressable modules (chapter 9).
Information hidingA module hides its internal data and algorithms and exposes only an interface (David Parnas, 1972).
Functional independenceEach module does one thing with little interaction with others, measured by cohesion and coupling.
Separation of concernsSplit a complex problem into parts that can be solved independently.
RefactoringRestructure code or design without changing its external behaviour (chapter 14).
Design patternsProven solutions to recurring problems: Singleton, Factory, Observer, MVC (from the "Gang of Four" book).

Common architectural styles

StyleIdeaExample
LayeredEach layer serves the one above itOSI model, presentation → business → data layers
Client–serverClients request, a central server respondsWeb apps, ATM ↔ bank server
Pipe-and-filterData flows through a chain of transforming filtersUnix pipes, compilers
Repository / data-centredComponents share a central data storeDatabases, IDEs
MVCSeparates Model (data), View (UI) and Controller (input logic)Web frameworks
Event-drivenComponents react to events or messagesGUIs, notification systems
MicroservicesSmall, independently deployable services that talk over APIsNetflix, Amazon

Function-oriented vs object-oriented design

Function-oriented design (Structured Analysis / Structured Design, SA/SD) decomposes the system into functions top-down. Its main design artefact is the structure chart: modules as rectangles, calls as arrows, data couples as arrows with an open circle, and control flags as arrows with a filled circle. Object-oriented design decomposes the system into objects that combine data and behaviour, and uses UML class, sequence and state diagrams.
🎯 IBPS exam alert "Information hiding was proposed by?" → Parnas. "Stepwise refinement?" → Wirth. "Which style suits a compiler?" → pipe-and-filter. "Structure chart is used in?" → function-oriented (structured) design.

8.9Solved Exam QuestionsADDED

Q1The output of the design phase is the: (a) SRS (b) SDD (c) test plan (d) source code
Answer: (b) SDD (Software Design Document).
Q2Which level of design treats the system as a black box and specifies only its inputs and outputs?
Answer: Interface design.
Q3Algorithms and data structures for each module are decided during:
Answer: Detailed design (LLD).
Q4"Divide and conquer" design that starts from the overall system and refines it into modules is:
Answer: Top-down design.
Q5Hiding a module's internal details behind a well-defined interface is called:
Answer: Information hiding (Parnas).

⚡ Rapid Revision

  • Design: input SRS → output SDD (IEEE 1016). HLD = architecture and interfaces; LLD = internal logic.
  • A good design covers all requirements, is free from conflict, ambiguity and incompleteness, is clear, and has high cohesion with low coupling.
  • Interface design = black box, I/O only · Architectural = components, responsibilities, interactions · Detailed = algorithms and data structures inside each component.
  • Hostage rescue: surroundings and secret path (interface) · house blueprint (architecture) · objects inside each room (detailed).
  • Top-down = decomposition, clear problem needed (4 years → semesters → units). Bottom-up = composition (study unit 1–6 the night before). Hybrid = sandwich.
  • Concepts: abstraction, refinement (Wirth), modularity, information hiding (Parnas), functional independence, patterns, refactoring.
  • Styles: layered, client–server, pipe-and-filter, repository, MVC, event-driven, microservices.
