Chapter 7

Process Synchronization

In Chapters 5 and 6 the scheduler could preempt any process at any instruction. That is harmless when processes are independent, but dangerous when they share data. A process preempted halfway through updating a shared variable can leave it inconsistent. This chapter covers how that happens (race condition), where it happens (the critical section), the rules a fix must follow, and the tools that provide the fix: software solutions, hardware instructions and semaphores. It ends with the three classic problems.

7.0Why Synchronization?

Process synchronization: coordinating processes that share resources (data, memory, files) so that they do not interfere with each other and the shared data stays consistent.
🎓 From the lecture P1 and P2 share some common data. P1 changes it, then P2 changes it, and the data can become inconsistent. Synchronization makes them take turns on the shared part. The two "very important terms" are the race condition and the critical section.

7.1Cooperative vs Independent Processes

Independent processCooperative process
Shares nothing with other processesShares data, memory, files or other resources
Cannot affect, and is not affected by, othersCan affect and be affected by others; "look at it from both sides"
No synchronization neededNeeds synchronization
➕ Why processes cooperate, and how Reasons (Galvin): information sharing, computation speed-up, modularity, convenience.
IPC models: (1) Shared memory: fast, but needs synchronization (this chapter). (2) Message passing (send / receive): the kernel handles it; easier, slower; can be direct or indirect (mailbox) and blocking (synchronous) or non-blocking. Pipes (ordinary and named / FIFO), sockets and RPC are forms of message passing.

7.2Race Condition: Shared Data Example

Race condition: several processes access and change shared data concurrently, and the final result depends on the order in which their instructions happen to run.
🎓 From the lecture — data = 100 Shared data = 100.
P1: ① a = data ② a = a + 50 ③ data = a.
P2: ① b = data ② b = b + 5 ③ data = b.
"The OS can preempt any process at any moment, forcibly."
InterleavingWhat happensFinal data
A: P1 ①②, preempt → P2 ①②, preempt → P1 ③ → P2 ③a = 150, b = 105 (still read 100). P1 writes 150; P2 then overwrites it with 105.105 ✗
B: P1 fully, then P2 (or P2 fully, then P1)100 → 150 → 155155 ✔ correct
C: P2 ①②, preempt → P1 ①②, preempt → P2 ③ → P1 ③P2 writes 105; P1 overwrites it with 150.150 ✗

Conclusion: three different answers (105, 150, 155) from the same code. "When the result depends on the order of execution, something is wrong. Everyone is racing." That is a race condition. Only serial execution gives the correct 155. The +50 or +5 update was lost in A and C, which is called a lost update.

7.3Critical Section: Count Increment/Decrement Example

Critical Section (CS): the segment of code in which a process accesses or updates shared data. Only that part needs protection; the rest of the code is the remainder section (the lecture calls it the "non-critical section").
🎓 From the lecture — count = 10 A single high-level statement is three machine instructions, and preemption can strike between any two of them. 
P1: count++               P2: count--
 ① r1 = count              ① r2 = count
 ② r1 = r1 + 1             ② r2 = r2 - 1
 ③ count = r1              ③ count = r2
OrderResult
1. P1 fully, then P2 (serial)10 → 11 → 10 ✔
2. P1 ①②, P2 ①②, P1 ③, P2 ③9 ✗
3. P2 ①②, P1 ①②, P2 ③, P1 ③11 ✗
⚠️ Exam trap Galvin's version of this example uses counter = 5, with wrong answers 4 or 6. The idea is identical. Remember also that the critical section is code, not the shared variable itself; the lecture sometimes uses the term loosely.

7.4Entry Section and Exit Section

🎓 From the lecture Entry section: the code just above the CS that checks whether I may enter. "We put a trap here" (a waiting loop).
Exit section: code that tells the other process I've left the CS, so it can now enter.

7.5Critical Section Requirements: Mutual Exclusion

Any solution to the critical-section problem is judged on three conditions.

1. Mutual Exclusion (ME): at any time, at most one process can be in its critical section. If P1 is inside, P2 must stay out. This is mandatory.

7.6Critical Section Requirements: Progress

2. Progress (lecture's version): an interested process must be able to enter the CS; a not-interested process must not block it. Also, no deadlock. This is mandatory.
🎓 From the lecture P1 wants to enter, P2 doesn't care right now. P2 must not stand in P1's way. The uninterested process says: "We have progressive thinking. You go ahead; if we change our mind later, we'll come too."
➕ Textbook definition (Galvin) If no process is in its CS and some processes want to enter, then only those not in their remainder section can take part in deciding who enters next, and that decision cannot be postponed indefinitely.

7.7Critical Section Requirements: Bounded Waiting

🎓 From the lecture — The phone call There must be a limit. You phone a busy friend:
  • "I'm busy, I'll call back in 5 minutes" → a known bound, so the wait is bounded ✔.
  • "I'll call, I'll call…" from a meeting, with no time given → you wait indefinitely ✗.
A process saying "I'll enter my CS at most 3 times" gives a bound; "infinite times" is not allowed, because the other process would wait forever.
3. Bounded Waiting (textbook): after a process has requested entry to its CS, there is a limit on how many times other processes may enter their CS before that request is granted. This guarantees no starvation.
⚠️ Exam trap (Is bounded waiting optional?) The lecture calls bounded waiting "not so mandatory". In Galvin, all three (ME, Progress, Bounded Waiting) are requirements of a correct CS solution. GATE/IBPS-style questions often say "ME and Progress are mandatory; Bounded Waiting is desirable". Answer according to the question's wording, but know that a solution without bounded waiting allows starvation.
➕ A fourth, informal condition No assumptions about speed or number of CPUs. A solution must not rely on relative process speeds or on running on a single processor. This is often called "architectural neutrality" (Tanenbaum).

7.8Two-Process Solutions

🎓 From the lecture A popular way to study solutions: take only two processes, try a technique to remove the CS problem, and test it against the three conditions. The lecture names the processes P1 and P2, with array index 0 for P1 and 1 for P2.
➕ The full map of solutions

7.9Turn Variable (Strict Alternation)

A shared variable turn (0 or 1) says whose turn it is: turn = 0 means P1 may enter; turn = 1 means P2 may enter.
Code (lecture) 
// shared: int turn = 0;
P1:                               P2:
while (1) {                       while (1) {
    while (turn != 0);  // trap       while (turn != 1);  // trap
    <critical section>                <critical section>
    turn = 1;           // exit       turn = 0;           // exit
    <non-critical section>            <non-critical section>
}                                 }
Two kinds of while: while(1){…} repeats its body forever. while(cond); (note the semicolon) is a trap: it spins on the condition and moves on only when the condition becomes false. This is busy waiting.
🎓 Mutual exclusion check turn can hold only one value at a time. With turn = 0, P2 is trapped; with turn = 1, P1 is trapped. Only one can be inside, so ME is satisfied ✔.

7.10Turn Variable: Why Progress Fails

🎓 From the lecture turn = 0, but P1 is not interested. P2 wants to enter, but it is stuck in while(turn != 1) until P1 goes through its CS and sets turn = 1. The uninterested P1 is blocking the interested P2, so Progress fails ✗. Entry is forced into strict alternation: P1, P2, P1, P2…
Turn variableVerdict
Mutual exclusion✔ Yes
Progress✗ No: strict alternation
Bounded waiting ADDED✔ Yes: after one turn each, the other process is guaranteed entry

7.11Flag Array Solution

boolean flag[2] = {false, false}. flag[i] = true means "I am interested in entering the CS".
Code (lecture) 
P1:                               P2:
flag[0] = true;    // interested  flag[1] = true;
while (flag[1]);   // trap        while (flag[0]);
<critical section>                <critical section>
flag[0] = false;   // exit        flag[1] = false;
<non-critical section>            <non-critical section>
🎓 From the lecture ME ✔: a process waits while the other's flag is true. Progress (no contention): if P1 is not interested (flag[0] = false), P2 sets flag[1] = true, finds flag[0] false and enters, so an uninterested process doesn't block. "But, but, but… the picture isn't over yet."

7.12Flag Array: Deadlock Problem

🎓 From the lecture — Both say "after you"
  1. P1 sets flag[0] = true, then is preempted.
  2. P2 sets flag[1] = true, then is preempted. Both flags are true.
  3. P1 resumes: while(flag[1]) is true, so it waits.
  4. P2 resumes: while(flag[0]) is true, so it waits.
Each waits for the other to reset its flag. Neither enters, forever: deadlock, so progress is hampered.
Flag arrayVerdict
Mutual exclusion✔ Yes
Progress✗ No: deadlock possible when both set their flags together
Bounded waiting✔ Yes (when no deadlock occurs)
⚠️ Exam trap flag[j] = true means "the other process is interested", not that it is in the CS. Summary: turn variable fails Progress through strict alternation; flag array fails Progress through deadlock. Peterson combines the two and fixes both.

7.13Peterson's Solution

Peterson's solution (1981): a software solution for two processes that combines the flag array and the turn variable. A process announces interest (flag) and then politely gives the turn to the other. It satisfies all three conditions.
Code (lecture form; initially turn = 0, flag = {F, F}) 
P1:                                    P2:
flag[0] = true;   // I'm interested    flag[1] = true;
turn = 1;         // "you go first"    turn = 0;
while (turn == 1 && flag[1] == true);  while (turn == 0 && flag[0] == true);
<critical section>                     <critical section>
flag[0] = false;                       flag[1] = false;
<non-critical section>                 <non-critical section>
Spin only while both are true: "it's the other's turn" and "the other is interested". If either is false, enter.
➕ Galvin's form (Pi / Pj, j = 1 − i) 
flag[i] = true;  turn = j;
while (flag[j] && turn == j);   // busy wait
    /* critical section */
flag[i] = false;
    /* remainder section */
This is logically identical to the lecture's code; only the order of the && operands differs.

7.14Peterson's Solution: Mutual Exclusion Scenario

Walkthrough (lecture): both want to enter
StepActionturnflag[0]flag[1]Result
1P1: flag[0] = T, turn = 1 → preempted1TF
2P2: flag[1] = T, turn = 00TT
3P2 checks turn==0 (T) && flag[0]==T (T)0TTP2 spins
4P1 resumes: turn==1? F → loop exits0TTP1 enters CS
5P1 exits: flag[0] = F0FT

Conclusion: turn can hold only one value, so whoever wrote turn last waits. Only one process enters at a time, so ME ✔. Unlike the flag array, there is no deadlock when both are interested.

7.15Peterson's Solution: Progress Guaranteed

🎓 From the lecture P1 is not interested (flag[0] = F, turn = 0). P2 sets flag[1] = T and turn = 0, then checks turn==0 (T) && flag[0]==T (F), which is false, so P2 enters immediately. It can do this again and again while P1 stays uninterested. The uninterested process never blocks, so Progress ✔.
Peterson's solutionVerdict
Mutual exclusion✔
Progress✔
Bounded waiting ADDED✔: a waiting process enters after at most one entry by the other, because the other sets turn in its favour on the next attempt
➕ Limitations (textbook)
  • Works only for 2 processes. For n processes, use the Bakery algorithm (Lamport). Dekker's algorithm was the first correct two-process software solution (1965). Both are covered in 7.15A.
  • Uses busy waiting, which wastes CPU cycles.
  • It is not guaranteed on modern CPUs, because compilers and processors may reorder independent reads and writes. Memory barriers are needed.

7.15ADekker's Algorithm & Bakery Algorithm ADDED

Dekker's algorithm (1965): the first correct software solution for two processes, by the Dutch mathematician Th. J. Dekker and published by Dijkstra. Like Peterson's, it uses flag[2] and turn. The difference: when both are interested, the process whose turn it is not lowers its flag and backs off until the turn comes to it.
Code (Pi, with j = 1 − i; initially flag = {F, F}, turn = 0 or 1) 
flag[i] = true;              // I'm interested
while (flag[j]) {            // the other is interested too
    if (turn == j) {         // and it is the other's turn
        flag[i] = false;     //   back off
        while (turn == j);   //   busy wait for my turn
        flag[i] = true;      //   show interest again
    }
}
<critical section>
turn = j;                    // hand the turn to the other
flag[i] = false;
<remainder section>
SituationWhat happens
Only Pi interested (flag[j] = F)The outer while is false, so Pi enters at once: progress ✔ (unlike strict alternation)
Both interestedturn breaks the tie. The process that does not hold the turn lowers its flag, so there is no deadlock (unlike the flag array), and only one enters: ME ✔
Pi leaves the CSIt sets turn = j, so if Pj is waiting it goes next: bounded waiting ✔
➕ Dekker vs Peterson Both are two-process, busy-waiting solutions that satisfy all three conditions. Peterson gives the turn away on entry (turn = j before waiting), which makes it a single short loop. Dekker gives the turn away on exit and needs the nested back-off loop. Peterson's (1981) is a simpler form of the same idea.
Bakery algorithm (Lamport, 1974): a software solution for n processes. It works like a bakery or bank token counter: each process that wants the CS takes a token number one larger than any number currently held, and the smallest token is served first. If two processes get the same number, the one with the smaller process id goes first.
Code (Pi; shared: bool choosing[n] = {F…}; int number[n] = {0…}) 
choosing[i] = true;                         // I'm picking a token
number[i] = 1 + max(number[0], …, number[n-1]);
choosing[i] = false;
for (j = 0; j < n; j++) {
    while (choosing[j]);                    // wait until Pj has its token
    while (number[j] != 0 &&
           (number[j], j) < (number[i], i)); // Pj is ahead of me: wait
}
<critical section>
number[i] = 0;                              // give up my token
<remainder section>
(a, b) < (c, d) means a < c, or a = c and b < d. number[i] = 0 means "not interested".
Walkthrough: P1, P2, P3 want the CS
StepEventnumber[1]number[2]number[3]
1P1 and P3 read the max at the same time (0), so both take 1101
2P2 arrives later and takes 1 + max = 2121
3Tie at 1: (1, 1) < (1, 3), so P1 enters121
4P1 exits: number[1] = 0, so P3 enters021
5P3 exits: number[3] = 0, so P2 enters020
Order served: P1 → P3 → P2, which is first-come first-served by token and then by process id.
Bakery algorithmVerdict
Mutual exclusion✔: the pair (number, id) is unique, so exactly one waiting process has the smallest pair
Progress✔: a process with number = 0 is skipped and never blocks others
Bounded waiting✔: FCFS. A process that arrives later gets a larger token, so each process waits for at most n − 1 others
⚠️ Exam traps
  • Why is choosing[] needed? Without it, Pi could look at Pj while Pj has read the max but not yet written its number. Pi sees number[j] = 0 and enters; Pj then writes the same number, has the smaller id, and also enters, so ME fails. while(choosing[j]) makes Pi wait until Pj's token is final.
  • Token numbers can be equal, because the max is not computed atomically. That is why ties are broken by process id.
  • Token numbers can grow without bound while the CS is always busy, which is a practical drawback.
  • All three (Peterson, Dekker, Bakery) use busy waiting and need no special hardware. They work using only ordinary reads and writes.

7.16Lock Variable

Lock variable: a single shared variable lock. 0 means the CS "room" is free; 1 means someone is inside, so it is locked. A process waits while the room is locked, then locks it, enters, and unlocks it on exit.
Code (lecture) 
// shared: int lock = 0;
while (lock != 0);   // ① test  (same as while(lock == 1);  "kaam ek, naam alag")
lock = 1;            // ② set — lock the room
<critical section>
lock = 0;            // exit: open the lock
<non-critical section>
🎓 From the lecture Without preemption, P1 finds lock = 0, sets it to 1, enters, and sets it back to 0 on leaving. Then P2 does the same. It looks perfect in either order. "But there is a very big BUT: preemption." Lock variables run in user mode and work for any number of processes.

7.17Lock Variable: Mutual Exclusion Failure under Preemption

Walkthrough (lecture): lock = 0 initially
StepEventlock
1P1 runs ① while(lock != 0), which is false (lock = 0)0
2P1 is preempted just before ② (a higher-priority process or an expired quantum)0
3P2 runs ①: still 0, so it passes, sets lock = 1 and enters the CS1
4P1 resumes at ② (it already "saw" 0), sets lock = 1 and enters the CS1
5Both P1 and P2 are inside the CS✗
Conclusion: Mutual exclusion fails ("dhajjiyan ud gayi", torn to shreds). Without ME, "why even talk about progress or bounded waiting?" Root cause: the test (①) and the set (②) are two separate instructions, and preemption can strike between them. Fix: combine test and set into one atomic instruction.

7.18Test-and-Set (TSL) Instruction

Test-and-Set (TSL, Test and Set Lock): a hardware instruction that, in one atomic (uninterruptible) step, returns the old value of a lock variable and sets it to true.
Code (lecture's "most popular snippet") 
boolean TestAndSet(boolean *target) {   // executed ATOMICALLY by hardware
    boolean s = *target;   // remember OLD value of lock
    *target = true;        // ALWAYS set lock = true
    return s;              // return OLD value
}

// shared: boolean lock = false;
while (TestAndSet(&lock));   // spin while old value was true
<critical section>
lock = false;                // release
First caller (lock = false): s = false, lock becomes true, and false is returned. The loop exits and the process enters the CS. Whatever the old value, TSL always leaves lock = true.

7.19Test-and-Set: Mutual Exclusion with Two Processes

Walkthrough (lecture)
  1. P1: TestAndSet(&lock) with lock = false returns false and sets lock = true. P1 leaves the loop, then is preempted before entering the CS.
  2. P2: TestAndSet(&lock) sees lock = true, returns true, and sets lock = true again. P2 is trapped and spins.
  3. P1 resumes. The test and the set already happened together, so it simply enters the CS, and on exit sets lock = false.
  4. P2's next call returns false, so it enters.
Conclusion: preemption can no longer split the test from the set, so ME is guaranteed ✔.
Simple TSL lock ADDEDVerdict
Mutual exclusion✔
Progress✔
Bounded waiting✗: an unlucky process may lose the race every time. Galvin gives an extended TSL algorithm with a waiting[] array to fix this.
Busy waitingYes: the process spins, so it is a spinlock

7.19ABusy Waiting, Spinlocks, Mutex & Hardware Support ADDED

  • Busy waiting: a waiting process loops continuously (the lecture's "trap"), wasting CPU cycles. A lock that busy-waits is a spinlock. It is useful on multiprocessors when the wait is short, because it avoids a context switch.
  • Disabling interrupts: on a uniprocessor, turn interrupts off before the CS so no preemption can occur. It is not feasible on multiprocessors and too dangerous to give to user programs (it is a privileged instruction, Chapter 3).
  • Swap / Compare-and-Swap (CAS): another atomic instruction. compare_and_swap(&lock, 0, 1) sets lock to 1 only if it is currently 0, and returns the old value. It is used in x86 (CMPXCHG) and in lock-free data structures.
  • Mutex lock: the simplest OS tool. acquire() waits until available is true, then sets it false; release() sets it true. Both must be atomic. A mutex is owned: only the process that locked it may unlock it.

7.20Semaphores: Introduction

Semaphore (Dijkstra, 1965): an integer variable that, apart from initialization, is accessed only through two atomic operations, wait() and signal(). It is used to manage concurrency and solve synchronization problems.
Binary semaphoreCounting semaphore
Value only 0 or 1Value is an unrestricted integer (lecture: −∞ to +∞)
Used for mutual exclusion; behaves like a mutex lockUsed to control access to a resource with N instances (initial value = N)
⚠️ Exam trap (Atomicity) The lecture calls a semaphore "just an integer variable". The key point is that wait and signal are atomic: no two processes can run wait/signal on the same semaphore at the same time. Otherwise a semaphore would fail exactly as the lock variable did in 7.17. Atomicity is achieved by disabling interrupts (uniprocessor) or with spinlocks or TSL (multiprocessor).

7.21Binary Semaphore: Wait (P) and Signal (V)

OperationOther namesLecture's meaning
P(S)wait · sleep · down (Dutch proberen, "to test") ADDED"Wait, I'm in the CS" · "you go to sleep" · "no need to be up right now". Called before the CS.
V(S)signal · wakeup · up (Dutch verhogen, "to increment") ADDED"I'm out, you can come" · "I'll wake you up" · "I'll make you up". Called after the CS.
Code (lecture, busy-wait form) 
P(S) {                 // wait / down
    while (S == 0);    // trap while 0      (Galvin: while (S <= 0);)
    S--;               // 1 → 0
}
V(S) {                 // signal / up
    S++;               // 0 → 1, no check at all
}

// each process:
P(S);   <critical section>   V(S);   <remainder>

7.22Binary Semaphore: Working Example

Walkthrough (lecture): S = 1
StepEventS
1P1 does P(S): S == 0? No → S-- → P1 enters the CS0
2P2 does P(S): S == 0? Yes → P2 trapped ("no matter how hard it tries")0
3P1 leaves → V(S)1
4P2: S == 0? No → S-- → P2 enters0
Conclusion: a binary semaphore initialised to 1 gives mutual exclusion. If it were initialised to 0, nobody could enter until someone signals, which is useful for ordering (see 7.24A).

7.23Counting Semaphore and Block List

🎓 From the lecture — S = 5 The initial value S = 5 means up to 5 processes may proceed at once. Each P(S) decrements S: P1 → 4, P2 → 3, P3 → 2, P4 → 1, P5 → 0 (capacity full). P6 → −1, so it goes to the block list. P7 → −2 (block list), P8 → −3 (block list).
wait / P with a block list (lecture) 
P(S) {
    S--;
    if (S < 0) {
        add this process to block list;   // "so ja bhaiya, thodi der ke liye"
        block();                          // sleep — NO busy waiting
    }
    // else: proceed into critical section / use resource
}
➕ Textbook form (Galvin) 
typedef struct { int value; struct process *list; } semaphore;
block() suspends the caller and moves it to the semaphore's waiting queue (the lecture's "block list"). This version has no busy waiting, unlike 7.21. Here the value can go negative; in the classic busy-wait definition it never does.
⚠️ Exam trap The lecture says "S = how many processes can be in the critical section". Strictly, a CS admits one process. A counting semaphore counts available instances of a resource, e.g. 5 printers or 5 database connections, so "5 processes may use the resource at once".

7.24Counting Semaphore: Signal Operation and Wake-up

signal / V with wake-up (lecture) 
V(S) {
    S++;
    if (S <= 0) {                       // someone is still blocked
        remove a process P from block list;
        wakeup(P);                       // "jaag jao" → moves to ready queue
    }
}
Example: S = −3 (P6, P7, P8 blocked). P1 leaves and does V(S), so S = −2. Since −2 ≤ 0, one blocked process is woken up and can proceed.
🎯 Interpreting the value (memorise)
  • Initial S = number of processes allowed through at the same time (resource instances).
  • S > 0: that many more can enter without blocking.
  • S = 0: all instances in use and the block list empty.
  • S < 0: |S| processes are blocked.
  • The woken process is often chosen FIFO, which gives bounded waiting. A woken process has already decremented S, so it proceeds directly.

7.24ASemaphore Numericals ADDED

Numerical 1: final value A counting semaphore is initialised to 10. Then 6 P (wait) and 4 V (signal) operations are performed. Final value?
Step: each P is −1 and each V is +1, so 10 − 6 + 4 = 8. The order does not matter for the final value.
Numerical 2: blocked processes S = 7. Twenty P operations and fifteen V operations are done. Final S? 7 − 20 + 15 = 2.
If instead only 12 P operations were done and no V, S = 7 − 12 = −5, so 5 processes are blocked.
Numerical 3: ordering with a semaphore initialised to 0 We need statement S1 (in P1) to run before S2 (in P2). Use synch = 0: 
P1:  S1;  signal(synch);        P2:  wait(synch);  S2;
P2 blocks until P1 signals, so S1 always precedes S2.
Numerical 4: deadlock with two semaphores S = Q = 1. 
P0: wait(S); wait(Q); …      P1: wait(Q); wait(S); …
P0 takes S and P1 takes Q. Then each waits forever for the other's semaphore: deadlock. Using the same order in both processes prevents it (see Chapter 8).
➕ Problems with semaphores Deadlock (above) · starvation (LIFO waiting list) · priority inversion: a low-priority process holds a semaphore needed by a high-priority one, fixed by the priority-inheritance protocol (the Mars Pathfinder bug) · programmer errors: swapping wait and signal breaks ME, and omitting signal causes deadlock. These errors led to monitors (7.38).

7.25Producer-Consumer Problem (Bounded Buffer)

A producer produces items one at a time and puts them into a shared buffer of n slots. A consumer takes items out one at a time. The two must be synchronized so that the producer never inserts into a full buffer, the consumer never removes from an empty one, and both never touch the buffer at the same time.
🎓 From the lecture "Very popular; many questions can be asked." Two dangers: overflow, when the producer keeps inserting into a full buffer, and underflow, when the consumer tries to consume from an empty buffer. "Remember these two words: empty and full."

7.26Producer-Consumer: Full, Empty and Mutex Semaphores

SemaphoreInitial valueCounts / purposePrevents
full (counting)0Number of filled slots; nothing is inserted yetUnderflow (consumer blocks at 0)
empty (counting)nNumber of empty slots; all are empty at the startOverflow (producer blocks at 0)
mutex (binary)1Mutual exclusion on the buffer: producer and consumer must never meet face to face ("aamna-saamna")Race on the buffer

At any time, full + empty = n (ignoring operations in progress).

7.27Producer Code Walkthrough

Producer (lecture; buffer index added from Galvin) 
// semaphore full = 0, empty = n, mutex = 1;   int in = 0;
Producer() {
    while (true) {
        item = produce_item();
        wait(empty);        // one fewer empty slot   (n → n−1); blocks if 0 = FULL
        wait(mutex);        // lock buffer            (1 → 0)
        buffer[in] = item;  // insert
        in = (in + 1) % n;  //                        [Galvin]
        signal(mutex);      // unlock                 (0 → 1)
        signal(full);       // one more filled slot   (0 → 1)
    }
}

7.28Consumer Code Walkthrough

Consumer (lecture; buffer index added from Galvin) 
// int out = 0;
Consumer() {
    while (true) {
        wait(full);          // one fewer filled slot  (blocks if 0 = EMPTY)
        wait(mutex);         // lock buffer
        item = buffer[out];  // remove
        out = (out + 1) % n; //                         [Galvin]
        signal(mutex);       // unlock
        signal(empty);       // one more empty slot
        consume_item(item);  // Galvin consumes outside the CS
    }
}
🎓 Lecture's key insight: "look how opposite they are" The producer does wait(empty) … signal(full). The consumer does wait(full) … signal(empty). "Once you get this, producer-consumer becomes a chindi (trivial) problem."
⚠️ Exam trap (Order of the waits) Never swap wait(empty) and wait(mutex) in the producer, or wait(full) and wait(mutex) in the consumer. If the producer takes the mutex first and then blocks on empty (buffer full), the consumer can never get the mutex to free a slot: deadlock. Swapping the two signals is harmless.
Numerical: trace with n = 3 Start: full = 0, empty = 3, mutex = 1.
The producer inserts 3 items, giving full = 3 and empty = 0. A 4th produce blocks on wait(empty), because empty would become −1 and the producer goes to the block list.
The consumer removes 1 item, giving full = 2 and empty = 1 after signal(empty), which wakes the producer.
Conclusion: overflow and underflow are prevented automatically by the counting semaphores.

7.29Readers-Writers Problem

A shared database or file is accessed by many readers (only read) and writers (update). Many readers may read together, but a writer needs exclusive access: no other writer and no reader.

7.30Readers-Writers: Writer Process Code

Writer (lecture) 
Writer() {
    wait(wrt);      // 1 → 0: no other writer, no reader
    /* perform WRITE */
    signal(wrt);    // 0 → 1: others may now read/write
}
"While I'm writing, please nobody come to write and nobody come to read."

7.31Readers-Writers: Reader Process Code

Reader (lecture): it uses the mutex twice 
Reader() {
    wait(mutex);                 // protect readcount
    readcount++;
    if (readcount == 1)          // FIRST reader…
        wait(wrt);               // …locks out writers for ALL readers
    signal(mutex);

    /* perform READ */           // many readers can be here together

    wait(mutex);
    readcount--;
    if (readcount == 0)          // LAST reader leaving…
        signal(wrt);             // …lets writers in
    signal(mutex);
}

Only the first reader competes with writers on wrt, and only the last reader releases it. Readers in between just update readcount.

7.33Dining Philosophers Problem

Dining philosophers (Dijkstra): 5 philosophers sit at a round table with a bowl of rice and 5 forks (chopsticks), one between each pair. A philosopher alternates between thinking and eating, and needs both adjacent forks (left and right) to eat. It models allocating several resources among processes without deadlock or starvation.
🎓 From the lecture "A very interesting problem; you get hungry looking at it." Philosophers only think and eat ("to think you need to eat"). There are exactly 5 forks, one per person, but eating rice needs two.

7.34Dining Philosophers: Semaphore Solution Code

Code (lecture): one binary semaphore per fork 
semaphore f[5] = {1, 1, 1, 1, 1};   // 1 = fork on table, 0 = picked up
Philosopher(i) {
    while (true) {
        think();
        down(f[i]);              // pick LEFT fork   (wait / P)
        down(f[(i + 1) % 5]);    // pick RIGHT fork
        eat();
        up(f[i]);                // put LEFT fork down (signal / V)
        up(f[(i + 1) % 5]);      // put RIGHT fork down
    }
}
Example: P2 wants to eat. down(f[2]) takes the left fork, and (2+1) % 5 = 3, so down(f[3]) takes the right fork. It eats, then puts back f2 and f3. For P4, the right fork is (4+1) % 5 = 0, which closes the circle.

7.35Dining Philosophers: Concurrent Eating by Non-Adjacent Philosophers

🎓 From the lecture P0 takes f0 and f1 and eats. P1 needs f1, which is taken, so P1 is blocked. P2 needs f2 and f3, which are both free, so P2 eats at the same time as P0. Non-adjacent philosophers can eat together: P0 with P2, or P0 with P3, but never P0 with P1.
➕ Maximum eating at once With n philosophers, at most ⌊n/2⌋ can eat simultaneously. With 5 philosophers that is 2 (each eater uses 2 of the 5 forks).

7.36Dining Philosophers: Deadlock Scenario

Walkthrough (lecture): everyone picks the left fork, then is preempted
StepEventf0 f1 f2 f3 f4
0Start1 1 1 1 1
1–5P0 takes f0, P1 takes f1, P2 takes f2, P3 takes f3, P4 takes f4, each preempted before taking its right fork0 0 0 0 0
6P0 needs f1, P1 needs f2, P2 needs f3, P3 needs f4, P4 needs f0, and all are taken0 0 0 0 0
Conclusion: every philosopher holds only the left fork and waits forever for the right one: deadlock. In Chapter 8 terms this is circular wait: P0 → P1 → P2 → P3 → P4 → P0.

7.37Dining Philosophers: Deadlock Solutions (Reversing Fork Order)

🎓 From the lecture — two approaches
  1. Change the problem (e.g. add more forks). The lecture rejects this: it changes the given constraints ("galat baat hai").
  2. Reverse the order for ONE philosopher. Four philosophers pick left then right; one chosen philosopher (any one, e.g. P4) picks right then left: down(f[(i+1)%5]); down(f[i]);
Walkthrough (lecture): P4 reversed, so it picks f0 first, then f4
  1. P0 takes f0, P1 takes f1, P2 takes f2, P3 takes f3 (each preempted).
  2. P4 tries its first fork, f0, which is taken, so P4 blocks without taking f4. f4 stays free.
  3. P3 takes f4, eats, and releases f3 and f4.
  4. P2 takes f3, eats, and releases f2 and f3. Then P1 eats and releases, then P0 eats and releases.
  5. All forks are free, so P4 takes f0 and f4 and eats.
Conclusion: the circle of waiting is broken, so no deadlock.
➕ Galvin's three remedies (know all of them)
  1. Allow at most 4 philosophers at the table at once (a counting semaphore initialised to 4).
  2. A philosopher picks up forks only if both are available, doing the check-and-pick inside a critical section.
  3. Asymmetric solution: odd philosophers pick left then right; even philosophers pick right then left. The lecture's "reverse one philosopher" is a variant of this.
A monitor-based solution uses philosopher states THINKING, HUNGRY and EATING and lets i eat only if both neighbours are not eating. Note: a deadlock-free solution does not automatically prevent starvation.

7.38Monitors, IPC & Master Comparison ADDED

Monitor: a high-level language construct (an abstract data type) that bundles shared data plus the procedures that operate on it. Only one process can be active inside a monitor at a time; mutual exclusion is automatic. For waiting, it provides condition variables with x.wait() (suspend) and x.signal() (resume exactly one waiting process; if none is waiting, it does nothing, unlike a semaphore signal).
  • Monitors remove the semaphore programmer errors (a wrong order, a missing signal). Examples: Java synchronized methods with wait() / notify(); C# lock.
  • Signal semantics: signal-and-wait (Hoare) vs signal-and-continue (Mesa / Java).

  • Race condition: the result depends on the order of execution. The CS is the code that touches shared data.
  • Three requirements: ME, Progress, Bounded Waiting. Peterson's satisfies all three, for 2 processes.
  • Semaphore operations: wait = P = down, signal = V = up. Inventor: Dijkstra.

  • Independent processes share nothing; cooperative processes share data and affect each other, so they need synchronization. IPC is via shared memory or message passing.
  • Race condition: data = 100, with +50 and +5 → results 105, 150 or 155 depending on order. count = 10 with ++/−− → 9, 10 or 11. Each statement is 3 machine instructions, and preemption between them causes a lost update.
  • CS structure: entry section ("trap") → CS → exit section → remainder.
  • ME: only one process in the CS. Progress: an uninterested process can't block an interested one, and no deadlock. Bounded waiting: a limit on how often others enter before you (the phone "5 minutes" analogy); it means no starvation.
  • Turn variable: ME ✔, progress ✗ (strict alternation). Flag array: ME ✔, progress ✗ (both flags true → deadlock).
  • Peterson's: flag[i]=T; turn=j; while(turn==j && flag[j]);. ME ✔, progress ✔, bounded waiting ✔. Two processes; busy waiting.
  • Dekker's (1965, first correct 2-process solution): flag + turn, the non-turn process lowers its flag and backs off; turn handed over on exit. Bakery (Lamport, n processes): take token = 1 + max, smallest (number, id) enters first, so FCFS; choosing[] stops a half-taken token from breaking ME. All ✔ ME, progress, BW.
  • Lock variable: while(lock!=0); lock=1;. Preemption between the test and the set means both enter, so ME ✗.
  • TSL: atomic {old = lock; lock = true; return old}; while(TestAndSet(&lock));. ME ✔, bounded waiting ✗, spinlock.
  • Semaphore (Dijkstra): an integer with atomic P/wait/down and V/signal/up. Binary (0/1) for ME. Counting: S=5 → P1–P5 enter, P6–P8 blocked (S = −3); V wakes one if S ≤ 0.
  • Producer-consumer: full=0, empty=n, mutex=1. Producer: wait(empty), wait(mutex), insert, signal(mutex), signal(full). Consumer: the opposite. Never swap the waits.
  • Readers-writers: mutex=1, wrt=1, readcount=0. The first reader does wait(wrt); the last does signal(wrt); R-R is allowed and anything with W conflicts. Writers can starve.
  • Dining philosophers: fork[i]=1; take f[i] then f[(i+1)%5]. Everyone holding the left fork → deadlock. Fix: reverse the order for one philosopher (or odd/even), allow at most 4, or take both-or-none. At most 2 eat at once.
  • Monitor: data + procedures, one process active at a time, condition variables with wait/signal.

R1Basics: Race Condition & Critical Section

  • Synchronization: coordinating processes that share data so the data stays consistent. Needed only by cooperative processes (they share data and affect each other); independent processes share nothing. 7.0–7.1
  • Why cooperate (Galvin): information sharing, computation speed-up, modularity, convenience.
  • IPC: shared memory (fast, needs synchronization) or message passing (send/receive via kernel; easier, slower; direct or indirect (mailbox), blocking (synchronous) or non-blocking; pipes, sockets, RPC).
  • Race condition: the result depends on the order of execution. One statement = 3 machine instructions (load, change, store); preemption between them causes a lost update. 7.2–7.3

  • Critical section = the code that touches shared data (not the variable itself). Structure: entry section (the "trap") → CS → exit section → remainder. 7.4
