Chapter 5

Process Management

Chapters 3 and 4 created processes (fork) and threads. This chapter covers how the OS keeps track of each process (the PCB), how it moves the CPU between processes (context switching), which states a process passes through, and which schedulers decide those moves. It is the foundation for CPU Scheduling in Chapter 6.

5.1Program vs Process: Cricket Analogy

Chapter 1 (1.15) covered the basic difference: a program is passive and sits on disk; a process is active and runs in RAM. The lecture makes it "crystal clear" with cricket.

🎓 From the lecture — Cricket When you watch a match, some players are active and some are passive.
  • Active players are on the ground, inside the circle, batting and bowling. They are the processes, and the ground is main memory.
  • Passive players sit in the dressing room waiting for their chance to go out and create a sensation. They are the programs, and the dressing room is secondary memory.

5.2Process Control Block (PCB)

PCB (Process Control Block), also called the Task Control Block: a data structure the OS creates for every process. It holds all the information about that process. It is the OS's complete record of the process, and it is created when the process is created and destroyed when it terminates.
🎓 From the lecture — "The process's kundali" The PCB is the process's complete kundali (horoscope): everything about it in one place. Each process has its own PCB, and the OS creates it. The lecture goes through these fields:
Memory aid for PCB fields: "PiS PC PR R FIP". In order: PID · State · Program Counter · PRiority · Registers · File list · I/O info · Protection.
FieldLecture explanation
Process ID (PID)Uniquely distinguishes P1, P2, P3, P4 in main memory, just as a roll number identifies a student even when several share a name ("10, Rakesh, stand up").
Process stateWhich state the process is in now: new, ready, running, waiting/blocked or terminated (see 5.4).
Program counter (PC)Points to the next instruction to execute. Example: P1 has instructions i1, i2, i3, i4… After i3, P1 is preempted for a higher-priority process. The PC holds i4, so when P1 returns it resumes from i4, not from i1.
PriorityEach process carries a priority value. Kernel/OS processes always have higher priority than user processes, because they do system work.
RegistersThe values the process left in CPU registers. Saved at a context switch (5.3).
File listThe list of files the process has opened.
I/O infoWhich input and output devices the process needs, and when.
ProtectionEnsures no process interferes with another process's workspace. That "will never be tolerated".
… (etc.)Additional OS-specific fields; each OS can add its own.
➕ Added for exam
  • Galvin's standard PCB fields: process state, program counter, CPU registers, CPU-scheduling information (priority, queue pointers), memory-management information (base and limit registers, page tables), accounting information (CPU time used, time limits, process numbers) and I/O status information (allocated devices, open files).
  • PCBs live in kernel memory, a protected area that user processes cannot access. The set of all PCBs forms the process table.
  • Queues (ready queue, device queues) are linked lists of PCBs, which is why each PCB has a pointer field.
  • In Linux, the PCB is the C structure task_struct.

5.3PCB Registers and Context Switching

Context switch: switching the CPU from one process to another by saving the state (context) of the current process in its PCB and loading the saved state of the next process from its PCB. A process's context is its CPU register values, program counter, process state and memory-management information.
🎓 From the lecture — Why registers must be saved
  1. P1 is using registers R1, R2, R3 and has stored the values 1, 2, 3.
  2. P1 is preempted (forcibly stopped), and P2 arrives. P2 also uses R1, R2, R3 and writes its own values, 2, 3, 4.
  3. Problem: P1's values 1, 2, 3 would be overwritten and lost.
  4. Solution: before the switch from P1 to P2, P1's register values (1, 2, 3) are saved in its PCB.
  5. When P1 resumes, the saved values 1, 2, 3 are loaded back, and the remaining instructions continue with the correct values.
P1's context was {1, 2, 3}; P2's context was {2, 3, 4}. Saving before switching is essential, because the process's further instructions depend on those values.

5.3AContext-Switch Overhead & Dispatcher ADDED

  • Context-switch time is pure overhead: the system does no useful work while switching. It typically takes a few microseconds and depends on memory speed, the number of registers and hardware support (some CPUs have multiple register sets).
  • What triggers a context switch: a timer interrupt (time slice over), a higher-priority process becoming ready (preemption), the running process blocking for I/O, or the process terminating.
  • Dispatcher: the module that actually gives the CPU to the process the short-term scheduler selected. It performs the context switch, switches to user mode and jumps to the right place in the user program.
  • Dispatch latency: the time the dispatcher takes to stop one process and start another. It should be as small as possible.
Numerical: CPU efficiency with context-switch overhead
CPU efficiency = useful time / (useful time + switch time) = q / (q + s)
Given: time quantum q = 10 ms, context-switch time s = 1 ms.
Step 1: Useful work per cycle = 10 ms; total = 10 + 1 = 11 ms.
Step 2: Efficiency = 10 / 11 = 90.9%, so overhead = 9.1%.
Step 3: With q = 2 ms: 2 / 3 = 66.7%, so a third of the CPU time is wasted.
Conclusion: the smaller the time quantum, the larger the share of time lost to context switches. This matters for Round Robin in Chapter 6.
⚠️ Exam trap The scheduler decides which process runs next; the dispatcher does the switch. "Dispatch latency" belongs to the dispatcher. A context switch saves state in the PCB, not on the process's stack. Recall Chapter 3: a mode switch (user↔kernel, same process) is not a context switch.

5.4Process States

🎓 From the lecture — The five states
  • New: the program has just been picked up from secondary memory to be put into main memory, but is not yet placed there.
  • Ready: it is now created in main memory, sitting in the ready queue (P1, P2, P3…) and ready to be given to the CPU.
  • Ready → Running: scheduling / dispatching picks one process from the ready queue and gives it the CPU.
  • Running: executing on the CPU. From here there are three exits:
    1. I/O request → Wait/Block: whenever a process is in wait/block, it is doing I/O and not using the CPU. When the I/O completes, it goes back to Ready.
    2. Completion → Terminated: it finished all its CPU work successfully and is terminated.
    3. Preemption → Ready: it was forcibly stopped (e.g. after a time unit) and goes back to the ready queue while P2 runs. P2 may be preempted in turn for P3, and so on.
TransitionCause
New → ReadyAdmitted by the long-term scheduler into main memory
Ready → RunningDispatched by the short-term scheduler
Running → ReadyPreemption: time quantum expired or a higher-priority process arrived
Running → WaitingThe process requests I/O or waits for an event
Waiting → ReadyI/O or event completed
Running → TerminatedThe process finishes (exit) or is killed
⚠️ Exam trap (Impossible transitions)
  • Waiting → Running directly is NOT possible. After the I/O completes, the process must go through Ready first.
  • Ready → Waiting is NOT possible. Only a running process can issue an I/O request.
  • New → Running is NOT possible; it must be admitted to Ready first.
  • Only one process per CPU can be Running at a time. Many can be Ready or Waiting.
  • In a non-preemptive system, the Running → Ready transition (on a time-out) does not occur.

5.5Types of Schedulers: Long-Term Scheduler

There are three schedulers: long-term ("thinks far ahead from the initial point"), short-term ("doesn't need to think so far, but is very fast") and medium-term.

Long-Term Scheduler (LTS), also called the Job Scheduler: works between the New and Ready states. It selects which processes from secondary memory (the job pool) are admitted into main memory (the ready queue).
🎓 From the lecture — Balancing the mix (selfie analogy again) Every process demands CPU time and I/O time. The LTS decides what combination of processes to put in the ready queue. There are two extremes:
  1. All CPU-heavy (P1, P2, P3 … P100 all want only CPU): every fan's phone is unlocked and the camera is clean, so each one takes all 10 selfies with no I/O delay. The 100th person waits and waits, afraid the movie will end before their turn. This leads to starvation.
  2. All I/O-heavy: everyone forgets their password, has a dirty camera or can't open the camera app. The celebrity (the CPU) just stands there saying "click the photo, yaar!" The CPU is idle and utilisation is ruined.
We want neither extreme. We want a balance between CPU-heavy and I/O-heavy processes, and maintaining that balance is the long-term scheduler's job.
➕ Added for exam — CPU-bound vs I/O-bound
CPU-bound processI/O-bound process
Spends most of its time on computation; has long CPU burstsSpends most of its time doing I/O; has short CPU bursts
e.g. scientific calculation, video encodinge.g. text editor, database queries, copying files
All CPU-bound: the I/O queues are empty, devices sit idle, and others starveAll I/O-bound: the ready queue is empty and the CPU sits idle
The LTS's goal is a good process mix of CPU-bound and I/O-bound processes. It also controls the degree of multiprogramming (5.9). It runs infrequently (minutes apart), so it can afford to be slow. In time-sharing systems such as UNIX and Windows, the LTS is absent or minimal: every new process is simply put in memory.

5.6Short-Term Scheduler (CPU Scheduler)

Short-Term Scheduler (STS), also called the CPU Scheduler: works between the Ready and Running states. It selects one process from the ready queue and allocates the CPU to it. This is scheduling / dispatching.
🎓 From the lecture — Why it must be fast CPU time is very valuable. When the running process goes off for I/O (to wait/block), the CPU must not stay idle. At that very moment the STS should pick a process from the ready queue and hand it to the CPU: "I won't keep you idle for long, only the shortest possible time." So its speed matters; it is "Fast & Furious". That is why it is called the CPU scheduler.
➕ Added for exam
  • It runs very frequently, about once every 100 milliseconds or on every interrupt and I/O event. It must be the fastest of the three: if it took 10 ms to decide for a 100 ms run, about 9% of CPU time would be wasted on scheduling.
  • The scheduling algorithms it uses (FCFS, SJF, SRTF, Round Robin, Priority, multilevel queue) are the subject of Chapter 6.
  • It is present in every multiprogramming OS.

5.7Medium-Term Scheduler and Suspended States

Medium-Term Scheduler (MTS), also called the Swapping Scheduler: swaps processes out of main memory to secondary memory, where they become suspended, and later swaps them back in. This temporarily reduces the number of processes in memory.
🎓 From the lecture — Swapping and the two suspended states
  • Swapping is like exchanging two values: variable A = 5 and B = 10 become A = 10 and B = 5. Here, processes are swapped between states / memories.
  • Ready and Wait/Block are both in main memory. The new Suspend states, Suspend-Wait and Suspend-Ready, are both in secondary memory.
  • Scenario: main memory is "khachakhach bhari hui, housefull" (packed full). A very high-priority process arrives and must run first, but there is no space. So the MTS moves one process out of main memory into secondary memory. Space is freed, and the high-priority process comes in, executes and leaves.
  • If the evicted process was in Ready (wanting CPU time), it becomes Suspend-Ready. If it was in Wait/Block (doing I/O), it becomes Suspend-Wait. The name tells you where it came from.
  • Once the high-priority process finishes, the suspended processes are swapped back in: Suspend-Wait → Wait/Block and Suspend-Ready → Ready.
➕ Added for exam — Other reasons to suspend Besides making room for a high-priority process, a process may be suspended to improve the process mix (too many CPU-bound processes), because memory is over-committed / thrashing, at the user's request (Ctrl+Z in UNIX), at the parent's request, or for timing (a periodic process waiting for its next interval). Swapping is mainly used in time-sharing systems. Modern OSs usually swap pages rather than whole processes (Chapter 10).

5.8Summary of Process States (7-State Model)

🎓 From the lecture — Which memory each state refers to
  • Secondary memory: New (the LTS hasn't placed it in RAM yet), Suspend-Wait and Suspend-Ready.
  • Main memory: Ready, Running and Wait/Block (I/O).
  • Terminated: the process completed successfully. Its PCB is destroyed and it is removed from main memory, because its work is done.
StateMemoryMeaning
NewSecondaryBeing created; not yet admitted
ReadyMainWaiting for the CPU
RunningMainExecuting on the CPU
Wait / BlockedMainWaiting for I/O or an event
Suspend-ReadySecondarySwapped out while ready; needs swap-in plus CPU
Suspend-Wait (Suspend-Blocked)SecondarySwapped out while waiting. When its I/O completes while still swapped out, it moves to Suspend-Ready ADDED
Terminated—Finished; PCB destroyed, memory freed
🎯 IBPS exam alert Models are counted as 2-state (Running / Not running), 5-state (New, Ready, Running, Waiting, Terminated) and 7-state (5 + Suspend-Ready + Suspend-Wait). The transition Suspend-Wait → Suspend-Ready happens without coming back into memory: the I/O finished while the process was on disk. A New process can go straight to Suspend-Ready if memory is full.

5.9Degree of Multiprogramming

Degree of Multiprogramming (DoM): the number of processes present in main memory at a given time.
🎓 From the lecture
  • Aim: keep as many processes as possible in main memory, so that CPU utilisation stays high.
  • If only one process is in memory and it goes for I/O, the CPU is idle because there is nothing else to schedule. With more processes: P1 goes to I/O, so give the CPU to P2; P2 goes to I/O, so give it P3; P4 finishes, so give it P5. Options should always be available.
  • Example: P1 to P10 are in main memory, so the DoM = 10.
  • Which scheduler impacts DoM most? The long-term scheduler. It works between New and Ready and decides what enters main memory, so it has the most control. The STS has much less control.
  • The medium-term scheduler does somewhat the opposite: in some situations it reduces the DoM by moving processes from main memory out to secondary memory (suspended).
➕ Added for exam
  • A stable DoM means the average rate of process creation = the average departure rate of processes leaving the system. The LTS may be invoked only when a process leaves.
  • Increasing the DoM raises CPU utilisation only up to a point. Beyond that, processes lack enough memory frames, page faults explode, and the CPU spends its time swapping pages. This is thrashing (Chapter 10), and the fix is to reduce the DoM, which is exactly what the MTS does.
  • Chapter 1's formula still applies: CPU utilisation = 1 − pⁿ, where n = DoM.

5.9AProcess Creation, Termination & Hierarchy ADDED

  • Creation: a parent process creates children (e.g. fork() in UNIX, CreateProcess() in Windows), forming a process tree. Each process is identified by its PID. Linux's root process is systemd/init (PID 1).
  • Resource sharing options: the parent and children share all resources, share a subset, or share nothing.
  • Execution options: the parent runs concurrently with its children, or waits until they finish (wait()).
  • Address-space options: the child is a duplicate of the parent (fork), or the child loads a new program (exec).
  • Termination: a process ends with exit(), and the OS frees its resources and destroys its PCB. A parent may abort a child (kill()) if the child exceeds its resources, its task is no longer needed, or the parent is exiting.
  • Cascading termination: some OSs do not allow a child to exist after its parent terminates, so all descendants are terminated too.
  • Zombie (terminated, not yet waited for) and orphan (parent died, adopted by init): see Chapter 3.6A.
  • Independent vs cooperating processes: a cooperating process can affect or be affected by others, through shared data. This motivates IPC (shared memory and message passing) and synchronisation (Chapter 7).

⚡ Rapid Revision — Chapter 5

  • Cricket: players on the ground = active processes in RAM; players in the dressing room = passive programs on disk.
  • PCB = the process's "kundali", made by the OS for each process: PID (roll number), state, PC (next instruction, e.g. resume at i4), priority (kernel > user), registers, file list, I/O info, protection, plus OS-specific fields; textbook adds memory and accounting info. Linux: task_struct.
  • Context switch: save P1's registers (1,2,3) and PC in PCB1, load P2's from PCB2, and later restore P1. It is pure overhead. Efficiency = q/(q+s).
  • Dispatcher performs the switch; the time it takes is the dispatch latency.
  • 5 states: New → (admit) Ready → (dispatch) Running → I/O → Wait → (I/O done) Ready; Running → (preempt) Ready; Running → (exit) Terminated. Waiting → Running directly is impossible.
  • Queues: job queue (disk), ready queue (RAM, linked PCBs), device queues.
  • LTS = job scheduler, New→Ready, slowest; balances CPU-bound vs I/O-bound (selfie: all-CPU means starvation, all-I/O means idle CPU); controls the DoM.
  • STS = CPU scheduler, Ready→Running, fastest, runs about every 100 ms; the CPU must never be idle.
  • MTS = swapping scheduler; "housefull" memory with a high-priority arrival means swap out. Ready → Suspend-Ready, Wait → Suspend-Wait, both on disk; swapped back in later; reduces the DoM.
  • Secondary memory states: New, Suspend-Ready, Suspend-Wait. Main memory states: Ready, Running, Wait. Terminated: PCB destroyed.
  • DoM = number of processes in RAM (P1…P10 gives DoM 10). Higher DoM means higher CPU utilisation, until thrashing.
  • Creation: parent → child (fork/exec), process tree, init = PID 1. Termination: exit/abort, cascading termination.
