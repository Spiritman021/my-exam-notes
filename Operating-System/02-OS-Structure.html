Chapter 2

Operating System Structure

Chapter 1 established that the OS sits between the user and the hardware and does many management jobs. This chapter looks inside the OS: how its many components are arranged, how they interact, and what each arrangement costs in speed, safety and ease of change.

2.0What "OS Structure" Means

🎓 From the lecture An OS contains many components and modules. The structure of the OS tells you how they are arranged and organised, and how they interconnect and interact to carry out a function.
➕ Added for exam — Why structure matters A modern OS is huge (millions of lines of code). A good structure makes it:
  • Reliable: a bug in one part should not crash everything.
  • Secure: user programs should not reach the hardware directly.
  • Maintainable / extensible: new drivers and features can be added easily.
  • Fast: fewer boundary crossings mean less overhead.
These goals conflict. Speed favours a monolithic design; safety and extensibility favour a microkernel. Every structure below is a different trade-off.

Structures in order of evolution: Simple → Monolithic → Layered → Microkernel → Modular → Hybrid. Exokernels and virtual machines are specialised variants.

2.1Simple Structure (MS-DOS)

Simple structure: the simplest, loosely organised OS design with no well-defined structure and no protection boundaries. Layers exist, but application programs can bypass them and access the hardware (I/O, BIOS) directly.
🎓 From the lecture — Layers & the "fresher" analogy From top to bottom: Application programs → System programs → Device drivers → BIOS (Basic Input/Output System) device drivers. The user/application program can interact directly with I/O. That is easy, but dangerous: no proper structure is followed, so if a user program fails, the whole OS crashes.

It is like a company where a fresher can directly access the company's accounting information. While the fresher is well-behaved there is no problem. But if a mischievous one leaks the accounts to a competitor, the company crashes. The best example is MS-DOS.

AdvantagesDisadvantages
  • Easy to design and implement
  • Fast, with very few layers between the app and the hardware
  • Fits in very little memory (MS-DOS was built for small machines)
  • No protection: a buggy or malicious program can crash the whole system
  • Poorly separated functions make it hard to maintain and extend
  • No security, so it is unsuitable for multi-user use
➕ Added for exam — Why MS-DOS had no protection MS-DOS was written for the Intel 8088, which had no dual mode (user/kernel) and no hardware memory protection. The OS therefore had no way to stop an application touching hardware. MS-DOS was single-user, single-tasking and CLI-based (COMMAND.COM). Original UNIX is also listed under "limited structuring"; see 2.1A.

2.1AMonolithic Kernel Structure ADDED

Monolithic kernel: the entire OS (process management, memory management, file system, device drivers, networking, system-call interface) runs as one large program in kernel space, in a single address space. Any part can call any other part directly.
AdvantagesDisadvantages
  • Highest performance: services talk by direct function calls, with no message passing
  • Simple communication inside the kernel
  • A bug in any service, such as a driver, can crash the entire system
  • A large kernel is hard to maintain, debug and port
  • Adding a feature may mean recompiling the kernel (solved by modules, 2.3A)

Examples: traditional UNIX, Linux (monolithic but modular), BSD, Solaris, MS-DOS, Windows 9x.

⚠️ Exam trap (UNIX) The lecture says the layered approach is used in UNIX. In textbook terms (Galvin), traditional UNIX is a monolithic structure with limited layering: a kernel layer plus system programs. The classic pure layered OS is THE (Dijkstra, 1968). In MCQs: "Linux kernel type?" → Monolithic. "First layered OS?" → THE.

2.2Layered Structure

Layered structure: the OS is divided into a number of layers (levels), each built on top of the one below. Layer 0 (L0) is the hardware; the outermost layer (LN) is the user interface. Each layer uses only the services of layers below it.
🎓 From the lecture — Layers & the company hierarchy
  • The layers are independent of each other. The innermost layer, L0, is the hardware layer, and layers build up as L1, L2, L3…
  • The outermost layer is the UI (user interface) layer, which faces the user. The innermost is hardware-oriented.
  • Each layer holds its own specific task / functionality.
  • Hierarchy: a layer can use the services of the lower layer. L1 uses L0; L2 uses L1 and L0.
  • Company analogy: the fresher is at the bottom, with the manager, HR and founding members above. Everyone above can get work done by the fresher, who can't refuse ("just got the job!"). Upper layers consume lower layers' services.
  • It looks more complex because there are many layers, but a user program failure does not crash the system the way it does in the simple structure.
AdvantagesDisadvantages
  • Easy debugging and verification: debug L0 first, then L1 assuming L0 is correct, and so on. A bug is found in the layer being tested.
  • Modularity / abstraction: a layer only needs to know what the lower layer does, not how
  • A layer's implementation can change without affecting the others
  • Better protection than the simple structure
  • Hard to define layers carefully, because a layer can use only lower layers. Example: the backing-store driver must sit below memory management, yet it may need scheduling.
  • Less efficient / slower: a request passes through many layers, and each adds overhead (parameter passing)
  • Complex to design
🎯 IBPS exam alert (Layered) "The main advantage of the layered approach?" → Simplicity of construction and debugging. "Main disadvantage?" → Overhead / reduced performance and difficulty in defining layers. Examples: THE OS (Dijkstra), MULTICS (rings), and partially Windows NT and UNIX. The same layering idea appears in networking as the OSI / TCP-IP models.

2.3Microkernel Structure

Microkernel: the kernel is made as small as possible by removing all non-essential components from it and running them as ordinary user-space processes (servers). Only the bare essentials stay in kernel space: IPC, basic memory management and CPU scheduling. Components talk to each other by message passing through the microkernel.
🎓 From the lecture
  • The kernel is the "karta-dharta", the sole worker of the OS. It does everything itself and is the brain of the OS.
  • We make it lighter and smaller by removing all non-essential components. What remains is the microkernel.
  • There are two modes or spaces: user mode / user space and kernel mode / kernel space. The microkernel in kernel space keeps only a few chosen functions: IPC (inter-process communication), memory management and CPU scheduling.
  • Drivers, the file system and application programs run in user space and communicate with the microkernel via messaging. The microkernel talks to the hardware beneath it.
  • The system becomes lightweight, and new components can be added without modifying the kernel: just add them in user space.
  • The lecture's example is macOS. Limitation: however simple it looks, the implementation turns out to be complex.
AdvantagesDisadvantages
  • Easy to extend: new services are added in user space with no kernel change
  • More reliable and secure: if a driver or file server crashes, only that server fails and the kernel keeps running
  • Portable: only the small kernel needs porting to new hardware
  • Small kernel → easier to verify
  • Performance overhead: every service request needs message passing and repeated user↔kernel mode switches / context switches, so it is slower than monolithic
  • Complex to design and implement (as the lecture notes)
➕ Added for exam — Examples Pure or near-pure microkernels: Mach (Carnegie Mellon), QNX (cars, RTOS), MINIX 3, L4 family, Symbian, Redox, Google's Zircon (Fuchsia), seL4 (formally verified).
⚠️ Exam trap (macOS) The lecture calls macOS a microkernel example. Precisely, macOS/iOS use the XNU kernel, a hybrid of the Mach microkernel plus BSD UNIX components, all running in kernel space. If the options contain both "microkernel" and "hybrid", choose hybrid for macOS and Windows NT. If only micro and monolithic are offered, macOS → microkernel (Mach-based).

2.3AModular & Hybrid Structures ADDED

Modular structure: Loadable Kernel Modules (LKM)

Modular kernel: a small core kernel plus a set of loadable kernel modules (drivers, file systems, network protocols) that can be linked in or removed at run time without rebooting or recompiling. It uses object-oriented ideas: each module has a defined interface.
  • It resembles layered (each module has defined interfaces) but is more flexible, because any module can call any other.
  • It resembles microkernel (small core) but is faster, because modules run in kernel space and need no message passing.
  • Examples: Linux (insmod, rmmod, lsmod), Solaris, modern UNIX and macOS kernel extensions.

Hybrid kernel

Hybrid kernel: combines microkernel design (modular servers, message-based structure) with monolithic performance. Most services are kept inside kernel space for speed.
  • Examples: Windows NT family (Windows XP/7/10/11, Windows Server); macOS / iOS (XNU = Mach + BSD); Android = Linux kernel (monolithic + modules) plus a user-space framework.
  • Almost all modern OSs are hybrids. Pure designs are rare.

➕ Hypervisor types (frequently asked with cloud/virtualisation)
  • Type 1 (bare-metal / native): runs directly on hardware. Examples: VMware ESXi, Microsoft Hyper-V, Xen, KVM. Used in data centres and cloud.
  • Type 2 (hosted): runs on top of a host OS like an application. Examples: VirtualBox, VMware Workstation, Parallels.
  • The first virtual machine OS was IBM VM/370. The JVM (Java Virtual Machine) is a process VM, not a system VM.

🎯 IBPS exam alert (one-liners)
  • Linux → monolithic (modular) · Windows NT/10/11 → hybrid · macOS/iOS → hybrid (XNU, Mach-based) · QNX, MINIX → microkernel · MS-DOS → simple · THE → layered.
  • Microkernel components communicate by message passing. The main drawback is performance overhead.
  • The famous Tanenbaum–Torvalds debate (1992) was about microkernel (MINIX) vs monolithic (Linux).

2.4User Interfaces: CLI and GUI

🎓 From the lecture — Where the interface lies Besides the kernel ("karta-dharta"), the interface plays an equally important role: Kernel + Interface = Operating System. The OS sits between the user and the hardware, and between the user and the OS there is the interface. It decides how the user will interact with the OS. There are two types: CLI and GUI.

Command Line Interface (CLI)

  • The user types commands and gets results back as text. Used to run programs and check system requirements and attributes.
  • Needs technical knowledge: you have to be a technical person who remembers command syntax.
  • Examples: MS-DOS prompt, Windows Command Prompt (cmd), PowerShell, Linux/UNIX terminal (bash, sh, csh, ksh, zsh).

Graphical User Interface (GUI)

  • User-friendly, icon-based, and not very technical. Install an app, its icon appears, double-click it and it opens. Inside the app you work through further GUI elements.
  • Used by most people today. Examples: Windows desktop, macOS Finder, GNOME/KDE on Linux, Android/iOS home screens.
🎓 Lecture's rule of thumb A normal / naive user should go for the GUI. A tech-savvy person with good technical knowledge can work comfortably with the CLI.

➕ Added for exam — More interface facts
  • Galvin lists three UI types: CLI, GUI and batch interface (commands put in files, such as .bat or shell scripts, and executed).
  • Also: the touch-screen interface (gestures on mobiles/tablets), voice UI (Siri, Alexa, Google Assistant), menu-driven and form-based interfaces (ATM screens).
  • A shell is the program that implements the CLI (the command interpreter). In Windows it is cmd.exe / PowerShell; in UNIX/Linux it is sh (Bourne), bash (Bourne Again), csh (C shell), ksh (Korn) or zsh (the default on macOS).
  • Two ways a command interpreter can work: (1) the interpreter itself contains the code for each command; (2) as in UNIX, each command is a separate program file that the shell loads and runs. Option 2 makes new commands easy to add.
  • WIMP = Windows, Icons, Menus, Pointer, the core GUI elements. The GUI was pioneered at Xerox PARC (Xerox Alto, 1973) and popularised by Apple Macintosh (1984) and Microsoft Windows (1985).
  • In Linux, the GUI is a separate layer: the X Window System / Wayland plus a desktop environment (GNOME, KDE).
⚠️ Exam trap Shell ≠ kernel. The shell is the user-facing interpreter; the kernel is the core that talks to hardware. MS-DOS is CLI, not GUI. Windows 1.0–3.x were GUI shells running on top of MS-DOS. bash = "Bourne Again SHell".

⚡ Rapid Revision — Chapter 2

  • OS structure = how OS components are arranged, interconnected and interact. It is a trade-off between speed, protection and extensibility.
  • Simple (MS-DOS): Apps → System programs → Device drivers → BIOS. Apps can touch I/O directly, so an app failure crashes the OS ("fresher with access to the accounts"). Easy and fast but unsafe. The 8088 had no dual mode.
  • Monolithic: whole OS in one kernel-space program; fastest, but one bug crashes everything. UNIX, Linux.
  • Layered: L0 = hardware (innermost) … LN = user interface (outermost); a layer uses only lower layers (company hierarchy). Pro: easy debugging. Con: overhead and hard layer definition. THE OS, MULTICS.
  • Microkernel: remove non-essentials, keeping IPC + memory management + CPU scheduling in the kernel. Drivers and file system run in user space and use message passing. Pros: extensible, reliable, secure, portable. Con: IPC overhead and complex design. Mach, QNX, MINIX.
  • Modular: core + loadable kernel modules at run time (Linux insmod). Hybrid: microkernel design with monolithic speed. Windows NT, macOS XNU (Mach + BSD).
  • Exokernel: only multiplexes hardware. Nanokernel: tiny. VM: a hypervisor; Type 1 bare-metal (ESXi, Hyper-V), Type 2 hosted (VirtualBox).
  • OS = Kernel + Interface. The interface sits between the user and the OS.
  • CLI: type commands; needs technical knowledge; fast, scriptable, low resources (cmd, bash, PowerShell). GUI: icons and double-click; user-friendly; more resources (Windows, macOS). Galvin's third type is the batch interface.
  • Shells: sh, bash = Bourne Again SHell, csh, ksh, zsh. WIMP = Windows, Icons, Menus, Pointer. The GUI was born at Xerox PARC.
