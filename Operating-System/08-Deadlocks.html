Chapter 8

Deadlocks

Chapter 7 met deadlock twice: the flag array (both flags true, both waiting) and the dining philosophers (everyone holding a left fork). This chapter looks at deadlock in general: the four conditions that create it, and the four strategies for dealing with it, which are prevent, avoid (Banker's algorithm), detect and recover, or ignore.

8.0What is a Deadlock?

Deadlock: a set of processes in which each process holds some resource and waits for a resource held by another process in the set, so none of them can ever proceed. Time "stops" for them.
🎓 From the lecture — "Aap pehle" and the car jam
  • "Sir-ji, aap pehle!" One empty chair, two very polite people. "You sit first." "No, no, you first." Nobody ever sits, and the chair stays empty. That is the simplest example of deadlock.
  • Four cars at a crossing: each car can move only when the car ahead of it moves, and the ahead-chain loops back to itself. This is the "deadlock ka phera" (the deadlock loop).
  • Earlier: the flag array (both waiting for the other to set its flag false) and the dining philosophers (everyone holds a fork, the rice bowl is right there, nobody eats).
➕ Deadlock vs Starvation vs Livelock
DeadlockStarvationLivelock
Processes wait for each other forever; nobody progressesOne process waits indefinitely while others keep progressingProcesses keep changing state in response to each other but make no progress
All four conditions hold; circular waitCaused by unfair scheduling (priority, SJF)e.g. two people in a corridor both stepping aside the same way, again and again
Fixed by prevention, avoidance, detectionFixed by agingFixed by randomised back-off
Every deadlock implies starvation of the processes involved, but starvation does not imply deadlock.

8.1Deadlock Example: Processes Holding and Requesting Resources

🎓 From the lecture P1 holds R1 but also wants R2. P2 holds R2 but also wants R1. P1 releases R1 only after it finishes, and it can't finish without R2. P2 is in the same position. They depend on each other and just "wait, wait, wait".
  • Arrow resource → process = the resource is assigned (held).
  • Arrow process → resource = the process is requesting it.

8.2Necessary Conditions for Deadlock

Coffman's four conditions (1971): a deadlock can occur only if all four hold simultaneously.

#ConditionMeaning
1Mutual ExclusionAt least one resource is non-sharable: only one process can use it at a time
2Hold and WaitA process holds at least one resource and waits for more held by others
3No PreemptionResources can't be forcibly taken away; a process releases them voluntarily, only after finishing
4Circular WaitA cycle P0 → P1 → … → Pn → P0 where each waits for a resource held by the next
🎓 From the lecture — The four-legged chair Deadlock is a chair with four legs, one leg per condition. Only when all four legs are strong can you "sit on the deadlock chair". Break even one leg and the chair falls: no deadlock. This idea leads directly to prevention.

If P1 waits for P2's R2 but P2 does not want R1, there is no circle. P2 finishes, releases R2, P1 takes it, and there is no deadlock. "All conditions must hold."

⚠️ Exam trap The four conditions are necessary, not sufficient (in general). With single-instance resources, circular wait is both necessary and sufficient. Circular wait also implies hold and wait, so the four conditions are not completely independent.

8.3Deadlock Handling Methods

🎓 From the lecture Prevention: "prevention is always better than cure"; deadlock must never happen, which is very strict. Avoidance is a lighter, less strict version. Detection and recovery: it has happened, so detect it and then recover. Ignorance: "Deadlock? What's that?" As you move left to right, strictness decreases.

8.4Deadlock Prevention: Violating Mutual Exclusion

🎓 From the lecture "Drive slow to prevent accidents." Here the accident is deadlock. Can we break mutual exclusion? Some resources (read-only files) can be shared, but others (a printer takes one command from one process at a time) are inherently non-sharable. "Not all resources can be made sharable", so in general this leg can't be broken. "Yahan to daal nahi gali" (no luck here).
➕ Partial trick Spooling makes a printer look sharable: jobs go to a disk spool and only the printer daemon touches the printer. But this doesn't work for every resource, for example a mutex lock or a semaphore.

8.5Deadlock Prevention: Violating Hold and Wait

🎓 From the lecture — three ways
  1. Get everything before running: P1 needs R1, R2, R3, so it must acquire all of them first, or it is not allowed to run. It can't ask for more mid-way. This is expensive: the process waits until all are free.
  2. Release before requesting: P1 holds R1 and wants R2, so it must release R1 first and only then gets R2. "A better approach", because maybe someone else needed R1.
  3. Time-out on waiting: a process may hold a resource for a limited time (e.g. 5 minutes). When the time-out expires, it must release it.
➕ Drawbacks (Galvin) Low resource utilisation (resources are allocated long before they are used) and starvation (a process needing several popular resources may wait forever).

8.6Deadlock Prevention: Violating No Preemption

🎓 From the lecture Allow preemption based on priority. P1 is running and holds R1, R2 and R3. A higher-priority P2 arrives and needs them. Preempt P1, so its resources are released, and P2 acquires them and runs.
➕ Textbook rules and limits
  • If a process holding resources requests one that cannot be granted immediately, all its held resources are preempted (implicitly released). It restarts only when it can get the old and new ones together.
  • Alternatively, take the resource from a waiting process that holds it.
  • This works only for resources whose state can be saved and restored: CPU registers and memory. It does not work for printers, tape drives or mutex locks.

8.7Deadlock Prevention: Violating Circular Wait

Resource ordering: number every resource type (R1 < R2 < R3 …). A process may request resources only in increasing order of these numbers.
🎓 From the lecture P1 holds R1 and requests R2, which is fine because the order increases. P2 holds R2, so it may request R3, R4, R5 … R100, but never R1 (a lower number). The edge P2 → R1 that would close the circle is forbidden, so no circular wait and no deadlock. "A very beautiful thing."
➕ Why it works Suppose a cycle existed: P0 waits for R(1), held by P1 waiting for R(2), and so on. Then the resource numbers would satisfy F(R0) < F(R1) < … < F(R0), which is impossible. Resource ordering is the most practical prevention technique; Linux lock-ordering rules (and tools like lockdep) use it. It is also why the reversed philosopher in Chapter 7.37 works.
ConditionHow to violate itPractical?
Mutual exclusionMake resources sharable✗ Mostly impossible
Hold and waitRequest all at once / release before requesting / time-outPossible; poor utilisation, starvation
No preemptionPreempt resources (by priority)Only for CPU and memory
Circular waitTotal ordering of resources, request in increasing order✔ Most practical

8.8Deadlock Avoidance

Avoidance: "if we can't prevent it, avoid it." Before granting each request, the OS checks whether granting it keeps the system in a safe state. It needs advance information: the maximum number of each resource every process may ever need.
🎓 From the lecture It is less strict than prevention, but has an overhead: the full requirement list of every process (which resources and how many) must be given to the system in advance, its complete "kundali". This is what the Banker's algorithm uses. (The lecturer's glasses fell off from excitement here!)
➕ Two avoidance algorithms
  • Single instance per resource type: use the Resource-Allocation Graph with claim edges (dashed P → R, "may request in future"). Grant a request only if converting it into an assignment edge creates no cycle.
  • Multiple instances: use the Banker's algorithm (Dijkstra). It is named after a banker who never lends cash in a way that leaves him unable to satisfy all his customers.

🎓 Lecture's recipe If Available ≥ Need, fulfil that process. It completes and releases what it held; add that to the old Available to get the new Available. Repeat with the new Available on the processes still pending, until all are done and a safe sequence is formed.
⚠️ Exam trap (What gets released?) When a process finishes, the new Available = old Available + its Allocation. The lecture describes it as "allocation + need", which gives the same number here only because P1's Need happened to equal the Available. In general, use Available + Allocation: the need was lent and returned, so it cancels out.

8.9ABanker's Full Algorithm, Request Numerical ADDED

Essential data structures (n processes, m resource types)
Available[m] – free instances of each type Max[n][m] – maximum demand of each process (declared in advance) Allocation[n][m] – currently allocated Need[n][m] = Max − Allocation Time complexity of safety algorithm: O(m × n²)

Safety algorithm

  1. Work = Available; Finish[i] = false for all i.
  2. Find i with Finish[i] = false and Need[i] ≤ Work. If none exists, go to step 4.
  3. Work = Work + Allocation[i]; Finish[i] = true; go to step 2.
  4. If Finish[i] = true for all i, the state is safe. Otherwise it is unsafe.

Resource-request algorithm (process Pi requests Request[i])

  1. If Request ≤ Need[i], continue. Otherwise it is an error (the process exceeded its declared max).
  2. If Request ≤ Available, continue. Otherwise Pi must wait.
  3. Pretend to allocate: Available −= Request; Allocation[i] += Request; Need[i] −= Request.
  4. Run the safety algorithm. If safe, grant. If unsafe, roll back and make Pi wait.
Numerical 2 (Galvin classic): 5 processes, A = 10, B = 5, C = 7
ProcessAllocation A B CMax A B CNeed = Max − Alloc
P00 1 07 5 37 4 3
P12 0 03 2 21 2 2
P23 0 29 0 26 0 0
P32 1 12 2 20 1 1
P40 0 24 3 34 3 1
Available = (10,5,7) − (7,2,5) = (3,3,2).
Safety: P1 (1,2,2 ≤ 3,3,2) → Work (5,3,2) · P3 (0,1,1) → (7,4,3) · P4 (4,3,1) → (7,4,5) · P0 (7,4,3) → (7,5,5) · P2 (6,0,0) → (10,5,7).
Safe sequence ⟨P1, P3, P4, P0, P2⟩. Other safe sequences may exist; any one proves safety.

Request: P1 asks for (1,0,2).
Step 1: (1,0,2) ≤ Need P1 (1,2,2) ✔. Step 2: ≤ Available (3,3,2) ✔.
Step 3: pretend. Available = (2,3,0), Alloc P1 = (3,0,2), Need P1 = (0,2,0).
Step 4: safety. P1 (0,2,0) → (5,3,2), P3 → (7,4,3), P4 → (7,4,5), P0 → (7,5,5), P2 → (10,5,7). This is safe, so the request is granted.
Follow-ups: P4 then requests (3,3,0): (3,3,0) ≤ Available (2,3,0) fails, so P4 must wait. P0 then requests (0,2,0): this leaves Available (2,1,0), with which no process's Need can be met, so the state is unsafe and P0 waits, even though the resources are physically free.

8.10Safe and Unsafe States

🎓 From the lecture If you can build a safe sequence, you are in the safe area and 100% guaranteed no deadlock. If no safe sequence exists, you are in the unsafe area, and that is where deadlock lives.
⚠️ Exam trap Safe state → no deadlock (guaranteed). Unsafe state ≠ deadlock: an unsafe state only may lead to deadlock, for example if processes ask for their full Max. Deadlock ⊂ unsafe. Avoidance keeps the system out of the whole unsafe region.

8.11Deadlock Detection

🎓 From the lecture "You couldn't prevent it and couldn't avoid it, and the deadlock has occurred. At least detect it first, then recover." The Banker's-style check (can a safe sequence be formed?) and the Resource Allocation Graph help in detection.
➕ Detection algorithms
  • Single instance of each resource: build a wait-for graph (WFG) by removing the resource nodes from the RAG. Pi → Pj means Pi waits for Pj. A deadlock exists if and only if the WFG has a cycle. Cycle detection costs O(n²).
  • Multiple instances: a Banker's-like algorithm using Available, Allocation and the Request matrix (current requests, not Max). Processes left with Finish = false at the end are deadlocked.
  • How often to run it? On every request (expensive), at fixed intervals, or when CPU utilisation drops below about 40%.

8.12Deadlock Recovery: Process Termination

🎓 From the lecture
  1. Abort all deadlocked processes (P1, P2, P3, P4) at once: "nobody is going to finish anyway."
  2. The lenient approach: abort one at a time. Kill P1, check whether the deadlock is resolved; if not, kill P3 and check again, and so on.
➕ Choosing the victim (minimum cost) Abort-all is expensive: lots of computation is lost. Abort-one-at-a-time has the overhead of rerunning detection after every kill. Victim-selection criteria: the process's priority; how long it has run and how much remains; resources it holds (and of what type); resources it still needs; how many processes must be terminated; and whether it is interactive or batch.

8.13Deadlock Recovery: Resource Preemption and Rollback

🎓 From the lecture Resources caused the problem, so preempt them. Take P1 and roll it back step by step, as in DBMS when conflicts occur. After each rollback step, check whether the released resource has broken the deadlock. If so, stop rolling back.
➕ Three issues (Galvin)
  1. Selecting a victim: which process and resources to preempt, at minimum cost.
  2. Rollback: return the process to a safe checkpoint, or a total rollback (restart it).
  3. Starvation: the same process may be picked as victim every time. Fix: count the number of rollbacks in the cost factor.

8.14Deadlock Ignorance (Ostrich Algorithm)

🎓 From the lecture — the ostrich When danger comes, the ostrich buries its head in the sand and acts as if nothing happened ("danger ke liye to main danger hoon"). In the same way, the OS assumes "no concept of deadlock exists". Deadlock is treated as a very rare event, and the cost of handling it (all the checks and overhead of prevention and avoidance) is very high. Spending that much on a rare event makes no sense. Popular OSs do exactly this.
➕ In practice Windows and UNIX / Linux use the ostrich approach for general resources. If the system hangs, the user or administrator reboots or kills the process. Application developers are expected to avoid deadlocks themselves, for example through lock ordering. Databases, by contrast, detect and recover (they abort a victim transaction).

8.15Resource Allocation Graph (RAG)

Resource Allocation Graph: a directed graph G = (V, E). The vertices are processes (circles) and resource types (rectangles), with a dot for each instance. The edges are request edges (Pi → Rj) and assignment edges (Rj → Pi).
🎓 From the lecture Vertices (nodes) are either processes (circles: P1, P2, P3…) or resources (rectangles). A resource can be single-instance (one dot) or multi-instance (several dots; R1 with 3 instances has 3 dots). Edges: resource → process = assigned (the process holds it); process → resource = request.

8.16Detecting Deadlock using RAG: Single-Instance Example

🎓 From the lecture — the golden rules
  • No cycle → 100% no deadlock.
  • Cycle exists → deadlock may or may not be present. "Get rid of the misunderstanding that a cycle always means deadlock."
  • Cycle + all resources in it single-instance → deadlock for sure.
Numerical 3 (lecture): single-instance cycle R1 (1 instance) is held by P0, and R2 (1 instance) is held by P1. P0 requests R2 and P1 requests R1 (Figure 8.2 with P0/P1).
ProcessAllocation R1 R2Request R1 R2
P01 00 1
P10 11 0
Available = (1,1) − (1,1) = (0,0). Neither request can be met, so no safe sequence exists.
Conclusion: a cycle, single-instance resources and no safe sequence: DEADLOCK ✔.

8.17Cycle with Multi-Instance Resources (No Deadlock)

🎓 From the lecture Same picture, but R1 and R2 each have 2 instances. One instance of each is allocated, so Available = (1,1) and Requested = (1,1). The free R2 goes to P0 and the free R1 goes to P1. A safe sequence exists, so there is no deadlock, even though a cycle is visible.
➕ The full decision table
RAGSingle instance per resourceMultiple instances
No cycleNo deadlockNo deadlock
CycleDeadlock (certain)May or may not: check with the detection or Banker's algorithm
A multi-instance cycle is a deadlock when every instance in the cycle is held by a process inside the cycle and no outside process can release one.

8.18Minimum-Resource Numericals & Comparisons ADDED

Essential formula: deadlock-freedom with one resource type
n processes, each needing at most k instances of a resource. Worst case: every process holds (k − 1) and waits for 1 more. Deadlock is IMPOSSIBLE if R ≥ n(k − 1) + 1 More generally (process i needs kᵢ): R ≥ Σ(kᵢ − 1) + 1
Q1. 3 processes, each needing 2 tape drives. Minimum drives for no deadlock? 3(2−1)+1 = 4. With 3 drives, each could hold 1 and wait, which is a deadlock.
Q2. 6 tape drives, each process needs 3. Maximum processes that are guaranteed deadlock-free? n(3−1)+1 ≤ 6 → 2n ≤ 5 → n = 2.
Q3. Processes need 3, 4 and 5 units. Minimum units? (2 + 3 + 4) + 1 = 10.
Q4. R = 10, each of n processes needs 4. Largest n that is deadlock-free? 3n + 1 ≤ 10 → n = 3.

🎯 IBPS exam alert (one-liners)
  • The four necessary conditions: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait (Coffman).
  • Banker's algorithm = avoidance (not prevention, not detection). It needs Max in advance. Need = Max − Allocation.
  • The most practical prevention: resource ordering (breaks circular wait). The condition that cannot generally be broken: mutual exclusion.
  • Safe ⇒ no deadlock; unsafe ⇒ possible deadlock. RAG cycle + single instance ⇒ deadlock.
  • Wait-for graph is used for detection with single-instance resources.
  • Windows and Linux use the ostrich algorithm.

⚡ Rapid Revision — Chapter 8

  • Deadlock: every process in a set holds something and waits for another's resource, forever. Analogies: "aap pehle" with one chair, four cars at a crossing, the dining philosophers.
  • Example: P1 holds R1 and wants R2; P2 holds R2 and wants R1. Arrows: R→P = assigned, P→R = request.
  • 4 conditions (the four-legged chair; break one leg and there is no deadlock): Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait. All must hold.
  • Handling (strict → lenient): Prevention → Avoidance → Detection + Recovery → Ignorance.
  • Prevention: ME can't be broken (printer). H&W: get everything first, release before requesting, or time-out. No preemption: preempt by priority (CPU and memory only). Circular wait: request in increasing resource order (the best method).
  • Avoidance: needs every process's requirements in advance. Banker's: if Need ≤ Available, run it, then Available += Allocation. Lecture: total (5,5,5), Available (0,1,2) → safe sequence ⟨P1, P0, P2⟩. Galvin: ⟨P1, P3, P4, P0, P2⟩.
  • Safe ⇒ no deadlock; unsafe ⇒ may deadlock; deadlock ⊂ unsafe.
  • Detection: wait-for graph (single instance) or a Banker's-like algorithm with the Request matrix.
  • Recovery: kill all or one at a time; preempt resources and roll back (watch for starvation of the victim).
  • Ostrich: ignore deadlock because it is rare and handling it is costly (Windows, UNIX).
  • RAG: circles are processes, boxes are resources, dots are instances. No cycle ⇒ no deadlock. Cycle + single instance ⇒ deadlock. Cycle + multi-instance ⇒ maybe (lecture: Available (1,1) = Request (1,1), so a safe sequence exists and there is no deadlock).
  • Minimum resources: R ≥ n(k−1) + 1 (3 processes needing 2 each → 4).
