Chapter 4

Threads

Chapter 3 ended with a problem. fork() lets us create identical workers, but each child is a full process with its own PCB, memory and resources: "wages for every worker". Threads solve this. Instead of hiring new workers, we give the same worker more hands.

4.0From fork() to Threads: The 8-Hands Analogy

🎓 From the lecture — The magic boon (vardaan) Same scenario: a 1,000-brick wall in one day. This time the contractor says, "I have magic powers. I won't bring more workers like you, because I'd have to pay each of them separately. Instead, I'll add more hands to you."
  • 2 hands → 4 → 6 (3 on each side) → full capacity: 8 hands (4 on each side). "Now you can't argue that you only have two hands!"
  • The key point: the contractor still pays only one worker. The work gets done cheaply.
  • The core is common: the torso, body, digestive system, respiratory system and brain stay the same. Only hands are added. These hands are the threads.

4.1Threads as Lightweight Processes

Thread: the basic unit of CPU utilisation, a single sequential flow of execution within a process. A thread is also called a Lightweight Process (LWP), because creating it and switching between threads is much cheaper than for a process.
🎓 From the lecture The work is done "saste mein" (cheaply), which is why a thread is called a lightweight process. The main expense, the core, is not repeated. Only hands are added.
➕ Added for exam — What a thread owns vs shares
Private to each threadShared by all threads of the process
  • Thread ID
  • Program counter (PC)
  • Register set
  • Stack (its own local variables and function calls)
  • Thread state, priority
  • Code (text) section
  • Data section (global variables)
  • Heap
  • Open files, signals
  • Address space, PCB, process ID
The per-thread information is stored in a TCB (Thread Control Block), which is much smaller than a PCB.
⚠️ Exam trap (PCB vs TCB) The lecture says "no PCB is made for a thread". That is right: threads share the process's single PCB. But a thread is not tracked by nothing; each thread has its own small TCB holding its thread ID, PC, registers, stack pointer and state. MCQ: "Which is NOT shared between threads?" → Stack / registers / program counter.

4.2Single-Threaded vs Multi-Threaded Processes

🎓 From the lecture
  • A single-threaded process has only one thread, one hand.
  • A multi-threaded process P has multiple threads: T1, T2 and T3 are hands added to the process. No new process was created from scratch and no duplicate was made.
  • The code, data and files part stays common to all the hands. It is the "core" of the process, so there is no need to create it again.
  • The PCB is one per process; no separate PCB is made per thread.
  • Context switching between threads is easier and faster than between processes.
  • The OS's view: for user-level threads, the OS sees only one process through its own eyes. Internally, at our end, we have created several threads, but the OS doesn't know about them. (This matters in 4.5.)

4.3Example: Multiple Tabs in a Browser

🎓 From the lecture "Arre sir, this is our daily routine!" You open one browser, which is the core body, and inside it you open many different tabs. The browser is the process, and the tabs are like threads working inside it on the same shared base.
➕ Added for exam — Other classic multithreading examples
  • Word processor: one thread displays graphics, one reads keystrokes and one does spell-check / auto-save in the background. This is Galvin's standard example.
  • Web server: one thread per client request, so thousands of users are served by one server process.
  • Media player: one thread decodes audio, one decodes video and one handles the UI.
  • Banking server: many teller threads update shared account data, which needs synchronisation (Chapter 7).
⚠️ Exam trap (Chrome tabs) Modern Google Chrome actually uses a multi-process architecture: each tab or site usually gets its own renderer process, so one crashing tab does not kill the others. The lecture's tabs-as-threads idea is a good intuition, and each process is itself multi-threaded. If an MCQ asks specifically about Chrome's architecture, the answer is multi-process.

4.4Need and Benefits of Threads

🎓 From the lecture — Four benefits
  1. Creating a new thread in the current process takes less time and effort than creating a new process from scratch.
  2. Threads can share common data: code, data and files are in a shareable mode.
  3. Context switching is quicker and easier.
  4. A thread can be terminated in less time: in less time than it takes to say "close it".
➕ Added for exam — Galvin's four benefits (memorise as R-R-E-S)
BenefitMeaning
ResponsivenessIf one thread is blocked or doing a long task, others keep the app responsive (the UI does not freeze while a file downloads).
Resource sharingThreads share memory and resources by default. Processes need explicit IPC (shared memory or message passing).
EconomyCheaper to create and context-switch. In Solaris, creating a process is about 30× slower than creating a thread, and a context switch is about 5× slower.
ScalabilityOn multicore / multiprocessor machines, threads can run in parallel on different cores. A single-threaded process can use only one core.
🎯 IBPS exam alert "Which is not a benefit of multithreading?" Distractors include "increased protection between threads" and "isolation". Threads share memory, so one buggy thread can corrupt the data of others and crash the whole process. Processes are better isolated than threads.

  • Concurrency: several tasks make progress by interleaving. Possible on one core.
  • Parallelism: several tasks run at the same instant. Needs multiple cores/CPUs.
  • Data parallelism: the same operation on different parts of the data (sum of the first half and second half of an array on two cores). Task parallelism: different operations run on different cores.
Essential formula: Amdahl's Law
Speedup ≤ 1 / ( S + (1 − S) / N ) S = serial (non-parallelisable) fraction, N = number of cores Maximum speedup as N → ∞ = 1 / S
Given: an application is 25% serial (S = 0.25) and 75% parallel.
Step 1 (N = 2): 1 / (0.25 + 0.75/2) = 1 / (0.25 + 0.375) = 1 / 0.625 = 1.6×
Step 2 (N = 4): 1 / (0.25 + 0.75/4) = 1 / (0.25 + 0.1875) = 1 / 0.4375 = 2.29×
Step 3 (N → ∞): 1 / 0.25 = 4×
Conclusion: the serial part limits the gain. Even infinitely many cores cannot make this program more than 4× faster.
➕ Multicore programming challenges (Galvin) Identifying tasks that can run separately · Balance (tasks should do equal work) · Data splitting · Data dependency (needs synchronisation) · Testing and debugging (many execution orders). Hyper-Threading (Intel SMT) makes one physical core appear as two logical cores by running two hardware threads.

4.5User-Level vs Kernel-Level Threads

User-Level Threads (ULT): created and managed in user space by a thread library inside the application. The kernel does not know they exist; it sees only one process.

Kernel-Level Threads (KLT): created, scheduled and managed directly by the OS kernel. The kernel knows about each thread.
🎓 From the lecture
  • ULTs are managed by the user / applications at the user end.
  • Their big plus is a faster context switch, even compared with kernel-level threads.
  • Their big "duvidha" (problem): a ULT can get the entire process blocked. The OS sees the three threads as one entity, so if something goes wrong in one thread, the OS can't block just that thread, because it doesn't know threads exist. It blocks the whole process, and the other threads suffer too.
  • KLTs are managed by the OS itself. There is no effect of one kernel-level thread on another. Their context switch is slower than ULTs'.
  • Context-switch time order: ULT (least) < KLT < Process (most).

⚠️ Exam trap (Why the whole process blocks) The textbook reason is not that the OS "detects a malicious thread". When one ULT makes a blocking system call (e.g. read() waiting for disk), the kernel sees the process make that call and puts the entire process into the waiting state. All its other ULTs stop, even though they were ready to run.

4.6Multithreading Models: Many-to-One

User threads must ultimately run on kernel threads. A multithreading model describes how user-level threads are mapped to kernel-level threads. There are three, and the lecture covers all three.

Many-to-One: many user-level threads are mapped to a single kernel-level thread. Thread management is done by the thread library in user space.
🎓 From the lecture — Disadvantages
  • If any one thread makes a blocking system call, the entire process gets blocked.
  • Because all ULTs map to one KLT, only one user thread at a time can access the kernel thread.
➕ Added for exam
  • Advantage: efficient, because thread management happens in user space with no kernel calls.
  • Cannot exploit multicore: only one thread can be in the kernel at a time, so there is no true parallelism.
  • Examples: Solaris Green Threads, GNU Portable Threads. It is rarely used today.

4.7One-to-One Model

One-to-One: each user-level thread is mapped to its own kernel-level thread.
🎓 From the lecture This is the solution to many-to-one's problem. Even if one user thread makes a blocking system call, the others are not affected and stay in the active running state.
AdvantagesDisadvantages ADDED
  • More concurrency: a blocking call does not block the others
  • True parallelism: threads can run on multiple cores
  • Creating a user thread means creating a kernel thread, which is overhead
  • Too many kernel threads burden the system, so many OSs limit the number of threads

Examples ADDED: Linux, the Windows family (95 onwards) and modern macOS. This is the model most used today.

4.8Many-to-Many Model

Many-to-Many: many user-level threads are multiplexed onto a smaller or equal number of kernel-level threads.
🎓 From the lecture Both sides are "many". The mapping follows an "equal to" or "less than" rule: with 2 user threads, you can map them to 2 kernel threads (equal) or to 1 (less than). With 1 user thread, map it to 1 kernel thread.
➕ Added for exam
  • Best of both: developers can create as many user threads as needed, which are cheap, and the corresponding kernel threads can still run in parallel on a multiprocessor. When one thread blocks, the kernel can schedule another.
  • Disadvantage: complex to implement.
  • Two-level model: a variation of many-to-many that also allows a user thread to be bound to its own kernel thread (one-to-one for important threads). Example: older Solaris (before version 9), IRIX, HP-UX.
  • Examples of many-to-many: Solaris before version 9, Windows with the ThreadFiber package.
  • Many-to-many and two-level models use an intermediate structure called an LWP (Lightweight Process): a virtual processor that a user thread runs on. The kernel informs the thread library of events through upcalls (scheduler activations).

4.8AThread Libraries, Threading Issues & Thread Pools ADDED

Thread libraries (APIs for creating and managing threads)

LibraryNotes
POSIX PthreadsThe IEEE 1003.1c standard. Can be user- or kernel-level. Used on UNIX, Linux and macOS. pthread_create(), pthread_join(), pthread_exit().
Windows threadsKernel-level. CreateThread(), WaitForSingleObject().
Java threadsManaged by the JVM and implemented on the host OS's library. Created by extending Thread or implementing Runnable; started with start() (not run()).

Implicit threading: the compiler or runtime creates the threads

  • Thread pool: create a fixed number of threads in advance at start-up and keep them waiting in a pool. When a request arrives, take a free thread; when it finishes, it returns to the pool. This is faster than creating a thread per request and limits the total number of threads. Used by web servers and Java's ExecutorService.
  • Fork-Join, OpenMP (#pragma omp parallel), Grand Central Dispatch (Apple), Intel TBB.

Threading issues

IssueKey point
fork() and exec() in a multithreaded programDoes fork duplicate all threads or only the calling one? UNIX offers both versions. If exec() is called right after fork(), duplicating only the calling thread is enough, because exec replaces everything.
Signal handlingDeliver the signal to the thread it applies to, to every thread, to certain threads, or to a designated signal-handling thread.
Thread cancellationTerminating a thread before it finishes (the target thread). Asynchronous cancellation: terminate immediately, which is risky because resources may not be freed. Deferred cancellation: the target periodically checks whether it should terminate, which is safer and the default in Pthreads.
Thread-Local Storage (TLS)Data each thread keeps its own copy of (e.g. a per-thread transaction ID). It differs from local variables because it persists across function calls.
Scheduler activationsThe kernel–library communication (upcalls via LWPs) used in M:N models.
🎯 IBPS exam alert (one-liners)
  • A thread is called a lightweight process. It is the basic unit of CPU utilisation, while the process is the unit of resource ownership.
  • Threads share code, data, heap and files. They have their own stack, registers, PC and thread ID.
  • Many-to-one → whole process blocks, no parallelism. One-to-one → Linux, Windows. Many-to-many → user threads ≥ kernel threads.
  • Thread states mirror process states: New → Ready → Running → Waiting/Blocked → Terminated.
  • In Java, calling run() directly does not create a new thread; start() does.

⚡ Rapid Revision — Chapter 4

  • Thread = unit of execution inside a process = Lightweight Process. The lecture's analogy: instead of hiring identical workers (fork, so wages for each), give one worker 8 hands, so you pay one wage and share one body.
  • Shared: code, data, heap, open files, PCB. Private: thread ID, PC, registers, stack, held in a TCB.
  • Single-threaded = one flow. Multi-threaded = many flows sharing the core. For ULTs, the OS sees only one process.
  • Examples: browser tabs (lecture; note that Chrome is really multi-process), word processor (spell-check thread), web server (thread per client).
  • Lecture benefits: less time to create, shares data, fast context switch, fast termination. Galvin's: Responsiveness, Resource sharing, Economy, Scalability.
  • Concurrency = interleaving (one core). Parallelism = simultaneous (multicore). Amdahl: speedup ≤ 1/(S + (1−S)/N), and the maximum is 1/S.
  • ULT: library-managed, kernel unaware, fastest switch, but one blocking call blocks the whole process and it cannot use multiple cores. KLT: kernel-managed, independent, parallel, slower switch.
  • Context-switch cost: ULT < KLT < Process.
  • Many-to-One: M ULT → 1 KLT; a blocking call blocks all; one thread in the kernel at a time (Green Threads). One-to-One: each ULT has its own KLT; no blocking issue but overhead (Linux, Windows). Many-to-Many: M ULT → N KLT with N ≤ M, flexible and parallel (Solaris < 9). Two-level = M:N plus binding.
  • Libraries: Pthreads, Windows threads, Java threads (Thread / Runnable, start()). Thread pool = pre-created threads reused per request.
  • Issues: fork/exec semantics, signals, cancellation (asynchronous vs deferred), TLS, scheduler activations.
