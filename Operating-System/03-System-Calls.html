Chapter 3

System Calls

Chapter 2 split the OS into user space and kernel space, with the hardware under the kernel's control. That raises a question: if a user program is not allowed to touch the hardware, how does it print, read a file or create a process? The answer is the system call, a controlled doorway from user space into the kernel. The lecture calls this "very important; many questions are asked on it".

3.0What is a System Call?

System call: the programmatic way in which a user program requests a service from the kernel of the OS, for anything that needs the hardware or privileged operations. It is the interface between a running process and the operating system.
🎓 From the lecture — "Mummy & the kitchen" analogy You are on the sofa watching "Five Minutes Engineering" before tomorrow's exam, and you get hungry. Two options:
  1. Option 1: go into the kitchen yourself, gather the Maggi ingredients and masala, chop the vegetables, cook, plate and eat. But with Mummy at home, the kitchen is her "Mahishmati Samrajya", and you don't dare step in. This option doesn't really exist.
  2. Option 2: say, "Mummy, I'm hungry, give me something to eat." Mummy does the whole task on your behalf and hands you ready-made food. You get the same end result.
In the same way, the user program needs something from the hardware, but the OS has sole authority over the hardware. So the program "gives a call" to the OS, a system call (SC), and the OS gets the work done from the hardware on its behalf.

3.0AHow a System Call Works (API, Trap, Parameters) ADDED

Programmers rarely call system calls directly. They call an API (Application Programming Interface) function from a library, which in turn makes the system call.

APIUsed on
POSIX API (via the C library libc)UNIX, Linux, macOS
Win32 / Windows APIWindows
Java API (runs via the JVM)Any OS with a JVM
  • Each system call has a number. The system-call interface keeps a table indexed by these numbers and invokes the matching kernel routine.
  • The caller does not need to know how the call is implemented. It only obeys the API and understands the result; the OS hides the details.
  • Most system calls are written in C/C++, with the lowest-level parts in assembly.

Three ways to pass parameters to the OS

MethodHowNote
1. RegistersPut parameters in CPU registersFastest, but limited by the number of registers
2. Block / table in memoryStore parameters in a memory block and pass its address in a registerNo limit on count or length. Used by Linux and Solaris.
3. StackThe program pushes parameters onto the stack; the OS pops themNo limit on count or length
⚠️ Exam trap (Library function vs system call) printf(), scanf(), malloc() and fopen() are library functions, not system calls. Internally they call system calls: printf → write(), scanf → read(), malloc → brk()/mmap(), fopen → open(). Library functions run in user mode; system calls switch to kernel mode.

3.1Types of System Calls

🎓 From the lecture Different system calls exist for different scenarios and tasks. The lecture groups them into process control (create, end, load, execute, terminate, wait, allocate/free memory, fork), file management (create, open, close, delete, read, write, get/set attributes, permissions), device management (request/release device, read, write, reposition), information maintenance (get system time, system data, process ID, attributes) and communication (create/delete connection, pipe, send/receive data).

🎯 IBPS exam alert Galvin lists six categories: Process control, File management, Device management, Information maintenance, Communication and Protection. The lecture covered five, so don't forget Protection. Typical MCQ: "getpid() belongs to?" → Information maintenance. "pipe()?" → Communication. "chmod()?" → Protection.

3.2User Mode and Kernel Mode (Mode Bit)

Dual-mode operation: the CPU runs in one of two modes, set by a hardware mode bit. Mode bit = 1 → User mode; mode bit = 0 → Kernel mode. This protects the OS and hardware from errant or malicious user programs.
🎓 From the lecture — Mode bit & the kitchen again
  • m = 1 (User mode): you are anywhere in the house (hall, bedroom, bathroom) except the kitchen. Your application programs run here.
  • m = 0 (Kernel mode): you have stepped into the "Mahishmati Samrajya", the kitchen, where the core OS functionality runs.
  • Other names for kernel mode: master mode, privileged mode, system mode. It is privileged enough to perform core functions.
  • Other names for user mode: slave mode, unprivileged (non-privileged) mode.
BasisUser modeKernel mode
Mode bit10
Also calledSlave / unprivileged / non-privileged modeMaster / privileged / system / supervisor mode
Who runs hereApplication programsOS kernel, device drivers (in monolithic kernels)
Hardware access ADDEDNo direct access; must use system callsFull access to hardware and all memory
Privileged instructions ADDEDNot allowed: an attempt causes a trap to the OSAllowed
Crash impact ADDEDOnly that process diesThe whole system can crash (BSOD / kernel panic)
Address space ADDEDPrivate virtual address space per processSingle shared kernel address space
➕ Added for exam — Beyond two modes Intel x86 CPUs have 4 protection rings (Ring 0 to Ring 3). Ring 0 = kernel, Ring 3 = user; Rings 1 and 2 are rarely used. CPUs with virtualisation support add a VMM / hypervisor mode (sometimes called "Ring −1"). MULTICS used 8 rings.

3.2APrivileged Instructions, Traps & Interrupts ADDED

Privileged instruction: a machine instruction that can harm the system if misused. The hardware lets it run only in kernel mode. If a user program tries one, the hardware treats it as illegal and traps to the OS.
Privileged (kernel mode only)Non-privileged (allowed in user mode)
  • I/O instructions
  • Setting the timer
  • Turning interrupts on/off (enable/disable)
  • Setting the mode bit to kernel
  • Modifying memory-management registers (base/limit, page table)
  • Clearing memory, halt instruction, context-switch instructions
  • Reading the clock / time
  • Generating a trap (issuing a system call)
  • Arithmetic and logic operations
  • Reading the status of the processor
  • Sending the final printout to the printer via a system call
⚠️ Exam trap (Favourite MCQ) "Which is NOT privileged?" → Read the clock / Issue a trap instruction. "Set the timer" and "Disable interrupts" are privileged. Note the subtle pair: reading the clock is non-privileged, setting it is privileged. The switch from user to kernel mode itself happens through a non-privileged trap; switching back is privileged.

Trap vs interrupt

Interrupt (hardware)Trap / exception (software)
Generated by hardware devices (keyboard, disk, timer)Generated by software: a system call or an error (divide by zero, invalid memory access)
Asynchronous: can occur at any timeSynchronous: caused by the current instruction
Handled via the interrupt vector table → ISR (Interrupt Service Routine)Also called a software interrupt. Also switches to kernel mode.

A timer interrupt prevents a user program from hogging the CPU forever (e.g. an infinite loop). The OS sets the timer, which is privileged, before giving the CPU to a user program, and gets control back when it fires.

3.3Example: Mode Switching via System Call (printf)

🎓 From the lecture — printf()
  1. The program runs in user mode and reaches printf(...). Printing or displaying output needs hardware.
  2. So a system call must be executed in the kernel. The CPU switches from the user context to the kernel context (user space → kernel space). The lecture calls this a "context switch".
  3. The kernel executes the required system call.
  4. Then it returns, switching back to user mode, and the rest of the program continues.
"Bhasha anek, bhavna ek": the kernel does not care whether you wrote the program in C, C++, Python or Java. All of them ultimately want the hardware to do something, and the kernel uses its fixed set of system calls to do it.
🎓 From the lecture — The police station analogy A man whose house was robbed comes crying to the police station. Does he grab the FIR register, write the FIR himself and then go hunting for the thief himself? No. He says: "Sir, please write the FIR and catch the thief on my behalf." Writing FIRs is within the police officer's authority. Likewise, any work that interacts with the hardware is within the authority of the kernel / OS.
⚠️ Exam trap (Mode switch ≠ context switch) The lecture uses "context switch" for user → kernel. In textbook terms:
  • Mode switch: the same process moves from user mode to kernel mode (system call or interrupt). It is cheap, because only the mode bit and some registers change.
  • Context switch: the CPU switches from one process to another. The OS saves the old process's state in its PCB and loads the new one's. This is more expensive and is pure overhead.
A context switch always involves mode switches, but a mode switch does not always cause a context switch.

3.4fork() System Call

fork(): a UNIX/Linux process-control system call that creates a new process (child) by duplicating the calling process (parent). After fork(), both parent and child continue executing from the next instruction after the fork.
🎓 From the lecture When fork() returns 0, we are in the child process. In the lecture's words, "1 means parent process". The child is an identical copy of the parent: "the son looks exactly like his father".
⚠️ Exam trap (Correction: fork() return values) The lecture says fork returns "1" in the parent. That is not exact. The correct values are:
Return valueMeaning
0Returned in the child process
Positive (> 0)Returned in the parent: it is the PID of the newly created child (e.g. 4521), not literally 1
Negative (−1)fork failed; no child was created (e.g. the process limit was reached or memory ran out)
Remember: 0 → child, >0 → parent (child's PID), <0 → error. The child can find its parent with getppid() and itself with getpid().
Code: typical fork() usage 
pid_t pid = fork();
if (pid < 0) {            // error
    printf("fork failed");
} else if (pid == 0) {    // CHILD
    printf("I am child, my PID = %d", getpid());
} else {                  // PARENT (pid = child's PID)
    wait(NULL);           // wait for the child to finish
    printf("I am parent, child PID = %d", pid);
}
Order of output: the parent and child run concurrently, so without wait() the order of their output is not guaranteed. It depends on the CPU scheduler.
➕ Added for exam — What the child does and does not inherit
Inherited (copied) from parentDifferent in the child
Code (text), data, heap, stack (a copy of the address space), open file descriptors, environment, current working directory, signal handlers, user IDPID (new), PPID (= parent's PID), fork() return value (0), CPU time counters reset, pending signals and locks not inherited
After the fork, parent and child have separate address spaces: if the child changes a variable, the parent's copy is not affected. (Threads, by contrast, share memory; see Chapter 4.)

3.5Numerical Example: Child Processes Created by n fork() Calls

🎓 From the lecture — Building the tree
  • 1 fork(): parent P creates child C1. Leaf nodes = P, C1 = 2, children = 1.
  • 2 fork()s: at level 2, each existing process forks again. C1 creates C2, and P creates C3, while P and C1 remain. Leaves = 4, children = 3.
  • n fork()s: leaf nodes = 2ⁿ (total processes), and since one leaf is always the original parent, children = 2ⁿ − 1.
Essential formulas: fork()
n fork() calls in sequence (no conditions): Total processes (leaf nodes) = 2ⁿ Child processes created = 2ⁿ − 1 A printf() after all n forks is printed 2ⁿ times
for (i = 0; i < n; i++) { fork(); printf("X"); } "X" printed = 2¹ + 2² + … + 2ⁿ = 2ⁿ⁺¹ − 2 times
Numerical 1: two fork() calls (lecture) fork(); fork();
Step 1: n = 2.
Step 2: Total = 2² = 4 processes.
Step 3: Children = 2² − 1 = 3 (C1, C2, C3) plus 1 parent.
Conclusion: 4 leaf nodes, matching the tree in Figure 3.6.
Numerical 2: how many times is "Hello" printed? 
fork(); fork(); fork();
printf("Hello\n");
Step 1: n = 3, so after 3 forks there are 2³ = 8 processes.
Step 2: Each of the 8 processes executes printf once.
Conclusion: "Hello" is printed 8 times, and 7 child processes are created.
Numerical 3: fork inside a loop, printf inside the loop 
for (int i = 0; i < 3; i++) {
    fork();
    printf("X");
}
Step 1: i = 0: 1 → 2 processes, so 2 prints.
Step 2: i = 1: 2 → 4 processes, so 4 prints.
Step 3: i = 2: 4 → 8 processes, so 8 prints.
Conclusion: "X" is printed 2 + 4 + 8 = 14 times (= 2⁴ − 2). There are 8 processes in total and 7 children.
Numerical 4: only the child forks again 
if (fork() == 0)   // only the child enters
    fork();
printf("A");
Step 1: The first fork gives P and C1. Only C1 (return value 0) enters the if.
Step 2: C1 forks again and creates C2. P does not.
Conclusion: 3 processes (P, C1, C2), so "A" is printed 3 times and 2 children are created. The 2ⁿ formula only applies to unconditional forks.
Numerical 5: the classic fork() && fork() || fork() Rule: && evaluates its right side only if the left is non-zero (the parent). || evaluates its right side only if the left is zero (false).
Step 1: The first fork() gives P (gets >0) and C1 (gets 0).
Step 2: In P, the left side is true, so the second fork() runs, giving P (>0) and C2 (0). P's && is true, so it skips || fork(). C2's && is false, so it runs the third fork(), creating C3.
Step 3: In C1, the left side is 0, so && short-circuits to false and C1 runs the third fork(), creating C4.
Conclusion: processes = P, C1, C2, C3, C4 = 5 in total (4 children). This is a common GATE / bank-IT question.

3.6Need for fork() and Its Overhead

🎓 From the lecture — The contractor & the wall The question: if the parent is running fine, why make identical copies of it?
  • A contractor wants a 1,000-brick wall built in one day. One worker with only two hands says "have mercy, I'm human!"
  • The contractor brings in more workers of the same capacity, strength, build and height: identical copies. Now the wall can be built in a day.
  • Likewise, when many users ask for the same behaviour/task, creating each process from scratch would be a big overhead for the OS. With just one call, fork() creates an identical process with the same behaviour.
The catch (overhead): now the contractor has to pay wages to every worker. Each child, and child of a child, has the same requirements as the parent: its own PCB (Process Control Block), its own memory space and resources, and it needs CPU time. Solving one problem created another. The lecture leaves the question open ("Is there a way to avoid this? There is…") and answers it in the next chapter: threads.
➕ Added for exam — Real uses of fork() and how the overhead is reduced
  • Real uses: the shell forks a child for every command you type (fork + exec); web servers such as Apache (prefork) handle each client in a child process; parallel work splits a task across child processes.
  • Copy-on-Write (COW): modern kernels do not copy the parent's memory at fork time. Parent and child share the same physical pages, marked read-only. A page is copied only when one of them writes to it. This makes fork() fast, especially when exec() follows immediately.
  • vfork(): an older variant where the child borrows the parent's address space with no copy, and the parent is suspended until the child calls exec() or exit().
  • Threads (next chapter): "lightweight processes" that share code, data and files and have only their own stack and registers. They are far cheaper than forking full processes.

3.6Aexec(), wait(), exit(), Zombie & Orphan ADDED

CallWhat it does

Zombie (defunct) processOrphan process
The child has terminated, but the parent has not yet called wait(). Its entry (PID, exit status) remains in the process table.The parent terminated while the child is still running.
Uses no CPU or memory, but holds a PID slot. Too many can exhaust the PID table.It is adopted by init / systemd (PID 1), which later calls wait() for it.

⚠️ Exam trap (fork vs exec) fork = same program, new process. exec = same process (same PID), new program. The first user-space process in Linux is init / systemd with PID 1, and it is the ancestor of every other user process. The Windows equivalent of fork + exec is a single call, CreateProcess().

⚡ Rapid Revision — Chapter 3

  • System call = how a user program requests a kernel service. "Mummy, give me food" rather than entering her kitchen (the hardware) yourself. Police analogy: ask the officer to write the FIR.
  • Programs usually call an API (POSIX, Win32, Java). The library issues a trap, the system-call interface looks up the syscall table by number, and the handler runs.
  • Parameter passing: registers, memory block/table (address in a register, used by Linux), stack.
  • 6 types: Process control (fork, exec, exit, wait) · File (open, read, write, close) · Device (ioctl) · Information (getpid, time) · Communication (pipe, shm) · Protection (chmod).
  • printf is a library function that calls the write() system call.
  • Mode bit: 1 = user (slave, unprivileged); 0 = kernel (master, privileged, system, supervisor).
  • Privileged: I/O, set timer, enable/disable interrupts, set mode bit, MMU registers, halt. Not privileged: read clock, issue trap.
  • Interrupt = hardware, asynchronous. Trap = software (system call or error), synchronous.
  • Mode switch (same process, user↔kernel) ≠ context switch (process → process, saves the PCB).
  • fork() returns 0 in the child, the child's PID (>0) in the parent and −1 on error. The child is a copy of the parent with its own address space, a new PID and its own PCB.
  • n forks → 2ⁿ processes, 2ⁿ − 1 children. A printf inside a loop of n forks prints 2ⁿ⁺¹ − 2 times. fork() && fork() || fork() → 5 processes.
  • Why fork: the "identical workers build the wall" analogy; it is cheaper than creating from scratch. Overhead: each child needs its own PCB, memory and resources ("wages"). The fixes are Copy-on-Write, vfork and threads.
  • exec replaces the program with the same PID. wait makes the parent block. Zombie = dead child not yet waited for. Orphan = parent died, so init/systemd (PID 1) adopts the child.
